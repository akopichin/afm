# Host `afm serve`

Пользовательское поведение: [Serve](../../docs/serve.md). MCP одного рана —
[mcpserver](../mcpserver/AGENTS.md), HTTP-границы — [server](../server/AGENTS.md).

- Host владеет только своим состоянием в `~/.afm/serve` (lock, receipts, `attached.json`,
  логи, prompt-файлы). Каталоги пользователя и run-директории не удаляй и не чисть:
  `Cleanup`/`RemoveAll`/`pruneRuns` сюда не относятся. Единственное удаление чужого файла —
  запись реестра процесса с доказанным выходом и перечитыванием (`Discovery.Reap`).
- Владение: managed — запущено host (есть receipt); attached — явный `afm_run_attach` или
  ручной run (запись реестра без `launch_id`), чей endpoint подтвердил свой `instance_id`;
  discovered — непроверенная запись или запуск чужого host. Forwarding работает для managed и
  attached, cancel и release — только для managed: attached никогда не получает сигнал,
  discovered не управляется. Ручной run attached только по листингу и в `attached.json` не
  пишется: его прежние циклы видны, пока есть запись реестра, после выхода — только после
  явного attach. Остановка host (SIGINT/SIGTERM) не трогает ни один run.
- Identity — `instance_id` + маркер старта процесса + ответ `/api/runtime`. Сигнал уходит
  только после проверки маркера (`signalProcess` берёт handle до проверки, на Linux это
  pidfd) и свежего `/api/runtime`: `instance_id` и `run_id` должны совпасть, иначе
  `run_changed`. Тот же `instance_id` + `run_id` проверяется при каждом (пере)подключении
  MCP-сессии. Повторное использование порта или PID не должно давать управление чужим
  процессом. SIGKILL — только native; Docker-run получает SIGINT и `stop_pending`.
- Права детей: пустой набор групп host — это read-only (`--mcp-allow read`), а не «все».
  Умолчание «все группы» принадлежит CLI (`AllHostGroups`), не `NewLauncher`.
- Допуск запуска сравнивает identity: checkout (резолвленный корень, для явного worktree —
  его путь от базы `engine.WorktreeBase` с учётом `root_dir`, symlink-ы раскрыты) и
  эффективное имя рана (worktree, иначе имя флоу), а не id проекта или имя файла. Identity
  вычисляется один раз и пишется в первый receipt (`Receipt.Identity`); позже конфиг и флоу
  не перечитываются. Для pipeline имя флоу известно только ребёнку: до его записи в реестре
  заменой служит источник pipeline. Неизвестная identity конфликтует со всем, пока процесс жив.
- История repeat-циклов хранится в receipt (`PreviousRunIDs`) и в `attached.json`, ограничена
  `maxRunHistory`; отчёт по прежнему циклу должен работать после выхода процесса. Каждое
  наблюдение (живая, ранняя и мёртвая запись реестра, листинг, attach, повторный attach)
  сливается одной `mergeRunBinding` и сохраняется до того, как его показали или удалили
  источник; запись реестра чужого instance/процесса не сливается. Сохранённый run (`based`) и
  запись реестра читаются до probe, а не в коммите: наблюдение, обогнанное более новым коммитом,
  не двигает текущий run, но его run_id остаётся в истории, а запись, прочитанная после ответа,
  выдала бы более новый run за предшествующий ответу. Наблюдение, которое обогнал выход
  процесса, тоже сливается; состояние завершения при этом не меняется. Это касается и последнего
  взгляда reaper на запись (в том числе Docker-контейнер, переживший процесс). Вернуть run из истории может только живой
  ответ процесса (`runBinding.Live`), полученный после последнего коммита, — так чинится
  проигравшее гонку наблюдение, которое на деле было новее; запись реестра без ответа этого
  не может (она отстаёт от runtime). На старте `reapExited` сохраняет каждое наблюдение скана
  до перечитывания (живое — процесс может выйти раньше любого другого взгляда; мёртвое — запись
  может исчезнуть до перечитывания) и повторную проверку перед удалением мёртвой записи, и только
  потом удаляет её (ошибка сохранения оставляет запись), затем `Recover`.
  Attach — read-modify-write под одним локом (`Host.UpdateAttached`).
- Запуск живёт, пока жив процесс: ранняя запись реестра без `api_url` с живым pid
  усыновляется; `ready=false` дольше `ReadyTimeout` — `failed`, слот `max_starting`
  освобождается, но `max_running` и конфликт identity — только когда выход процесса доказан
  (`ProcessGone`; правило `holdsRuntime` общее для допуска, watcher, reaper и recovery).
  Таймаут — условный переход из `starting` на текущем receipt, не на устаревшем снимке.
  Docker-ран, чей контейнер ещё отвечает (`active_orphaned`), держит слот после выхода
  host-процесса.
- Все loopback-адреса проходят через `ParseLoopbackURL` (его же использует мост
  `afm mcp serve`): без userinfo, без redirect, только `http`. Ошибки не содержат исходный
  URL (в нём может быть пароль). Сбои транспорта к рану (probe, connect/verify сессии,
  пересылка, подписки) наружу выходят только как `*RemoteError` с фиксированным текстом:
  net/http цитирует битый `Location` редиректа до `CheckRedirect`. Причина доступна через
  `errors.Is/As`.
- Receipt создаётся до работы через tmp+fsync+`os.Link`; повтор `request_id` с теми же
  параметрами возвращает тот же receipt, с другими — конфликт. Повтор сверяется с receipt до
  проверок изменчивого (файл флоу, список проектов, права host): `canonical` смотрит только на
  сам запрос, `prepare` — только для нового запуска; опущенный `mcp_allow` повтора равен
  выданному при приёме. Упавший старт тоже тратит
  `request_id`. `instance_id` ребёнка выводится из `launch_id` (`InstanceIDFor`), поэтому
  его находят и до записи pid. Неизвестная судьба запуска — `uncertain`, потом `lost`;
  host никогда не перезапускает ребёнка вслепую. `lost` — условный переход на текущем receipt:
  запуск, чей процесс уже найден (PID записан), не теряется.
- Ребёнок стартует через `exec.Command` без контекста запроса (отмена MCP-вызова не должна
  убивать принятую работу), в своей сессии, со stdin `/dev/null`, логом 0600 и env из
  `childenv.ForAFMChild`. Prompt передаётся файлом `--task @…`, в argv его нет; файл
  удаляется, когда запуск готов или завершён. Reaper не ждёт `Close`: ребёнок переживает host.
  `Host.Close` берёт тот же лок, что и запись, и после него любая запись отказывается
  (`errHostClosed`): reaper закрытого host дожидается ребёнка, но ничего не пишет — состояние
  уже может принадлежать следующему host.
- Шлюз не копирует семантику этапа 1: инструменты и шаблоны ресурсов берутся из
  `mcpserver.Catalog()`/`ResourceTemplates()`, `run_id` снимается для не-`RunBound`.
  Сессия принимается после сверки `run_id` из `afm_run_status` в той же сессии. Control
  после обрыва транспорта не повторяется (`outcome_unknown`); повтор возможен только для
  read-only и для `ErrSessionMissing` (запрос не был доставлен). Группа проверяется в
  каждом вызове, не только при регистрации. Подписки считаются по host-сессиям (членство
  URI → сессии, отключение клиента снимает его подписки), а не по числу вызовов. Изменение
  членства и ответ рана на subscribe/unsubscribe идут под одним `transitions` (Subscribe,
  Unsubscribe, ReleaseHost и replay новой сессии; dial — вне него); ожидание лока ограничено
  контекстом вызова, держатель отменяется через `Close`. Новая сессия публикуется после replay
  подписок того же run_id: обрыв транспорта её не публикует, отказ рана снимает членство этого
  URI и уведомляет его подписчиков. Подписка подтверждается, только пока сессия с upstream-
  подпиской текущая. SDK записывает подписчика лишь после ответа хендлера, поэтому
  `ResourceUpdated`, отправленный в этом окне (в том числе о потере сессии), middleware
  `recordSubscribers` повторяет после записи. Он же выполняет subscribe и unsubscribe одного
  клиента и URI по очереди до записи SDK: иначе unsubscribe, обогнавший subscribe, оставит SDK
  подписчика без подписки рана. Сбойная или закончившаяся сессия снимается одним `retire`: не ждёт её
  вызовов (`ClientSession.Close` ждёт все — закрытие в фоне), один раз шлёт `ResourceUpdated`
  подписчикам ключа (кроме остановки host) и вне локов. `Close`
  сначала отменяет пересланные вызовы и закрывает сессии к ранам (параллельно, с пределом
  `closeGrace`), и только потом host-сессии: иначе припаркованный `afm_run_wait` держит
  остановку.
- Ошибки SDK `-32005`/`-32003`/`-32001` — обрыв соединения, а не ответ рана.
- YAML-контракт `serve.yaml`: парсер, валидация, `schema/serve.schema.json` и guard в
  `pkg/schemacheck` меняются вместе.
- Тесты: настоящие дети — это сам тестовый бинарь (`TestMain` + `SERVE_FAKE_AFM=1`), HOME и
  каталоги состояния только временные, настоящий `~/.afm` не трогай. Cleanup: убить детей,
  дождаться `launcher.reapers`, и только потом удалять каталоги.
