# Release Notes — afm dashboard

## 2026-09-04

- **Файловый браузер: переключатель вида «все / изменённые файлы»** (Docker-only). Сверху левой панели — расширяемый тулбар инструментов с сегментом из трёх режимов:
  - **All** — прежнее дерево всех файлов (по умолчанию);
  - **Unstaged** — плоский список отличий от индекса (`git diff`) + untracked-файлы как *added*;
  - **vs HEAD** — плоский список отличий от последнего коммита (`git diff HEAD`) + untracked как *added*.
  - Untracked видны в обоих changed-режимах (агенты постоянно создают файлы); режимы расходятся только на staged-правках. Тултип каждого режима поясняет baseline.
  - Новый компонент `ChangedFilesList`: строка со статус-бейджем **M/A/D** (буква — не только цвет; слово статуса озвучивается скринридером через visually-hidden span). Selectable-файл открывается кликом (таб **DIFF** справа по-прежнему `HEAD → current`), выбирается чекбоксом для вставки `[AFM file: …]`. Удалённый файл — приглушённая некликабельная строка-маркер. Поле поиска скрыто в changed-режимах и возвращается в **All**; кнопка **Refresh** перезапрашивает список (фонового git-polling нет). Список скроллится внутри модалки; длинные пути обрезаются и не вылезают в правую панель. Работает во всех скинах × light/dark.
  - Клиент `getChanged` (`api/files-client.ts`), мок-роут `/api/files/changed` в `test-support.ts`.
- `npx vitest run`: 382 теста, 39 test files.

## 2026-08-10

- **Видимость авто-ответов afm на вопросы non-interactive стадий** (бэкенд-фича: `pollQuestions` сам отвечает на вопрос агента вместо перевода стадии в `awaiting_user_input`, когда `interactive` не `true`):
  - Event feed: новый case `auto_answered` — строка вида `auto-answered q1: <ответ>`.
  - Панель диалога (`DialogChannel`): отвеченная запись с меткой авто-ответа получает класс `qa-auto` и бейдж `⚙` (`title="Answered automatically by afm"`).
  - Два бага, найденные только ручной проверкой в браузере (юнит-тесты в изоляции их не поймали):
    1. Панель диалога вообще не монтировалась для обычных non-interactive стадий — `App.tsx`'s `showDialog` был `interactive || autonomous`, а авто-ответ по определению происходит именно на стадии, у которой оба флага `false`. Добавлен третий сигнал `stage_has_dialog` (`/api/status`, тот же file-presence паттерн, что и `stage_autonomous`), `showDialog`/внутренний гейт `DialogChannel`'s `hasContent` теперь также учитывают его.
    2. Событие `auto_answered` терялось при перезагрузке страницы/переподключении — публиковалось только живьём в WebSocket-шину, без дублирования в `notices.jsonl` (в отличие от `agent_completed`/`context_warning`/`script_output`, которые уже это делают). Клиент, подключившийся после срабатывания, никогда не видел строку в ленте, хотя история диалога была на месте.

## 2026-08-07

- **Комментарии к плану/диалогу и скролл:**
  - Форма комментария к строке плана/вопроса теперь закрывается только по явному ×, а не при выделении текста мышью для копирования (клик вне формы больше не сбрасывает набранный текст).
  - Клик на другую строку плана, пока открыт непустой черновик комментария, больше не переносит и не закрывает форму — сначала нужно закрыть текущую (× или отправка).
  - `APPROVE`/`SEND REVISION` в панели плана и кнопка `▸ SEND` в диалоге блокируются, пока есть хотя бы один сохранённый комментарий **или** непустой незакрытый черновик (раньше проверялись только сохранённые).
  - `useStickToBottom` переведён с `useRef` на callback-ref — чинит баг, при котором панель диалога/чата открывалась со скроллом к первому сообщению вместо последнего (контейнер монтировался позже эффекта, слушавшего старый `ref.current`).
- **Авто-рост textarea** (комментарий к строке плана, реплика в диалоге, заметка агенту):
  - Новый хук `useAutoGrowTextarea`: растёт по мере набора текста до `maxHeight`, дальше — обычный скролл; ручной resize выше `maxHeight` отключает авто-расчёт высоты до следующей очистки поля.
  - Ручная resize-хватка (`resize: vertical`) сохранена — авто-рост её не подавляет.
  - Три бага, найденные только вручную в браузере (автотесты и код-ревью их не поймали): (1) CSS `max-height: 400px` на самой textarea не давал ручному resize вытянуть её выше — убран, авто-рост сам ограничивает высоту через JS; (2) `ResizeObserver` навешивался в `useEffect` с пустыми deps на компоненте, где textarea монтируется условно (`{activeCommentLine === ... && <textarea/>}`) — тот же класс бага, что и в `useStickToBottom` выше, лечится тем же callback-ref паттерном; (3) `scrollIntoView` целился в саму textarea, а не в кнопку под ней — при росте до `maxHeight` внутри невысокого контейнера кнопка "Добавить"/"Отправить" уезжала за нижнюю границу и пряталась.
- **Персистентные IDLE/BACKOFF метрики футера** (переживают reload/restart, не тикают в офлайне):
  - Сервер считает накопленные idle/backoff инкрементально в `pkg/state` (`RunState.IdleAccumulatedMs`/`BackoffAccumulatedMs`), восстанавливает их replay'ем `events.jsonl` при `Store.Open`/`LoadRunState` — старые раны получают корректные числа при первом же обращении после обновления, без миграций. Отдаётся через `/api/status` (`idle_accumulated_ms`, `idle_since`, `backoff_accumulated_ms`, `backoff_open_since`).
  - Хуки `useIdleMs`/`useBackoffMs` (замена `useIdleTime`/`useStatusDuration`, которые теряли историю за пределами 200-событийного кэша `useEventFeed`) считают `accumulated + live delta` от серверного якоря — как уже работавший `useElapsed`. Замирают, пока WebSocket не в сети (`connected === false`), и подхватывают уже скорректированное сервером значение сразу при реконнекте — никакой отдельной логики "доверстать пропущенное" на клиенте не нужно.
  - `ELAPSED`/`STARTED` не менялись — уже были restart-safe и тикают через офлайн по замыслу.
- `npx vitest run`: 210/210 тестов, 26 test files.
