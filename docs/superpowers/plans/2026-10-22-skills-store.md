# Skills: центральное хранилище `~/.afm/skills` + относительные симлинки в агентов

Ревизия 8 — после codex-ревью №1–№6 и решений пользователя (2026-10-22):
убрать `--skills-dir`; все скиллы afm — с префиксом `afm-`; обновить пин Codex в образе. См. «Журнал ревью» в конце.

## Цель

Скиллы afm видны Claude и Codex, которых запускает afm, на хосте
и в Docker, и совпадают по версии с установленным afm.
Сейчас `afm install-skills` копирует папки только в `~/.claude/skills`, без
`--force` старые версии не обновляются, Codex скиллов afm не видит, а
`make install-skills` — второй независимый установщик.

## Имена скиллов: префикс `afm-`

Как в goga (`goga-*`), все скиллы afm называются `afm-*`, чтобы не путать их с
личными скиллами пользователя и скиллами других инструментов:

| Было | Стало |
|---|---|
| `afm` | `afm-run` |
| `afm-check`, `afm-init`, `afm-retry`, `afm-review` | без изменений |
| `live-run` | `afm-live-run` |
| `mesh-driven-development` | `afm-mesh-driven-development` |

Переименование — папка в `assets/claude/skills/` + `name:` во frontmatter + все
упоминания (`/afm` → `/afm-run` в `assets/claude/skills/afm-*/SKILL.md`,
`docs/getting-started.md`, `docs/browser.md:68`, `install.sh`, README).
Тест: каждое embedded-имя начинается с `afm-` и совпадает с `name:`.

**Старые имена** (`afm`, `live-run`, `mesh-driven-development`) afm **не трогает
никогда** — ни ссылки, ни папки, ни с `--force`: под этими именами у
пользователя могут лежать собственные скиллы (у автора `live-run` и
`mesh-driven-development` — личные) и не упоминает их в выводе (подсказка о
старых именах была в первой версии реализации и удалена после ревью кода: она
шумела на каждом `afm run`). CHANGELOG описывает переименование.

## Образец: goga (`goga connect`)

Хранилище `~/.goga/skills/` + симлинк на каждый скилл в `~/.claude/skills`,
`~/.codex/skills`, …, re-sync при install/upgrade. Отличие: goga пишет
**абсолютные** ссылки, а в Docker-ране afm `HOME=/home/afm`
(`pkg/docker/launcher.go:24`) — там они битые. afm пишет **относительные**.

## Контракт версий

Store один на машину: **последний успешный sync определяет содержимое скиллов
для всех агентов**. Обновление пофайловое, не транзакционное: sync, завершившийся
ошибкой, может оставить смесь версий; следующий успешный sync восстанавливает
полный набор (автосинхронизация делает это при следующем `afm run`). Если параллельно стоят разные afm (stable/alpha, см.
`docs/getting-started.md`), ран версии V1 после sync из V2 читает скиллы V2.
Это осознанный компромисс (без версионных хранилищ), описывается в
документации. Скиллы пишутся обратно совместимыми с предыдущей версией CLI,
насколько это возможно.

## Модель угроз

`~/.afm` смонтирован в контейнер на запись (`launcher.go:337`), агенты в
контейнере и так могут переписать любой файл store. Защищаемся от **случайного**
повреждения чужих данных (симлинк, оставленный пользователем или прошлой
версией), а не от злонамеренного агента с правом записи в `~/.afm`: такой агент
может изменить содержимое скилла напрямую, и sync это не усугубляет.

## Решения

1. **Хранилище** `~/.afm/skills/<name>/<file>` — принадлежит afm (документируем:
   свои скиллы туда не класть). Файлы — все файлы embedded-скилла (сейчас это
   только `SKILL.md`). Frontmatter каждого embedded `SKILL.md` содержит `name`
   (= имя папки) и `description` по документации Codex; сейчас `name` есть
   только у `mesh-driven-development`, остальным добавляем (задача 1a). Спайк
   показал, что Codex 0.162.1 подставляет имя папки при отсутствии `name`, но
   полагаться на это не будем.
2. **Запись store без следования симлинкам.** `os.Lstat` на `~/.afm` и
   `~/.afm/skills` **до** `MkdirAll`: существующий симлинк или не-папка → ошибка,
   ничего не пишем. Затем для `<name>` и `<name>/<file>`:
   - симлинк (store принадлежит afm) → удаляем саму запись-симлинк (`os.Remove`,
     без следования), создаём настоящую;
   - `<name>` — не папка, `<file>` — не обычный файл (FIFO, сокет, устройство) →
     ошибка для этого скилла, содержимое не читаем (нет зависания на FIFO).
   Файл пишется temp-файлом в `<name>/` + `os.Rename` поверх; обычный файл с
   совпадающим содержимым не переписывается.
3. **Папки агентов** (`agentDirs`):
   - Claude: `~/.claude/skills` (флаг `--skills-dir` **удаляется**: он нигде не
     документирован, использовался только тестами, а произвольный путь был
     источником почти всех находок о пересечениях; тесты подменяют `$HOME`);
   - Codex: `$CODEX_HOME/skills`, иначе `~/.codex/skills`.
   Обе **создаются всегда** (`MkdirAll`, после проверок п. 4) — без эвристики
   «установлен ли агент»: Codex может быть установлен, но ещё не запускаться, или
   жить только в образе. Чистая установка и ручной `docker run` получают ссылки.
   Docker-совместимость обещаем для стандартной раскладки (`~/.claude/skills`,
   `~/.codex/skills`); в контейнере `CODEX_HOME` всё равно `/home/afm/.codex`.
4. **Канонизация и проверка пересечения — до создания папок агентов.**
   Корни {store, папка Claude, папка Codex} должны быть **попарно непересекающимися**:
   ни один не совпадает с другим, не лежит внутри другого и не содержит другой.
   Иначе `--force` мог бы перенести в backup папку, содержащую store или другую
   папку агента. После удаления `--skills-dir` произвольным остаётся только
   `$CODEX_HOME` (например, `CODEX_HOME=~/.afm`), плюс симлинки `~/.claude`/`~/.afm`.
   Порядок: проверки корней store (п. 2) → `MkdirAll` store → канонизация всех
   трёх корней одной функцией `canonical(p)`: `filepath.Abs`, затем
   `EvalSymlinks` ближайшего существующего предка + неразрешённый хвост
   (симлинки внутри существующей части раскрыты, отсутствующие компоненты
   сохранены). Пересечение пары = один канонический путь равен другому или
   начинается с него + разделитель, **сравнение без учёта регистра** (macOS/Windows
   по умолчанию нечувствительны к регистру; на чувствительной ФС это даёт лишь
   ложный отказ для путей, различающихся только регистром — допустимо).
   При пересечении — ошибка, ничего не создаём. Общие предки (`$HOME`, `/`)
   пересечением не считаются, соседние папки проходят.
   Только после этого `MkdirAll` папки агента,
   `filepath.EvalSymlinks` обеих сторон и
   `rel = filepath.Rel(agentDirReal, storeReal/<name>)`; для стандартной
   раскладки это `../../.afm/skills/<name>`.
   Проверено ревью №1: Claude в контейнере (`/home/afm/.claude` bind mount) и
   Codex (`cp -a` в `/home/afm/.codex/skills`) резолвят её в `/home/afm/.afm/skills/<name>`.
5. **Классификация `<agentDir>/<name>`** (через `os.Lstat`) для каждого embedded-имени:
   - нет записи → создать ссылку;
   - симлинк, чья цель лежит в store → afm-ссылка: заменить, если `os.Readlink`
     отличается от вычисленного `rel` (в том числе исправная абсолютная ссылка —
     в Docker она сломается);
   - симлинк куда-то ещё (goga, личный) → не трогать никогда (и с `--force`), предупредить;
   - настоящая папка (копия старого установщика или своя) → без `--force`
     пропустить с предупреждением «настоящая папка; `afm install-skills --force`
     заменит её ссылкой, папка уйдёт в backup»; с `--force` → заменить ссылкой.
     Подсказка — всегда ровно `afm install-skills --force` (флагов пути больше нет).
     Содержимое не сравниваем: миграция только явная, backup всегда сохраняется;
   - любой другой тип (обычный файл, FIFO, сокет) → не трогать никогда, предупредить.
6. **Одна процедура замены записи на ссылку** (`replaceWithLink`) для всех веток:
   1. создать temp-симлинк `<agentDir>/.afm-tmp-<name>-<rand>` → `rel`;
   2. если запись — папка: создать уникальную настоящую папку
      `os.MkdirTemp(filepath.Dir(agentDirReal), ".afm-skills-backup-")` (рядом с
      папкой агента — та же ФС в типичной раскладке; новая папка, поэтому не
      совпадает с `agentDir` и не следует чужим симлинкам; без коллизий имён) и
      `os.Rename` исходную папку в `<backup>/<name>`;
   3. если запись — afm-ссылка, сначала `os.Remove` самой ссылки (на Windows
      `Rename` поверх существующей ссылки на каталог не работает); затем
      `os.Rename` temp-симлинк на `<agentDir>/<name>`;
   4. при ошибке шага 3 — вернуть папку из backup; при ошибке отката — оставить
      backup и сообщить его путь;
   5. после успеха backup остаётся, его путь печатается.
   Ошибка `os.Rename` в backup (например, `EXDEV`, если папка агента — точка
   монтирования) → запись не трогаем, temp-симлинк удаляем, сообщаем ошибку для
   этого скилла; остальные скиллы продолжают устанавливаться.
   Файлы, которые afm не ставил, не удаляются ни в одном режиме.
7. **Никакого fallback-копирования.** Не удалось создать симлинк (например,
   Windows без прав на симлинки) → ошибка для агента с подсказкой (Developer Mode
   на Windows). Второй алгоритм установки не поддерживаем.
8. **Никакого удаления из store и никакого манифеста.** Sync идемпотентен и дёшев
   (~7 файлов + ~14 `Lstat`), выполняется полностью при каждом вызове — чинит
   удалённые/битые ссылки, повреждённые файлы, появление Codex. Удаление
   вышедших скиллов — вне скоупа (ни один ещё не удалялся).
9. **Конкурентность** — весь sync под существующим `progress.Lock`
   (`pkg/progress/progress.go:106`) на `~/.afm/skills.lock` (вне store; перед
   открытием `os.Lstat`: существующая запись не обычный файл → ошибка; lock-файл
   никогда не заменяется и не удаляется): сериализует
   параллельные `afm run` / `install-skills` на хосте. Записи контейнерных агентов
   им не синхронизируются — см. модель угроз.
10. **Автосинхронизация** — `afm run` до Docker re-exec вызывает
    `syncSkillsForRun(home, stderr)`: при `config.InContainer()` ничего не делает
    (ни managed re-exec, ни ручной контейнер не пишут в смонтированное хостовое
    store), иначе `Sync` с `Force=false`; предупреждения и ошибка → stderr, ран
    продолжается. Агенты в контейнере видят скиллы хостовой версии (осознанно).
11. **Пути в `<skills>` промпта — НЕ делаем.** Агенты без нативных скиллов,
    которые afm запускает сейчас, файлов прочитать не могут
    (`scripts/openai-as-claude.sh` — текстовый запрос, `cursor-as-claude.sh` —
    удалённый Cloud Agent), а Claude и Codex получают скиллы нативно.
12. **Ручной `docker run`:** sync только на хосте, поэтому в `docs/docker.md` —
    один раз выполнить `afm install-skills` на хосте (создаёт папки обоих агентов
    всегда, п. 3). Рецепт дополняется монтированием Codex-состояния, которое
    entrypoint уже умеет копировать (`docker-entrypoint.sh:25`):
    `-v ~/.codex:/tmp/host-codex:ro`. Без него Codex в контейнере скиллов не видит
    — это явно написано в доке. Явный `install-skills` в контейнере не запрещён.
13. **Переход со старого установщика.** Старые настоящие папки в
    `~/.claude/skills` автоматически не мигрируют (п. 5): автосинхронизация
    печатает предупреждение с командой `afm install-skills --force`, пока папка
    не заменена. `install.sh` вызывает `install-skills --force` — это безопасно,
    т.к. `--force` переносит папки в backup, ничего не удаляя. CHANGELOG и
    getting-started явно описывают одноразовую миграцию.

## Тесты (TDD, `t.TempDir()` как `$HOME`)

Общая подготовка каждого теста: `t.Setenv("HOME", tmp)` **и**
`t.Setenv("CODEX_HOME", "")` (иначе унаследованный `CODEX_HOME` разработчика
заставит тест писать в настоящие Codex-скиллы); свой `CODEX_HOME` — только в
кейсах, которые его проверяют.

0. `Sync("", false)` и `Sync("relative", false)` → ошибка, файловая система не изменена.

Store:
1. Чистый `$HOME` (нет ни `.claude`, ни `.codex`, ни `.afm`): store заполнен,
   `~/.claude/skills` и `~/.codex/skills` созданы со ссылками `../../.afm/skills/<name>`.
2. `CODEX_HOME=<tmp>/cx` — ссылки в `<tmp>/cx/skills`, `~/.codex` не создан.
3. Повторный `Sync` — без изменений (mtime не меняется).
4. V1 → V2 (подмена embedded FS): файл в store обновлён, ссылки целы.
5. Ошибка замены файла (read-only `<name>/`) → прежний файл сохранён, ошибка возвращена.
6. `~/.afm/skills` — симлинк → ошибка, ничего не записано.
7. `~/.afm/skills/afm-run` — симлинк на внешнюю папку → внешний `SKILL.md` не изменён,
   в store настоящая папка; то же для `~/.afm/skills/afm-run/SKILL.md`-симлинка.
7a. `~/.afm/skills/afm-run/SKILL.md` — FIFO (Unix) → ошибка для скилла, sync не зависает
    (тест с таймаутом).
7b. `~/.afm/skills.lock` — симлинк → ошибка до любых записей.

Папки агентов:
8. Настоящая папка (с `notes.md`) → без `Force` не тронута, предупреждение с
   командой; с `Force` → ссылка, backup содержит всё, путь в отчёте.
9. Миграция legacy: настоящая папка V1 → `Force` → ссылка; затем embedded V2 →
   обычный `Sync` → агент читает V2 через ссылку; затем V3 — так же.
9a. Обычный файл `~/.claude/skills/afm-run` → не тронут ни с `Force`, ни без.
10. Ошибка шага 3 `replaceWithLink` (инъекция) с `Force` → папка возвращена на место.
