# Ожидание ответа пользователя в интерактивных стадиях: таймаут и воркэраунд

**Дата:** 2026-07-17
**Статус:** воркэраунд (proper-fix отложен)

## Проблема

Интерактивный агент, ожидающий ответа на вопрос, крутит bash-цикл
(`while [ ! -f answer.json ]; do sleep 30; done`) и в это время **ничего не пишет
в stdout**. Idle-timeout исполнителя (`pkg/executor/executor.go:507`, по умолчанию
**30 минут**) сбрасывается только на новой строке stdout — поэтому через 30 минут
ожидания он срабатывает, убивает агента, и стадия падает (ошибка `idle timeout`
не входит в retryable-набор → `EvFail`).

Итог: **по умолчанию ответить нужно примерно за 30 минут**, иначе стадия упадёт.
Это pre-existing поведение (аудит-находка #8, кластер «lifecycle процессов»),
кластером «надёжность ядра + персистентность» НЕ затрагивалось.

## Воркэраунд (можно сделать сейчас, без изменения кода)

Поднять idle-timeout в `.afm/config.yaml` (или глобальном `~/.afm/config.yaml`):

```yaml
executor:
  idle_timeout: 24h
```

Тогда окно ответа станет сутки (значение — Go-duration: `24h`, `12h`, `168h` и т.п.).
Побочный эффект: реально зависший агент тоже будет жить дольше до принудительного
убийства — приемлемо, если интерактивные стадии для тебя важнее быстрого детекта
зависаний.

## Proper-fix (отложен, отдельная итерация)

Исключить состояние `awaiting_user_input` из idle-timeout: пока стадия ждёт ответа,
таймер не должен убивать агента (ожидание человека не равно зависанию). Тогда
«ответить хоть через неделю» будет работать без ручной настройки таймаута, а
idle-timeout продолжит ловить только реально застрявших агентов в рабочих фазах.
Находится в отложенном кластере «lifecycle процессов» (см.
`.superpowers/sdd/progress.md` и аудит-находку #8).
