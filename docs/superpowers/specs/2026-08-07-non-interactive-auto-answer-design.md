# Авто-ответ на вопросы в non-interactive стадиях — design

Date: 2026-08-07

## Контекст

Файловый диалоговый протокол (`AFM_STAGE_DIR`, `<phase>.<id>.question.json` /
`<phase>.<id>.answer.json`, см. раздел «File-Based Dialog Protocol» в
CLAUDE.md) сегодня рассчитан на то, что вопрос агента дойдёт до человека
через дашборд. Но агент или используемый им скилл может решить задать
вопрос независимо от того, помечена ли стадия `interactive: true` — просто
потому что скилл сам всегда использует этот протокол, когда ему нужно
уточнение. Если стадия при этом `interactive: false` (или флаг не указан —
это тот же дефолт), происходит следующее:

- `pkg/orchestrator/runner_factory.go` не пробрасывает агенту
  `AFM_STAGE_DIR` вообще (кроме автономного трека `agents: [auto]`) — писать
  question.json физически некуда для обычных planning/implementation/review
  стадий.
- Даже если агент всё же обнаружит вопрос через какой-то параллельный канал
  (или для `agents: [auto]`, где `AFM_STAGE_DIR` уже есть), фоновый поллер
  (`pkg/orchestrator/dialog_poller.go`) переводит стадию в
  `awaiting_user_input` так же, как для интерактивной — но в автоматическом
  (non-interactive) флоу это никто не отвечает: стадия либо зависает
  бессрочно, либо агент, устав ждать, завершает процесс без ответа —
  `pkg/orchestrator/retry.go`'s `runWithRetry` для non-interactive/non-auto
  стадии в этом случае идёт по пути `completionCheck` → «missing artifact or
  incomplete» → стадия падает (`EvFail`), падение каскадируется на зависимые
  стадии (`failBlockedStages`).

## Цель

Non-interactive стадия (`interactive` не `true`, включая дефолт и
`agents: [auto]`), у которой агент/скилл написал вопрос через файловый
протокол, не должна зависать или падать из-за отсутствия ответа. afm сам
синтезирует ответ — выбирая явно помеченный «рекомендованный» вариант или
первый по списку — атомарно записывает `answer.json`, и агент (у которого
есть собственный опрашивающий цикл, как в интерактивном протоколе) продолжает
работу, не отличая это от настоящего ответа пользователя.

## Область действия

- Применяется к любой стадии, где `stage.Interactive != true` — то есть и к
  обычным planning/implementation/review с `interactive: false`/дефолтом, и
  к автономному треку `agents: [auto]` (который сегодня **всегда** ждёт
  живого человека независимо от `interactive` — это тоже переводим на
  авто-ответ). Единственное исключение — явный `interactive: true`.
- Не меняются: промпты (`pkg/prompts/builder.go`), `retry.go`'s условие
  `(s.Interactive || phase == phaseAutonomous) && hasOpenQuestion` (держит
  стадию открытой на выходе агента без ответа) и сессии/`--resume` — они
  остаются исключительно для настоящего interactive-протокола. Обоснование
  см. в разделе «Не покрытый крайний случай» ниже.

## Архитектура

### 1. `pkg/orchestrator/runner_factory.go` — `AFM_STAGE_DIR` всегда

`StageDir` сейчас проставляется в `Executor.Config` только когда
`s.Interactive` или `phase == phaseAutonomous`. Убираем это ограничение —
`StageDir` проставляется для любой стадии/фазы, независимо от `Interactive`.
Без этого агенту в обычной non-interactive стадии физически некуда писать
`question.json`. Остальная часть non-interactive-ветки (plain runner, без
`--session-id`/`--resume`) не меняется — авто-ответ рассчитан на то, что
агент ждёт файл в текущем процессе, а не на восстановление сессии после
перезапуска.

### 2. `pkg/mcp/dialog.go` — выбор и запись авто-ответа

Новая чистая функция:

```go
func PickAutoAnswer(q QuestionFile) (answer string, fromOptions bool)
```

- Если `q.Options` пуст (открытый вопрос, только `allow_custom`) —
  возвращает фиксированный текст «Прими самое релевантное решение
  автономно или предложи варианты ответов», `fromOptions=false`.
- Иначе ищет в текстах вариантов (case-insensitive substring) маркеры, в
  этом порядке: `(recommended)`, `(default)`, `(рекомендую)`,
  `(рекомендуется)`, `(по умолчанию)`. Первый вариант, где найден любой из
  маркеров, возвращается с вырезанной пометкой (и лишним пробелом/дефисом
  перед ней), `fromOptions=true`.
- Если ни у одного варианта маркера нет — возвращается `options[0]` как
  есть, `fromOptions=true`.

Туда же выносится (extract) текущая atomic-write-логика ответа из
`pkg/server/handlers.go`'s `handleDialogAnswer` (O_EXCL создание
`answer.json` + append в `dialog.jsonl`) в переиспользуемую функцию:

```go
func WriteAnswer(stageDir, phase, id, answer string, fromOptions bool, role string) error
```

HTTP-хендлер и новый авто-ответчик пишут через один и тот же атомарный
путь — без дублирования инварианта «answer.json создаётся ровно один раз,
O_EXCL». `role` — `"user"` для HTTP-пути (как сейчас), `"afm"` для
авто-ответа.

### 3. `pkg/orchestrator/dialog_poller.go` — ветка авто-ответа

В `pollQuestions`, для каждой найденной непройденной `question.json`: если
`!stage.Interactive` — вместо текущего `EvAskUser`/`EventAskUser`:

1. `answer, fromOptions := mcp.PickAutoAnswer(q)`
2. `mcp.WriteAnswer(stageDir, phase, id, answer, fromOptions, "afm")`
3. Публикуется новое событие `bus.EventAutoAnswered` в event feed вместо
   `EventAskUser` (текст вида `auto-answered question q1: "<answer>"`).
4. FSM стадии **не трогается** — никакого перехода в
   `awaiting_user_input`, статус остаётся тем, каким был (running/planning).

Если `stage.Interactive` — всё как сейчас, без изменений.

### 4. Видимость в дашборде

`dialog.jsonl` получает третье значение поля `role`: `"afm"` (сейчас только
`assistant`/`user`) — этого достаточно, чтобы дашборд (`DialogChannel.tsx`)
отрисовал запись отдельно (например, ⚙️ вместо 🤖/🧑, с подписью
«auto-answered»), без нового булева флага в схеме. Небольшая фронтенд-правка
рендера роли `afm` в компоненте диалога — единственное изменение на этой
стороне.

## Recovery / перезапуск — уже работает без доработок

Проверено по коду (не гипотеза):

- `pkg/orchestrator/recovery.go` переспавнивает агента для ЛЮБОЙ стадии,
  найденной `Running`/`Planning`/`Revising`/`Retrying`/`HookFailed` при
  возобновлении run'а — независимо от `Interactive`. Interactive-специфична
  только очистка сессии (`clearInteractiveSessions`), не сам факт рестарта.
- После `Store.Open()` статус стадии в снапшоте восстанавливается сразу
  (без промежуточного окна) — следующий тик `pollQuestions` (≤1с после
  старта) увидит зависший `question.json`.
- `question.json`/`answer.json` никогда не удаляются ни на retry, ни на
  recovery (только `<phase>.session.json`/`<phase>.jsonl`) — если поллер
  успел авто-ответить до краша, ответ переживёт рестарт как обычный файл на
  диске; если не успел — новый поллер после рестарта увидит тот же файл и
  ответит.
- Ctrl+C и жёсткий креш проходят через разные промежуточные статусы (Ctrl+C
  почти всегда логирует стадию как `Failed`/context canceled и резюмится
  через `autoRecoverFailedStages`; жёсткий креш оставляет стадию `Running`
  без терминального события и резюмится напрямую), но оба пути в итоге
  переспавнивают агента с нуля — это универсальное поведение уже сегодня,
  не специфичное для этой фичи.

Итог: никакого дополнительного кода под recovery не требуется.

## Не покрытый крайний случай (осознанно)

Если агент завершает процесс быстрее, чем поллер успевает ответить
(интервал поллинга — 1 секунда), стадия по-прежнему упадёт как сегодня
(«missing artifact or incomplete»). Это принято как приемлемое ограничение:
любой разумный опрашивающий цикл агента ждёт значительно дольше секунды
(интерактивный протокол сегодня рассчитан на то, что человек может отвечать
минутами). Закрытие этого края потребовало бы дать non-interactive стадиям
сессии/`--resume`-инфраструктуру, которой у них сегодня нет — сознательно
не делаем это сейчас.

## Тестирование

**Go (`pkg/mcp`):** таблица случаев для `PickAutoAnswer` — пустые options
(fallback-текст), один вариант с `(recommended)`, с `(default)`, с
`(рекомендую)`, несколько вариантов без маркеров (берёт первый), маркер не
в первом варианте по списку. Тест на `WriteAnswer` — атомарность (повторный
вызов с тем же id не перезатирает существующий answer.json), корректная
запись в `dialog.jsonl` с `role: "afm"`.

**Go (`pkg/orchestrator`):** интеграционный тест на `pollQuestions` —
non-interactive стадия с `question.json` без ответа → поллер пишет
`answer.json` сам, стадия НЕ переходит в `awaiting_user_input`, событие
`EventAutoAnswered` публикуется. Отдельный тест — `agents: [auto]` стадия
без `interactive: true` получает то же поведение. Тест на
`runner_factory.go` — `AFM_STAGE_DIR` пробрасывается для non-interactive
planning/implementation/review стадии (раньше не пробрасывался).

**Frontend:** рендер записи с `role: "afm"` в `DialogChannel.tsx` —
отдельная визуальная пометка, не путается с `assistant`/`user`.

**Ручная проверка в браузере:** сценарий с mock-agent-скриптом, который в
non-interactive стадии пишет `question.json` с вариантами (один помечен
`(recommended)`) и ждёт `answer.json` в цикле (как интерактивный
протокол) — убедиться, что стадия не мелькает в `awaiting_user_input`, в
`dialog.jsonl`/event feed видна пометка авто-ответа, и агент продолжает
работу как обычно.
