# Дизайн (отложено): изоляция рабочей директории между параллельными стадиями

**Дата:** 2026-07-28
**Статус:** обсуждено, подход НЕ выбран — решение отложено, вернуться позже

## Контекст

Обнаружено при систематическом аудите параллельного выполнения стадий (`/superpowers:systematic-debugging`), запрошенном после отчёта «запустил и там куча багов» на реальном флоу (`GogaReview`, лог `~/Documents/afm-logs/afm-log-8/.../GogaReview-20260728-133804-69ce`).

**Подтверждённый разбором лога факт:** стадии без взаимного `depends_on` реально выполняются параллельно — в разобранном флоу `code-review`/`contracts-review`/`documentation-review` (все `depends_on: [discovery-scope]`, друг к другу зависимостей нет) стартовали и работали одновременно (события `start_planning`/`start_run` в пределах миллисекунд-секунд друг от друга в `events.jsonl`).

**Структурный факт из кода:** `Flow.RootDir` (одно значение, `flow.yaml`) передаётся как `Dir` исполнителя КАЖДОЙ стадии без исключения (`pkg/orchestrator/runner_factory.go:47,88`). Изоляции рабочей директории между параллельными стадиями нет вообще — ни worktree, ни блокировок; `grep -rn "worktree\|isolat" pkg/flow/*.go README.md` не даёт совпадений.

Практический риск для стадий `agents: [planning, implementation]`, работающих параллельно в общем `root_dir`:
- конкурентные правки одних и тех же файлов (гонка последней записи);
- конкурентные git-операции (`.git/index.lock`);
- `verify:`-команды (`pkg/orchestrator/completion.go:98-100`, `runVerify`) гоняются в том же `projectDir` — результат стадии может зависеть от незакоммиченных правок параллельной соседней стадии.

**Важная деталь конкретного флоу-репро:** ни одна из трёх параллельных review-стадий не декларирует `artifacts`/`inputs` — какие файлы будут затронуты, решает сам агент по свободному промпту в рантайме. Значит **статическое обнаружение пересечений по конфигу невозможно** — afm заранее не знает, что стадия тронет.

**В этом конкретном логе конфликта файлов не случилось** (стадии по факту трогали разные области: `docs/*.md`, `goga/config/project/CODEMANIFEST`, `goga/assets/pipelines/review.yml`) — реальный найденный и уже исправленный баг в этом же логе был другим (см. Out of scope ниже). То есть риск подтверждён структурно, но не подтверждён как причина конкретного инцидента.

## Осложняющий фактор: флоу рассчитан на накопление незакоммиченных правок

В разобранном флоу три review-стадии **намеренно не коммитят** — они оставляют правки в рабочем дереве; финальный коммит делает отдельная стадия `commit-changes` в конце цепочки (`depends_on: [testing]`), которая одним разом коммитит всё накопленное. Любое решение с git worktree на стадию обязано учитывать этот паттерн — наивный «взять merge с полноценным коммитом» меняет семантику «накопленных незакоммиченных изменений», на которую флоу сейчас рассчитывает.

## Рассмотренные подходы

### A. Git worktree на стадию + merge при завершении

Каждая параллельная implementation-стадия работает в своём `git worktree`/ветке; при завершении — merge обратно в `root_dir`. Конфликт мерджа → стадия падает с понятным сообщением (не тихая порча состояния), worktree и ветка остаются на диске для ручного разбора.

**Проблемы:**
- Ломает паттерн «накопить незакоммиченное → одна финальная стадия коммитит всё» (см. выше) — потребовался бы синтетический коммит внутри каждого worktree только чтобы включить merge-механику.
- Требует, чтобы `root_dir` реально был git-репозиторием — нужен fallback на негит-каталоги (тихо отключать изоляцию + предупреждать).
- Docker-режим сейчас монтирует единственный `$(pwd)` — новый worktree (обычно каталог-сосед) нужно тоже примонтировать или разместить внутри уже смонтированного дерева.
- Самый корректный по существу вариант, но самый дорогой и с реальным риском регресса для существующих флоу.

### B. Детект + предупреждение (без изоляции поведения)

Ничего не меняется в исполнении. После завершения стадии сравнить её `git diff --stat` с тем, что трогали ДРУГИЕ параллельно активные (non-terminal, без взаимного `depends_on`) стадии — при пересечении путей опубликовать warning-событие (dashboard + лог), не хардфейл (по времени не всегда можно быть уверенным, чьё изменение «легло» раньше — риск ложных срабатываний). Плюс явное дополнение README: «стадии могут работать параллельно» ⇒ общий `root_dir`, рекомендация `depends_on`/`max_parallel: 1` для конфликтующих по содержимому стадий.

**Оценка:** дёшево, не меняет поведение существующих флоу, ничего не ломает. Не предотвращает конфликт — только подсвечивает постфактум.

### C. Явный опт-ин lock (`exclusive`/`lock_group`) в flow.yaml

Новое опциональное поле стадии — стадии с одинаковой меткой форсированно выполняются по одной, независимо от `depends_on`, тем же семафорным механизмом, что уже есть для `max_parallel` per-command (`pkg/orchestrator/concurrency.go`), только ключ — явная метка вместо команды агента.

**Оценка:** минимум нового кода (переиспользует существующий `semChan`/`semNop`), нулевой риск для существующих флоу (без указания поля поведение не меняется), но требует, чтобы автор флоу сам явно пометил конфликтующие стадии — не защищает «наивные» флоу автоматически (ровно как колега из разобранного лога).

## Рекомендация (не утверждена пользователем)

Комбинация **B + C**: дёшево, не меняет поведение по умолчанию, даёт реальный рычаг тем, кто осознаёт риск, и предупреждает тех, кто не подумал. Полная изоляция (A) выглядит избыточной ценой относительно подтверждённого риска — конкретный инцидент в разобранном логе был вызван другим, уже исправленным багом (см. Out of scope), а не гонкой за файлы.

## Out of scope (уже исправлено в этой же сессии, отдельными коммитами)

- `retryStage` не проверял `depsDone` для автономных стадий при ручном retry — коммит `4663f88`. Это и был подтверждённый причинный баг в разобранном логе (`commit-changes` реально выполнил `git commit` до завершения `testing`/трёх review-стадий).
- `max_parallel` реально учитывался только у первой по порядку в YAML стадии, делящей команду с другими — коммит `d945595`.
