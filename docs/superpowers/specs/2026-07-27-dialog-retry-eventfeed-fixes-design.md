# Дизайн: три фикса надёжности (dialog misplacement, cascade retry, event feed persistence)

## Контекст

Расследование трёх багов, о которых сообщил пользователь, велось через systematic-debugging
по реальному прод-логу (`.afm/runs/GogaFeature-20260726-133106-3c1c/events.jsonl`, гоняется
поверх afm внешним wrapper'ом "goga"). Все три подтверждены чтением кода и события в логе,
не догадками.

## 1. Агент прячет question.json от поллера

### Проблема

`relocateMisplacedQuestions` (`pkg/orchestrator/dialog_poller.go`) — единственная защита от
того, что агент кладёт `*.question.json` не в канонический `stageDir`. Она находит такие файлы,
парся stream-json лог агента (`<phase>.jsonl`) в поисках вызова инструмента **`Write`**
(`executor.WrittenFiles`, `executor.go:312`). Если агент создаёт файл вопроса через **Bash**
(`cat > ... <<EOF`, `echo ... >`) — что вполне ожидаемо, так как весь протокол описан агенту
как bash-poll-loop — вызов в логе есть, но это `tool_use` с `Name == "Bash"`, и код его
игнорирует. Файл остаётся невидим: поллер никогда не находит вопрос в `stageDir`, UI никогда
не показывает диалог пользователю. Ровно это и произошло — коллеге пришлось руками угадывать
путь и создавать `answer.json` в обход UI.

### Решение

Заменить парсинг Write-вызовов на скан файловой системы — не зависит от того, каким
инструментом агент создал файл.

**Зона сканирования:** `stageDir` (как и раньше — ловит случай "внутри директории, но
неправильный префикс") **+ верхний уровень `root_dir`** (`o.opts.RootDir`), **без рекурсии**.
Обоснование: судя по описанному в CLAUDE.md паттерну бага (агент строит путь из CWD вместо
`$AFM_STAGE_DIR`), файл почти наверняка оказывается прямо в корне `root_dir` — это O(1) от
размера репозитория и не требует эвристик по глубине/игнор-листам. Если на практике всплывёт
случай глубже — расширим отдельным фиксом с фактами на руках, а не заранее.

**Активная фаза** (заменяет "фаза = чей `<phase>.jsonl` содержал Write"): берём фазу из
`dialogPhases(stageDir)`, чей `<phase>.jsonl` изменялся последним — это и есть фаза, в которой
сейчас реально работает агент (одновременно активна только одна).

**Разбор имени файла:** как и раньше, `<phase-or-stageid>.<id>.question.json` →
нормализуется в `<активная-фаза>.<id>.question.json`. Дополнительно: если в имени вообще нет
точки-разделителя (агент написал голый `q1.question.json` без префикса) — считаем всё имя
целиком `id` и подставляем активную фазу. Это не отдельный код: та же активная фаза, что и для
случая с неправильным префиксом.

**Безопасность при нескольких параллельных interactive-стадиях:** если top-level `root_dir`
скан находит файл-кандидат, а сейчас параллельно активны ≥2 interactive-стадии без открытого
вопроса (редкий, но возможный случай — стадии без `depends_on` друг на друга) — **не
релоцируем** этот файл ни для одной из них, только логируем предупреждение. Угадывать, какой
стадии он принадлежит, когда однозначного маркера (кроме id) нет — хуже, чем оставить стадию
висеть ещё на один тик поллера (1с) до следующей проверки.

**Как раньше, без изменений:** нормализация содержимого в канонический путь + dangling-симлинк
на "неправильном" пути (там, где реально поллит bash-цикл агента) → канонический `answer.json`,
чтобы агент нашёл ответ независимо от того, как он ошибся с путём/именем.

**Throttling:** сам walk (не полный `pollQuestions`, а именно filesystem-часть) выполняется не
чаще раз в 5 секунд на стадию — это запасная сеть, а не основной путь, лишняя частота не нужна.

## 2. Каскадный retry не работает для стадий дальше по цепочке

### Проблема

Подтверждено дословно в логе: `architecture-review` падает → `failBlockedStages`
(`scheduling.go:266`) транзитивно каскадит `failed` на все зависимые стадии разом через
`blocked_by_dep`, **до того как у них когда-либо появлялся `stageDir` на диске** (директория
создаётся только при реальной активации стадии). После успешного retry `architecture-review`,
retry следующей стадии (`apply-architecture`) падает мгновенно и стабильно с:
```
open log file: open .../apply-architecture/autonomous.log: no such file or directory
```
шесть раз подряд в логе. `runPlanningAgent` (`agents.go:24`) и `runReviewAgent`
(`agents.go:266`) защищаются от этого сами — оба делают `os.MkdirAll(stageDir)` в начале
функции. `runAutonomousAgent` (`agents.go:307`) — единственная из четырёх функций-раннеров,
которая этого не делает.

### Решение

Добавить в начало `runAutonomousAgent` тот же защитный паттерн, что уже есть в
`runPlanningAgent`/`runReviewAgent`:
```go
stageDir := filepath.Join(o.opts.RunDir, s.ID)
if err := os.MkdirAll(stageDir, 0755); err != nil {
    o.Trigger(s.ID, EvFail, GuardCtx{}, "mkdir failed")
    return
}
_ = os.WriteFile(filepath.Join(stageDir, "autonomous.flag"), nil, 0644)
```
Почему тут, а не патч в `retryStage`: это единая точка для всех вызывающих путей
(`retryStage`, resume-после-рестарта в `recovery.go`, любой будущий caller), а не только для
retry. Заодно чинит скрытую зависимость фикса №1 от фикса №2: без `autonomous.flag`
`dialogPhases()` не включает `autonomous_execution` в список фаз, и активная фаза для
relocation (см. пункт 1) не определилась бы для автономных стадий.

## 3. Event feed не переживает ни рефреш, ни рестарт afm

### Проблема

`UIBus` (`pkg/orchestrator/bus.go`) — чистый in-memory fan-out без истории: `Publish`
доставляет только тем, кто подписан **прямо сейчас**. Фронтенд (`useEventFeed`,
`use-event-feed.ts:17`) стартует с пустого массива при каждом монтировании. REST-эндпоинта,
отдающего историю событий, не существует вообще.

Проверка показала: почти все типы событий из живой ленты уже 1:1 лежат на диске:
- `stage_status_changed`/`ask_user`/`user_answered`/`manual_retry`/`approved`/`revised`/
  `retry_scheduled`/`retry_exhausted` публикуются в UI **из того же вызова `Trigger`**, что
  синхронно пишет FSM-переход в `events.jsonl` (`orchestrator.go:228`) — те же имена событий,
  `reason` уже содержит нужный текст (напр. `revised` — это и есть feedback из `reason`).
- `agent_action` — уже на диске в `<phase>.jsonl` (stream-json), тем же парсером что и
  `WrittenFiles`/`LogAction` в `executor.go`.
- `supervisor_decision` — уже пишется отдельно в `supervisor.jsonl`
  (`supervisor_track.go:112`).

Два типа не имеют следа на диске сейчас: `agent_completed` (публикуется напрямую в critical
bus, `retry.go:111,116`, без `Trigger`) и `context_warning` (`agents.go`, несколько мест,
тоже голый inline-publish). Трогать схему `events.jsonl` ради них — плохой размен: это
единственный источник правды с CAS-инвариантом (`Store.Apply`, `store.go:251` — строгая
проверка `current != t.From`), и "фейковая" transition с `From==To` этот инвариант нарушает.
Вместо этого — маленький сайдкар-файл `notices.jsonl` на стадию, по аналогии с уже
существующим `supervisor.jsonl`: пишется рядом с существующими `o.ui.Publish(...)` вызовами,
`events.jsonl` не трогаем вообще.

### Решение

**Backend:** новый `GET /api/events` (run-level, без `{id}` стадии — по аналогии с уже
run-level `/api/status`, так как лента агрегирует события всех стадий рана) реплеит:
1. `events.jsonl` → маппинг FSM-событий в UI `EventType` (имена практически совпадают,
   `reason`/`to` → payload).
2. `<phase>.jsonl` каждой стадии → `agent_action`, тем же парсером, что и `WrittenFiles`.
3. `supervisor.jsonl` каждой стадии → `supervisor_decision`.
4. Новый `notices.jsonl` каждой стадии → `agent_completed`/`context_warning`.

Все четыре источника сливаются по времени, результат **обрезается до последних 200** записей
(совпадает с текущим `MAX_EVENTS` во фронте — история всё равно обрежется на клиенте до этого
числа, отдавать больше бессмысленно).

Каждая точка публикации `EventAgentCompleted`/`EventContextWarning` в `retry.go`/`agents.go`
дополнительно дописывает строку в `notices.jsonl` соответствующей стадии.

**Frontend:** `useEventFeed` меняет порядок подключения — **сначала открывает WebSocket**
(буферизует всё входящее в локальный массив, ещё не показывая), **затем** фетчит
`/api/events`, **затем** сливает историю с буфером и дедуплицирует по стабильному ключу (`seq`
для FSM-производных событий; для `agent_action`/`notices` — по кортежу
`stageId+phase+tool+timestamp`). Так гарантированно нет ни дыры, ни дубля на стыке
истории и live-потока.

Отдельная правка, обнаруженная по ходу: `toEvent()` в `use-event-feed.ts` сейчас **всегда**
проставляет `timestamp: new Date().toISOString()` для входящего сообщения, игнорируя
серверное время. Для реплея истории это не подходит — записи из `events.jsonl` несут
реальное время, которое обязано попасть в фид как есть (иначе relative-time будет врать,
показывая "сейчас" для событий недельной давности). Правим `toEvent`, чтобы использовать
`timestamp` из payload, если он есть, и падать на `Date.now()` только если сервер его не
передал.

## Тестирование

- **№1:** unit-тест на `relocateMisplacedQuestions` с файлом вне `stageDir` в top-level
  `root_dir`, включая bare-имя без префикса; отдельный тест на safety-guard при ≥2 активных
  interactive-стадиях без однозначного адресата.
- **№2:** unit/integration-тест: стадия каскадно попадает в `failed` через `blocked_by_dep` без
  созданного `stageDir`, ручной retry должен успешно создать директорию и запустить агента
  (аналог существующего `TestIntegration_IncompleteRetry`).
- **№3:** unit-тест на backend reconstruction-эндпоинт (сборка из всех 4 источников, сортировка,
  обрезка до 200); frontend-тест на `use-event-feed` — merge истории с буфером WS без дублей/дыр,
  и на исправленный `toEvent` (сохраняет переданный timestamp).
