# Аудит: что делают агенты, но мог бы делать бинарник (детерминизм флоу)

**Дата:** 2026-07-24
**Тип:** аналитический аудит (reference), НЕ spec-к-реализации
**Цель:** найти места, где предсказуемость флоу упирается в решения/самоотчёт LLM,
и которые можно передать детерминированному коду afm («сделать жёстче»).

Метод: трассировка всех LLM-вызовов (`RunPlanning`/`RunAgent`/`RunJSONQuery`),
сборки промптов (`pkg/prompts/builder.go`) и контракта завершения
(`pkg/orchestrator/completion.go`).

## Все точки, где флоу полагается на LLM (call sites)

| Фаза | Вызов | Продукт LLM | Сигнал завершения |
|------|-------|-------------|-------------------|
| Planning | `agents.go` `RunPlanning` (план / reprompt недостающих секций / revise) | `plan.md` | наличие+валидность `plan.md` |
| Implementation | `agents.go:238` `RunAgent(ImplAgent)` | правки в проекте | агент пишет `.done` |
| Review | `agents.go:255,295` `RunAgent(review)` | текст ревью | — (не гейтит) |
| Autonomous | `agents.go:334` `RunAgent(autonomous)` | правки + `execution_summary.md` | наличие `execution_summary.md` |
| Supervisor | `supervisor.go:135` `RunJSONQuery` | JSON `can_execute_autonomously` | — (advisory + выбор трека) |

## Детерминированный «пол» (уже жёстко, бинарником)

- Сборка промптов (`prompts.Build`) — полностью детерминирована.
- FSM/оркестрация, event-log как источник правды, retry/recovery, flock, чистый shutdown.
- Валидация секций плана (`prompts.ValidatePlan` + `requiredPlanSections`) с reprompt.
- Проверка наличия объявленных артефактов (`completion.go`).
- Инъекция планов зависимостей (`CollectDependencyPlans`).
- Диалог-протокол (file-based), нормализация неверно расположенных вопросов, сессии.
- `agents: [auto]` — жёсткий автономный трек без LLM-супервизора (`Stage.IsAuto`).
- `Verify` (`Stage.Verify` → `completion.go:83` `runVerify`) — шелл-гейт после стадии:
  non-zero exit → `IncompleteWorkError` → retry. **НО опционален и не используется в
  дефолтных флоу.**

## Центральная находка

**Контракт «готово» построен на доверии к агенту.** `checkCompletion`
(`completion.go:64`) считает стадию завершённой, когда:
1. агент сам создал непустой `.done` (implementation) / `execution_summary.md`
   (autonomous) — **самоотчёт агента**;
2. объявленные артефакты присутствуют — проверка *наличия*, не *корректности*;
3. `Verify` (если задан) вышел с кодом 0 — **единственная бинарная проверка
   истинности, и она опциональна**.

Итог: по умолчанию «сделано» == «агент так сказал». Это корень непредсказуемости.

## Реестр «LLM → бинарник» (по убыванию выгоды)

### #1 — Контракт завершения: не доверять самоотчёту ⭐ (макс. качество)
Сейчас: `.done`/`execution_summary.md` + наличие артефактов; `Verify` опционален,
ретраит один раз, вывод гейта не всегда возвращается агенту.
Кандидат: сделать детерминированные гейты first-class — стандартные verify-рецепты
(build/test/lint/typecheck/git-clean), «done» только при прохождении гейта, а
`.done` — необходимое-но-недостаточное; цикл agent→verify→вывод-обратно→повтор до
прохода/бюджета; возможно per-phase verify.
Ссылки: `completion.go:64-110`, `retry.go` (incomplete-work retry), `agents.go:218-221`.

### #2 — Механические шаги всё ещё агенты ⭐ (макс. предсказуемость)
Сейчас: коммит/ветка/PR, прогон тестов/сборки/миграций, форматирование, генерация
файлов — всё через `agents: [...]`. Нет примитива «стадия = детерминированное
действие».
Кандидат: новый тип стадии-действия (`run: <shell>` или `action: git-commit|test|
build|script|scaffold`), который afm выполняет сам, без LLM. Отсутствующий примитив;
прямой ответ на «что делают агенты → пусть делает бинарник».
Ссылки: `flow.Stage` (`pkg/flow/flow.go`, нет поля action/run), `runnerFor`.

### #3 — Форма флоу решается LLM (супервизор)
Сейчас: `supervisor: true` → `EvaluateStage` (LLM) выбирает autonomous/standard на
каждый прогон → набор фаз плавает от запуска к запуску.
Кандидат: декларативный/правило-based выбор трека (config/эвристики), LLM → advisory
(лог/UI, не критический путь). Частично уже начато (`agents:[auto]`, inline-artifact
guard в `supervisor_track.go:98-104`).
Ссылки: `supervisor.go`, `supervisor_track.go:82-127`.

### #4 — Review ничего не гейтит
Сейчас: ревью-агент производит текст, но не влияет на pass/fail стадии.
Кандидат: детерминированные ревью-гейты (lint / статический анализ / тесты) вместо
или вместе с LLM-ревью.
Ссылки: `agents.go:237-296`.

### #5 — Генерация шаблонных файлов (низко-средне)
Шаблонные/скаффолд-файлы агент создаёт вручную; afm мог бы генерировать
детерминированно по шаблону. Пересекается с #2 (`action: scaffold`).

### #6 — Structured output LLM (низкая выгода)
Секции плана, supervisor JSON — уже парсятся и репромптятся детерминированно
(`prompts.ValidatePlan`, `supervisor.go` `parseDecision`). Ужесточать смысла мало.

## Вывод и рекомендованный порядок

Два корневых рычага композируются:
- **#1** закрывает «проверку» (не доверять «done» от агента),
- **#2** закрывает «делание» (убрать LLM из механики).

Рекомендованный первый под-проект: **#1 (verify-гейты first-class)** — наибольшая
отдача по качеству при минимальном новом примитиве (механизм `Verify` уже есть,
нужно сделать его стандартным + усилить цикл). Затем **#2 (стадии-действия)**.
**#3/#4** — снижают структурный варианс, независимы.

Каждый пункт — отдельный под-проект (свой spec → plan → impl).
