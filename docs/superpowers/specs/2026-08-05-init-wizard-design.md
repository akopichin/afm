# afm init v2: мастер построения flow.yaml по архетипам + afm validate

**Дата:** 2026-08-05
**Статус:** design (одобрен к реализации)

## Цель

Сегодня `afm init` (`cmd/afm/init.go`) — примитивный построчный wizard: спрашивает
имя/описание флоу, затем в цикле id/name/description/depends_on/agents по каждой
стадии. Он покрывает лишь малую часть схемы `flow.yaml` (`pkg/flow/flow.go`) —
ни слова про `artifacts`/`inputs` (структурированную передачу данных между
стадиями), `verify` (авто-гейт готовности), `interactive` (диалог с
пользователем), `script`/`auto` (альтернативные типы стадий), `plan:`
(готовый план вместо планирующего агента). Новый пользователь либо не знает
об этих возможностях, либо узнаёт о них только через README.

Отдельная проблема: ошибки в `flow.yaml` (циклы в графе, битые ссылки в
`depends_on`/`inputs`, отсутствующее обязательное поле) сегодня всплывают
только при реальном `afm run` — то есть после того, как уже подняты
настоящие агенты. Нет способа проверить флоу «на сухую».

Нужен интерактивный мастер, который:
1. Даёт новичку 3-4 узнаваемых готовых паттерна вместо чистого листа и
   попутно объясняет концепции прямо в процессе интервью.
2. Не удлиняет путь опытного пользователя, который и так знает, что хочет —
   дефолты + Enter должны давать рабочий флоу почти так же быстро, как
   сегодня.
3. Проверяет собственный результат перед тем, как сказать «готово».

## Область охвата

- Полностью переписывается `cmd/afm/init.go` (`afm init`) — детерминированный
  Go CLI wizard (bufio.Scanner-промпты, без LLM/AskUserQuestion — команда
  должна работать и вне Claude Code).
- Новая команда `afm validate <flow.yaml>` — dry-run парсинг без запуска
  агентов, переиспользует существующий `flow.ParseFile()`/`validate()`.
- Claude Code skill `afm-init` (`assets/claude/skills/afm-init/SKILL.md`) в
  этой итерации **не меняется** — его синхронизация с новым порядком
  вопросов является следующей отдельной задачей.
- Настоящий циклический review-loop (`goto_targets`) не реализован в схеме
  на момент этого дизайна (см. `docs/superpowers/specs/2026-08-04-stage-goto-design.md`,
  раздел «Вне охвата») — соответствующий архетип использует существующий
  `verify:` (один авто-retry), а не полноценный цикл.
- Инференс структуры флоу из свободного текста (LLM-driven) — не в этой
  итерации, мастер полностью основан на меню и структурированных вопросах.

## 1. Архетипы

Первый вопрос мастера — выбор архетипа, который задаёт число стадий и граф
зависимостей; дальнейшие вопросы по стадиям (раздел 2) одинаковы для всех
архетипов, кроме custom, где ничего не предзаполнено.

```
What kind of flow are you building?
  1. Single change (planning → implementation → review)
  2. Build + verify loop (build → automated check, one retry on failure)
  3. Parallel tracks → integration (independent stages merge into one)
  4. Custom (build stage-by-stage from scratch)
```

### 1. Single change

Одна стадия. Самый частый сегодняшний паттерн (см. `example-flow.yaml`,
стадия `backend-auth`). Дефолт для набора фаз (раздел 2) — planning +
implementation + review.

```yaml
stages:
  - id: implementation
    name: "Implementation"
    description: "<текст пользователя>"
    agents: [planning, implementation, review]
```

### 2. Build + verify loop

Две стадии: `build` → `check` (`depends_on: [build]`). На `build` мастер
**обязательно** спрашивает shell-команду для `verify:` (например
`go test ./...`) вне зависимости от ответа на «advanced?» — это и есть
«петля»: при ненулевом exit code afm сам делает один авто-retry `build`,
прежде чем зафейлить стадию. Явная подсказка пользователю в момент выбора
архетипа: *«это один авторетрай, не бесконечный цикл — полноценные циклы
(goto) в разработке»*, чтобы не создавать ложных ожиданий.

`check` — отдельная стадия после `build`, дефолт режима — **script**
(механическая проверка, парная с `verify:` на `build` — не требует ни
planning-агента, ни `plan:`, что и делает её валидной по правилу
«стадии нужен один из: planning-агент / `plan` / `interactive` / `auto` /
`script`», см. раздел 2). Пользователь может вместо этого выбрать «Standard
agent stage» (режим 1) с planning + review, если хочет более глубокую
LLM-проверку вместо чисто механической.

```yaml
stages:
  - id: build
    name: "Build"
    description: "<текст пользователя>"
    agents: [planning, implementation]
    verify: "<shell-команда пользователя>"
  - id: check
    name: "Check"
    description: "<текст пользователя>"
    depends_on: [build]
    script: "<shell-команда пользователя>"
```

### 3. Parallel tracks → integration

N независимых стадий (без `depends_on` друг у друга — мастер спрашивает
количество, по умолчанию 2) + одна `integration`, зависящая от всех.
Паттерн из `example-flow.yaml` (`backend-auth` + `frontend-login` →
`integration-tests`).

```yaml
stages:
  - id: track-1
    agents: [planning, implementation, review]
  - id: track-2
    agents: [planning, implementation, review]
  - id: integration
    depends_on: [track-1, track-2]
    agents: [planning, implementation, review]
```

### 4. Custom

Сегодняшний stage-by-stage цикл (пустой ID — стоп), без предзаполнения
графа, но с обновлённым набором вопросов на стадию (раздел 2) вместо
сегодняшнего голого текстового `agents [planning,implementation,review]`.

## 2. Вопросы по стадии

Применяются к каждой стадии независимо от архетипа (кроме предзаполненных
полей graph-уровня — `depends_on` у архетипов 1-3 не переспрашивается).

1. **Stage ID** — текст, дефолт подсказан ролью стадии в архетипе
   (`implementation`, `build`, `check`, `track-1`, `integration`…), Enter
   принимает дефолт.
2. **Stage name** — текст, дефолт = ID с большой буквы.
3. **Description** — текст, обязателен всегда, кроме auto/interactive/script/
   plan-стадий (тогда не спрашивается вовсе — совпадает с правилом
   `validate()`: описание не нужно для этих типов).
4. **Режим стадии** — меню:
   ```
   1. Standard agent stage (planning/implementation/review — сами выбираете фазы)
   2. auto (полностью автономный агент, без планирования/супервизора)
   3. script (шелл-команда вместо агента)
   ```
   Дефолт — режим 1. Custom command (override бинарника агента) — не
   отдельный режим, а опциональная настройка внутри режима 1 в
   advanced-блоке (шаг 6).

   Если выбран **режим 1**, два дополнительных вопроса:

   a. *«У этой стадии уже есть готовый план, или планирование делает
      агент?»* — `1. Планировать агентом [default]` / `2. У меня уже есть
      файл с планом (укажу путь)`. Вариант 1 добавляет `planning` в
      `agents`; вариант 2 спрашивает путь и заполняет `plan:` (планирующий
      агент пропускается — так же, как сегодня описано в схеме).

   b. Multi-select фаз выполнения (`[x] implementation` default-checked,
      `[ ] review`) — независимо от (a). Итоговый `agents:` собирается из
      выбранного: например `[planning, implementation]`,
      `[implementation]`, `[implementation, review]`.

   Если выбран режим 2 (`auto`) или 3 (`script`) — `agents`/`plan`/фазы не
   спрашиваются вовсе (несовместимы по схеме), вместо этого для `script`
   сразу спрашивается shell-команда.

5. **`depends_on`** — для архетипов 1/2/3 предзаполнено графом архетипа, не
   спрашивается; для custom — текст (comma-separated), как сегодня.
6. **Один опциональный вопрос**: *«Нужны продвинутые настройки для этой
   стадии? (artifacts/inputs, verify, interactive, custom command) [y/N]»*.
   - `N` (дефолт, Enter) — идём к следующей стадии без дополнительных
     вопросов.
   - `y` — короткая под-анкета:
     - **Artifacts**: «Эта стадия производит файл(ы), которые нужны
       следующим стадиям? Имя/путь/описание» (можно несколько подряд,
       пустое имя — стоп).
     - **Inputs**: если стадия зависит (по `depends_on`) от стадий с уже
       объявленными artifacts — предложить найденные `stage.artifact`
       галочками, какие подключить как `inputs`.
     - **Verify**: «Shell-команда, которая должна пройти, чтобы стадия
       считалась готовой?» (пусто — пропустить). Для архетипа 2 стадия
       `build` уже спросила это на шаге архетипа — здесь не переспрашивается
       повторно.
     - **Interactive**: «Стадия должна уметь задавать вопросы пользователю
       через диалог? [y/N]».
     - **Custom command**: «Использовать нестандартный агент вместо
       `claude`? (имя бинарника, пусто — использовать дефолтный)».

Каждый пункт меню сопровождается коротким пояснением в скобках (как в
транскриптах выше) — это основной канал, через который мастер попутно
обучает концепциям во время интервью, не отправляя читать README отдельно.

## 3. `afm validate`

Новая команда, `cmd/afm/validate.go`:

```
afm validate <flow.yaml>
```

- Вызывает `flow.ParseFile(path)` — он уже гоняет `validate()` внутри (это
  тот же путь ошибок, что при `afm run`, но без запуска агентов и без
  побочных эффектов в `.afm/`).
- Успех: `OK: "<flow name>" — N stage(s), valid` (exit 0).
- Ошибка: `invalid flow.yaml: <err>` (exit 1) — сообщение как есть,
  `validate()` уже даёт человекочитаемые ошибки с контекстом стадии.
- **Существующее ограничение, не меняется в этом дизайне:** `validate()`
  останавливается на первой найденной ошибке (fail-fast), не копит все
  сразу.
- Регистрируется в `cmd/afm/main.go` рядом с остальными subcommands.

## 4. Интеграция мастера с validate

После генерации YAML (`.afm/flows/<name>.yaml`, как сегодня) мастер сразу
вызывает `flow.ParseFile` **в процессе** (прямой Go-вызов, не subprocess —
тот же бинарник):

```
✓ Created: .afm/flows/my-feature.yaml
✓ Validated: 3 stage(s), valid

Run now? [y/N]
```

При ошибке:

```
✗ .afm/flows/my-feature.yaml — invalid flow:
  stage "integration": depends_on references "fronted-login" which does not exist

What next?
  1. Edit the file manually, then re-validate  [default]
  2. Restart the wizard from scratch
  3. Exit (file stays on disk, but invalid)
```

Вариант 1 после Enter повторно вызывает `flow.ParseFile` на том же пути.
Прыжок «к конкретному полю конкретной стадии» внутри мастера сознательно не
делаем — переусложнение для v1: у архетипов 1-3 `depends_on` предзаполнен
автоматически и не может быть ошибочным, ошибки такого рода реалистичны
в основном в custom-архетипе или после ручного редактирования файла.

## 5. Реализация: затронутые файлы

- `cmd/afm/init.go` — полная замена `newInitCmd()` и вспомогательных типов
  (`stageInput` расширяется полями `Agents []string`, `Plan string`,
  `Verify string`, `Interactive bool`, `Artifacts []Artifact`, `Inputs
  []string`, `Command string`; добавляются функции выбора архетипа,
  генерации графа по архетипу, рендеринга YAML с новыми полями).
- `cmd/afm/init_test.go` — тесты на каждый архетип + ветвления вопросов.
- `cmd/afm/validate.go` (новый) — `newValidateCmd()`.
- `cmd/afm/validate_test.go` (новый).
- `cmd/afm/main.go` — регистрация `validate` subcommand.
- `README.md` — обновление Quick Start (упоминание архетипов) и добавление
  `afm validate` в раздел команд.

## Тестирование

- Golden-тест на каждый архетип: сгенерированный YAML парсится
  `flow.ParseFile` без ошибок и содержит ожидаемые стадии/связи/поля.
- Ветвление «план агентом vs. готовый план» → корректные `agents:`/`plan:`.
- Multi-select фаз (`implementation`/`review`) → корректный набор в
  `agents:`.
- Advanced-блок: artifacts/inputs/verify/interactive/custom command →
  корректные поля.
- `afm validate`: валидный флоу → exit 0 + `OK: ...`; флоу с циклом в
  `depends_on` → exit 1 + понятная ошибка; битая ссылка в
  `inputs`/`depends_on` → exit 1.
- Пост-генерационный цикл валидации в мастере: невалидный custom-флоу
  (опечатка в `depends_on`) → ошибка показывается, предлагается меню
  «исправить вручную / начать заново / выйти».
- Ручной smoke-тест (не CI, вне охвата автоматизации): пройти мастер по
  каждому из 4 архетипов в скретч-директории, для «single change» по
  возможности прогнать реальный `afm run` (требует живого Claude Code/ключа).

## Вне охвата

- Обновление Claude Code skill `afm-init` под новый порядок вопросов —
  отдельная последующая задача.
- Настоящий циклический review-loop через `goto_targets` — архетип 2 сегодня
  даёт только одно авто-retry через `verify:`, полноценный цикл ждёт
  реализации goto.
- LLM/natural-language вывод сценария из свободного текста.
- Накопление всех ошибок валидации разом (`validate()` остаётся fail-fast).
- Переход «к конкретному полю конкретной стадии» при исправлении ошибки
  внутри мастера.

## Ожидаемый эффект на онбординг

Сегодня `afm init` покрывает примерно четверть полей схемы и не проверяет
результат до реального `afm run` — первая ошибка нового пользователя стоит
ему настоящего прогона агентов. Этот дизайн бьёт в обе точки: архетипы дают
3-4 узнаваемых готовых паттерна вместо чистого листа, advanced-блок вводит
artifacts/verify/interactive явно, но необязательно, а `afm validate` ловит
структурные ошибки бесплатно, до траты денег/времени на агентов. Пояснения
в скобках у каждого пункта меню попутно обучают концепциям прямо в процессе
интервью. Для опытных пользователей путь «Enter, Enter, Enter» на архетипе 1
остаётся не длиннее сегодняшнего wizard'а. Не закрывает: глубокое понимание,
*когда* выбирать verify vs script vs interactive — это по-прежнему требует
чтения README.
