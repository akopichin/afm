# Дизайн: надёжность ядра и персистентность состояния

**Дата:** 2026-07-17
**Ветка:** theme-fix
**Статус:** согласовано, готово к написанию плана реализации

## Проблема

Ядро afm архитектурно крепкое: событийный лог (`events.jsonl`, append + fsync),
снапшот (`state.json`, temp+rename), FSM, разделение critical/UI шин, широкое
покрытие тестами. Но у гарантий, на которые опирается вся система восстановления,
есть тихие бреши. Они кластеризуются вокруг одного инварианта, который сейчас
не выдерживается end-to-end:

> Событийный лог — единственный доверенный источник правды; записи долговечны;
> повреждение никогда не разрушает данные молча; процесс стартует, останавливается
> и восстанавливается, ничего не теряя и не расходясь по состоянию.

Аудит выявил девять конкретных дефектов, ломающих этот инвариант. Ниже — дизайн
их устранения. Дефекты за пределами этого кластера (безопасность, refactoring
god-object, lifecycle процессов) вынесены в отдельные итерации и здесь не
рассматриваются.

## Принятые решения

1. **Фокус:** только кластер «надёжность ядра + персистентность».
2. **Cross-process модель:** `flock` — живой `afm run` держит эксклюзивную
   блокировку; CLI-мутации (`approve`/`retry`/`revise`) падают с понятным
   сообщением, если run активен. (Отвергнуты: intent-файлы через оркестратор —
   больше работы; flock-только-headless — промежуточный вариант.)
3. **Поведение при повреждении в середине лога (A2):** quarantine + abort —
   копируем битый лог в сторону и падаем с явной ошибкой, ничего не теряя.
   (Отвергнут best-effort: молчаливый откат к устаревшему состоянию небезопасен.)

## Архитектура: три рабочих потока

### Секция A — единый источник правды и долговечность (`pkg/state`)

#### A1. Cross-process flock (закрывает state#1)

**Проблема.** `Store` защищает только внутрипроцессные горутины через
`sync.Mutex`. Файловой блокировки на `events.jsonl` нет. Когда стадия ждёт в
`awaiting_approval`, пользователь запускает `afm approve` **отдельным процессом**,
который делает `ReadFile → Truncate(lastGoodOffset)` на том же живом файле, пока
`afm run` держит свой `Store`. Результат: события, дописанные оркестратором между
`ReadFile` и `Truncate` approve-процесса, безвозвратно обрезаются; два `Store`
ведут независимые счётчики `lastSeq` → дублирующиеся `Seq`; их писатели
`state.json` гонятся.

**Решение.**
- `state.Open` берёт эксклюзивный `TryLock` на `<runDir>/.lock`, удерживаемый
  на всё время жизни `Store`, снимается в `Close`.
- Живой `afm run` держит блокировку. CLI `approve`/`retry`/`revise` при занятой
  блокировке завершается с понятным сообщением:
  `run "<flow>" is active — approve via the dashboard at <url>, or stop the run first`.
- Переиспользовать существующий `flock` из `pkg/progress`
  (`flock_unix.go` + `flock_windows.go`, API `Lock`/`TryLock`/`Unlock`). Вынести
  в отдельный маленький пакет `pkg/lockfile` (или импортировать `pkg/progress`
  напрямую, если не создаёт цикл импортов — уточнить на этапе плана).

**Затрагивает:** `pkg/state/store.go` (`Open`, `Close`), `cmd/afm/approve.go`,
`cmd/afm/retry.go`, `cmd/afm/revise.go`.

#### A2. Недеструктивный replay (закрывает state#2)

**Проблема.** `replayEvents` делает `break` на первой строке, которая не
распарсилась, и возвращает `goodOffset` конца последней валидной строки. Затем
`Open` **обрезает файл** до этого offset — одна битая строка в середине молча
удаляет все последующие валидные события И стирает улики с диска. Если битая
строка первая — run молча сбрасывается в all-`pending`.

**Решение (quarantine + abort).** Разделить исходы replay:
- **(a) чисто до EOF** — норма.
- **(b) оборвана ТОЛЬКО последняя строка** (crash в момент append) — безопасно:
  усечь до `lastGoodOffset`, как сейчас. Это единственный случай, где усечение
  допустимо.
- **(c) непарсящаяся строка с валидными строками ПОСЛЕ неё** (реальное
  повреждение середины) — **не усекать**. Скопировать `events.jsonl` в
  `events.jsonl.corrupt-<ts>` и вернуть явную ошибку из `Open`; процесс
  завершается. Резюме возможно вручную после разбора.

Ключевое отличие от текущего кода: `replayEvents` должен различать «оборванный
хвост» и «повреждение до конца валидных данных», а не сваливать оба в одно
усечение.

**Затрагивает:** `pkg/state/store.go` (`replayEvents`, `Open`).

#### A3. Долговечный снапшот как производный кэш (закрывает state#3, state#11)

**Проблема.** `writeSnapshot` делает `Create(tmp) → Write → Close → Rename`, но
никогда не `fsync`-ит ни tmp-файл, ни родительскую директорию после `Rename` —
на потере питания rename может быть недолговечен, а `state.json` может выжить
пустым/частичным. Отдельно: `Apply` логирует ошибку снапшота в stderr и
**продолжает**, поэтому `events.jsonl` уходит вперёд, пока `state.json` молча
гниёт. При этом `afm check` и `findLatestRunDir` читают `state.json`
**напрямую**, а не лог — устаревший снапшот заставляет их врать при исправном
логе.

**Решение.**
- `writeSnapshot`: `f.Sync()` перед `Close`, fsync родительской директории после
  `Rename`.
- Снапшот записывает `last_seq`.
- Ошибка записи снапшота остаётся нефатальной (это кэш), но логируется на уровне
  WARN.
- Пути чтения перестают слепо доверять снапшоту: если `snapshot.last_seq` ≠
  хвостовому seq лога, состояние перестраивается из лога.

**Затрагивает:** `pkg/state/store.go` (`writeSnapshot`, `Apply`, `Snapshot`,
типы состояния), пути чтения (`cmd/afm/check.go`, поиск последнего run — см. A4).

#### A4. Единый «поиск последнего run» (закрывает state#6, state#7)

**Проблема.** Три расходящихся реализации: `state.FindLatestRunDir` (prefix-match,
берёт последний в порядке `ReadDir`), `cmd/afm/approve.go:findLatestRunDir`
(reverse-sort + чтение `state.json`), `cmd/afm/check.go` (`dirs[len-1]`, вообще
без фильтра по flow). Они могут давать разные ответы. Плюс prefix-match
`flowName + "-"` ошибочно матчит `foo` на run-директории flow `foo-bar`.

**Решение.**
- Свести к одной функции в `pkg/state`, которая опирается на событийный лог /
  долговечный run-id, а не на `state.json`.
- Заякорить match по имени flow (`flowName + "-" + <паттерн timestamp>`), чтобы
  `foo` не матчил `foo-bar`.
- Использовать её из `run`, `approve`, `check`.

**Затрагивает:** `pkg/state/state.go`, `cmd/afm/approve.go`, `cmd/afm/check.go`,
`cmd/afm/run.go`.

#### A5. Коллизия run-id (закрывает state#8)

**Проблема.** `ts := time.Now().Format("20060102-150405")` — секундная
гранулярность. Два запуска одного flow в одну секунду дают одну и ту же
`runDir`, `MkdirAll` — no-op, оба процесса делят одну директорию и лог.

**Решение.** Добавить короткий случайный суффикс к timestamp run-id
(например `20060102-150405-a3f9`), чтобы два запуска в одну секунду не могли
разделить директорию и лог.

**Затрагивает:** `cmd/afm/run.go` (`resolveRun`).

> **Отложено (по желанию, аддитивно, ниже по важности):** поле версии схемы в
> persisted JSON (state#5) и сохранение реальных timestamp'ов транзакций при
> replay вместо времени резюма (state#12).

### Секция B — проброс фатальных ошибок (`pkg/orchestrator`)

#### B1. Перестать глотать storage-ошибки (закрывает C3, state#14)

**Проблема.** `fsm.Apply` возвращает `*StorageError` (`ClassStorageFatal`), когда
fsync/запись `events.jsonl` падает. `Trigger` логирует это как `CRITICAL` и
возвращает `false`, после чего оркестратор продолжает принимать решения против
теперь-неполного авторитетного лога. Вся история восстановления (`recovery.go`)
зависит от доверия к `events.jsonl`/`state.json`. Отдельно: доброкачественный
CAS-mismatch (`concurrent change`) тоже логируется как `CRITICAL`, создавая шум
из ложных критов.

**Решение.** Инфраструктура классификации уже есть (`errors.go`: `StorageError`,
`ClassStorageFatal`). Развести два случая в `Trigger`:
- **CAS-mismatch** («concurrent change: stage … expected …») → тихий no-op
  (ожидаемо при конкуренции; debug-лог, не CRITICAL).
- **`ClassStorageFatal`** → пробросить наверх в `Run`, который возвращает ошибку
  и **завершает run**. Продолжать принимать решения против сломанного
  авторитетного лога — ровно то, чего делать нельзя.

**Затрагивает:** `pkg/orchestrator/orchestrator.go` (`Trigger`, `Run`,
`handleEvent`), `pkg/orchestrator/fsm.go`, `pkg/orchestrator/errors.go`
(классификация уже есть).

### Секция C — чистый shutdown и отсутствие deadlock (`pkg/orchestrator`)

#### C1. Нет утечки горутин на shutdown (закрывает C1)

**Проблема.** Завершения агентов публикуют в `context.Background()` на
critical-шину (`retry.go:108`, `:113`, `:171`). `CriticalBus.Publish` блокируется
на `b.ch <- ev` и разблокируется только когда event loop дренирует канал. Когда
`Run` возвращается (`ctx.Done()` или ошибка `handleEvent`), канал больше никто не
дренирует — незавершённые агенты заполняют 16-слотовый буфер и блокируются
**навсегда**. Нет `WaitGroup`, нет дренажа, нет джойна.

**Решение.**
- Отслеживать горутины агентов в `sync.WaitGroup`.
- Вывести agent-context из run-ctx.
- На выходе `Run`: отменить его и продолжать дренировать critical-шину, пока
  агенты не завершатся (с ограниченным таймаутом).
- Заменить три `context.Background()` в `retry.go` на run/agent-ctx, чтобы
  публикация завершающегося агента никогда не блокировалась навсегда на мёртвом
  канале.

**Затрагивает:** `pkg/orchestrator/orchestrator.go` (`Run`, spawn-сайты),
`pkg/orchestrator/retry.go`.

#### C2. Нет реентерабельного deadlock (закрывает C2)

**Проблема.** Headless auto-approve на `orchestrator.go:633` делает
**блокирующий** `o.critical.Publish(ctx, EventApproved)` изнутри
`onAgentCompleted`, который выполняется в единственной горутине, дренирующей
шину. Если 16-слотовый буфер полон — `Publish` ждёт читателя, который сам
заблокирован внутри публикации → self-deadlock. Редко (буфер 16), но достижимо
под нагрузкой.

**Решение.** Обработать одобрение **inline** (долговечный переход +
`startReadyStages`), а не публиковать в шину, которую сейчас дренируем.

**Затрагивает:** `pkg/orchestrator/orchestrator.go` (`onAgentCompleted`,
`onApproved`).

#### C3. Долговечный intent пользователя (закрывает H4)

**Проблема.** `Approve`/`Revise`/`Retry` публикуют событие в **in-memory**
critical-шину; оно не персистится. Если процесс падает после одобрения
пользователем, но до `onApproved`, восстановление видит статус всё ещё
`awaiting_approval` и оставляет его нетронутым — одобрение потеряно, пользователь
одобряет заново. Задокументированная гарантия долговечности покрывает *ответы*
(O_EXCL answer.json на диске), но не approve/revise/retry.

**Решение.** Сделать intent долговечным-первым: `approve`/`revise`/`retry`
применяют FSM-переход к `Store` (долговечно, с fsync) в момент интента, **затем**
публикуют событие для side-effects. Восстановление уже резюмит
`Ready`/`Revising`/`Retrying` (см. `recovery.go`), поэтому крах после
долговечного `Apply` корректно реплеится — одобрение больше не теряется вместе с
in-memory шиной. Это делает dashboard-путь таким же долговечным, каким CLI-путь
уже является.

> **Проверить на этапе плана:** что `recovery.go` действительно резюмит каждый из
> статусов, в которые может перейти долговечный-первый intent (`Ready` для
> approve, `Revising` для revise, `Retrying`/planning для retry). Из чтения
> `recovery.go` — да (`startReadyStages` в конце `startPlanningForPending`
> подхватывает `Ready`), но подтвердить тестом.

## Данные / модель

- `<runDir>/.lock` — новый файл блокировки (A1).
- `events.jsonl.corrupt-<ts>` — карантинная копия при повреждении (A2).
- `state.json` получает поле `last_seq` (A3).
- run-id: `<flow>-<timestamp>-<rand>` вместо `<flow>-<timestamp>` (A5).

## Обработка ошибок (сводка изменений)

| Место | Было | Стало |
|-------|------|-------|
| replay середины лога | молча усечь + потерять | карантин + abort (A2) |
| write снапшота | swallow + continue | fsync + WARN; read-path перестраивает из лога (A3) |
| storage-fatal в Trigger | log CRITICAL + continue | пробросить → завершить run (B1) |
| CAS-mismatch в Trigger | log CRITICAL | тихий no-op (B1) |
| completion publish | `context.Background()` (утечка) | run/agent-ctx + WaitGroup дренаж (C1) |
| headless auto-approve | блокирующий self-publish | inline-обработка (C2) |
| approve/revise/retry | in-memory событие | долговечный `Apply` первым (C3) |

## Тестирование

- **A1:** запустить два `Store.Open` на одну `runDir` → второй получает ошибку
  блокировки; CLI-команда при живом run падает с сообщением.
- **A2:** собрать `events.jsonl` с (b) оборванным хвостом → усекается и
  открывается; с (c) битой строкой в середине + валидными после → `Open`
  возвращает ошибку, создан `.corrupt-<ts>`, оригинал не тронут.
- **A3:** упасть между записью лога и снапшотом (через существующий
  `SetApplyHook`) → снапшот отстаёт по `last_seq`, read-path перестраивает
  корректное состояние из лога.
- **A4:** несколько flow с пересекающимися префиксами (`foo`, `foo-bar`) →
  каждая команда находит правильный run.
- **A5:** два `resolveRun` в одну секунду → разные `runDir`.
- **B1:** мок `Store`, у которого `Apply` возвращает `StorageError` → `Run`
  завершается с ошибкой; CAS-mismatch → run продолжается без CRITICAL.
- **C1:** отменить ctx, пока агент in-flight → `Run` возвращается, горутина
  агента завершается (нет утечки; проверяется через `goleak` или счётчик
  WaitGroup).
- **C2:** headless-прогон с полным буфером шины → нет deadlock, стадия
  одобряется.
- **C3:** одобрить, затем «упасть» до обработки события (не публиковать) →
  повторный `Open` + recovery резюмит стадию как `Ready`.

## Границы (что НЕ входит)

- Безопасность dashboard (auth/Origin/лимиты тела), утечка секретов в env,
  path traversal через `flow.Name`/`Stage.ID` — отдельная итерация.
- Refactoring god-object (`spawnAgent`/`DialogWatcher`/`agentrunner`), мёртвый
  код `detectDialogViolation`, TOCTOU маркера, зависание interactive-retry —
  отдельная итерация.
- Process groups, SIGTERM/forward в docker, idle-timeout, гонка `Timer.Reset`,
  буфер строки 1MB→16MB — отдельная итерация.
- Ручной merge конфига (`mergeFile`), доковый дрифт — отдельная итерация.
- Аддитивные state#5 (версия схемы) и state#12 (timestamp'ы при replay) —
  отложены, при желании включаются в план.
