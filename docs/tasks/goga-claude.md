# Миграция afm на архитектуру Goga

## Current State

В проекте `afm` (модуль `github.com/akopichin/afm`, Go 1.26) архитектуры Goga не
существует: `goga schema` возвращает `[]`, `CODEMANIFEST` нет ни в одной директории. `.goga/`
до этой задачи не было вообще — сейчас там только `.goga/usages/cooks/` с 7 practice-файлами на
внешние зависимости (см. «Внешние зависимости»). Черновой каркас `cells/`, обсуждавшийся как
альтернативная раскладка на этапе formulировния, в рабочем дереве отсутствует (проверено: `find`/
`git status` не находят `cells/`) — по решению пользователя такая раскладка не используется: клеточки
строятся поверх текущего расположения кода, без переноса файлов.

Проект — зрелый, рабочий Go CLI/оркестратор (~56 000 строк, включая тесты) из **15 логических
единиц** (14 Go-пакетов + `assets`), уже связанных реальным графом внутренних импортов (проверено
`grep` по факту, не предположено):

```
Слой 0 (независимые листья):
  pkg/config  pkg/flow  pkg/state  pkg/progress  pkg/mcp  pkg/proxy  pkg/web
  assets  tools/setstatuslinter

Слой 1 (зависят только от слоя 0):
  pkg/prompts  → pkg/flow
  pkg/docker   → pkg/flow
  pkg/executor → pkg/progress

Слой 2:
  pkg/orchestrator → pkg/config, pkg/executor, pkg/flow, pkg/mcp, pkg/prompts, pkg/state

Слой 3:
  pkg/server → pkg/executor, pkg/mcp, pkg/orchestrator, pkg/state, pkg/web

Слой 4:
  cmd/afm → pkg/config, pkg/docker, pkg/flow, pkg/orchestrator, pkg/proxy, pkg/server, pkg/state, assets
```

Кратко по назначению каждой единицы:
- `cmd/afm` — CLI entrypoint (9 файлов): run, check, approve, retry, revise, list, init, install_skills, main
- `pkg/orchestrator` — ядро оркестрации: FSM переходов стадий, шина событий, граф зависимостей стадий,
  сессии, recovery/retry, adoption плана (крупнейший пакет — 11 файлов: bus, completion, context,
  errors, fsm, graph, orchestrator, plan_adopt, recovery, retry, session)
- `pkg/executor` — запуск и мониторинг агентских процессов (stdout/stderr стриминг, транскрипты)
- `pkg/server` — HTTP + websocket дашборд, отдаёт события оркестратора в UI, встраивает `pkg/web`
- `pkg/proxy` — reverse-proxy для агентского HTTP-трафика (в т.ч. ZAI-transform под `api.z.ai`)
- `pkg/config` — загрузка и мердж конфигурации (`.afm/config.yaml`, `~/.afm/config.yaml`)
- `pkg/flow` — модель flow.yaml (стадии, артефакты, входы/выходы)
- `pkg/docker` — запуск afm внутри Docker-контейнера (перезапуск, монтирование томов, TTY-детекция,
  drop привилегий через `gosu`)
- `pkg/mcp` — файловый протокол диалога агент↔пользователь (вопрос/ответ файлы, `dialog.go`)
- `pkg/progress` — файловые advisory-локи прогресса рана (кроссплатформенно: flock/LockFileEx)
- `pkg/prompts` — сборка system-промптов для агентов по данным flow
- `pkg/state` — персистентное хранилище состояния стадий рана
- `pkg/web` — встроенные веб-ассеты дашборда (`embed.go` + `index.html`/`style.css`/`app.js`/
  `markdown-it.min.js`/`favicon.svg`, `go:embed`)
- `assets` — `assets.go` (`go:embed`) отдаёт system-промпты (`prompts/`) и claude-скиллы
  (`claude/skills/afm*`, 5 директорий) как embedded FS; используется в `cmd/afm/run.go` и
  `cmd/afm/install_skills.go`
- `tools/setstatuslinter` — кастомный статический анализатор (`go/analysis`), не имеет внутренних
  зависимостей на другие пакеты проекта

Из этого кода уже нельзя разрабатывать/рефакторить через пайплайн Goga (`goga-brainstorm` /
`goga-change` / `goga-plan`), так как отсутствуют CODEMANIFEST-контракты, описывающие API каждой
единицы.

## Description

Реверс-инжиниринг существующего, уже работающего кода `afm` в клеточки Goga с CODEMANIFEST-файлами,
описывающими **текущий** контракт каждой единицы (реальные экспортируемые типы/методы/routines и их
сигнатуры), а не проектирование новой функциональности. Клеточки создаются поверх существующего
расположения кода (`pkg/<name>/`, `cmd/afm/`, `assets/`, `tools/setstatuslinter/`) — без переноса
файлов между директориями. Итог должен покрывать значимые нюансы работы проекта (см. `CLAUDE.md`:
file-based dialog protocol, built-in reverse proxy, Docker mode — эти механики должны быть узнаваемы
в аннотациях соответствующих клеточек), чтобы после миграции всё дальнейшее развитие/рефакторинг
проекта можно было вести через `goga-brainstorm`, `goga-change` и `goga-plan`.

Для `pkg/web` — включить в охват `embed.go` (Go-часть) отдельным контрактом; для веб-части
(html/css/js) — свой CODEMANIFEST, описывающий её как есть (минимальный, без выдумывания API);
дальнейшее дробление веб-части — последующая работа, не эта задача.

## Scope

**In scope:**
- Создание клеточек (`CODEMANIFEST` + `.usages/` где уместно) для всех 15 единиц, перечисленных в
  Current State — стартовая гранулярность «1 Go-пакет (или `assets`/`tools/setstatuslinter`) =
  1 клеточка» (подтверждена пользователем), с единственным обязательным исключением `pkg/web` — эта
  единица описывается двумя CODEMANIFEST (Go-часть `embed.go` + отдельный контракт для веб-ассетов,
  см. Description), то есть базовое число клеточек — 16, не 15; если на этапе `goga-brainstorm` внутри
  пакета обнаружится несколько независимых зон ответственности — например, `pkg/orchestrator` может
  логически распасться на FSM / bus / session-recovery — допускается дальнейшее дробление именно на
  этом этапе, не раньше, и без физического переноса файлов между директориями
- Контракты клеточек строятся из реальных экспортируемых сущностей текущего кода — сигнатуры
  списываются с существующих `.go`-файлов (и, для `pkg/web`, разметки/JS), а не придумываются
- Project-level usage-файлы для внешних зависимостей в `.goga/usages/cooks/` (уже созданы — см.
  «Внешние зависимости»)
- Cell-level `.usages/` файлы для клеточек, у которых есть внутренние потребители (по графу импортов
  выше) — описывающие, как реально сегодня вызывается facade клеточки
- Если черновой каркас `cells/` (альтернативная раскладка) появится в рабочем дереве — не
  использовать его и удалить
- Соблюдение порядка проектирования bottom-up по 5 слоям, описанным в Current State — каждый
  следующий слой проектируется только после того, как определены контракты слоя, от которого он
  зависит (`goga-cookbook`: нельзя корректно описать `Imports`, не зная точно, что предоставляет
  зависимость)

**Out of scope:**
- Изменение поведения существующего кода — задача только описывает архитектуру «как есть», не
  рефакторит и не исправляет код (рефакторинг — последующая работа через `goga-change` уже поверх
  готовых клеточек)
- Физический перенос `.go`-файлов между директориями (решено пользователем: `CODEMANIFEST` кладётся
  в существующие `pkg/<name>/`, `cmd/afm/` и т.д., без переезда на структуру `cells/`)
- Тестовые файлы (`*_test.go`) как отдельный предмет контракта — не становятся частью
  CODEMANIFEST-контракта клеточек
- `docs/`, `README.md`, `Makefile`, CI-конфиги (`.gitlab-ci.yml`), `.golangci.yml`,
  `.claude/worktrees/*` (временные git worktree параллельных агентов)

## Acceptance Criteria

- `goga schema` показывает минимум 16 клеточек (15 единиц из Current State + 1 дополнительная за счёт
  обязательного разделения `pkg/web` на два контракта, см. Description) — и больше, если слой 2/
  `pkg/orchestrator` дополнительно раздроблен на этапе brainstorm; клеточки сгруппированы согласно
  графу импортов из Current State
- Каждая клеточка содержит `CODEMANIFEST`, проходящий `goga lint` без ошибок структуры/казинга
  DSL-ключей
- Контракт каждой клеточки покрывает публичный API реального Go-пакета (сверяемо: экспортируемые
  типы/функции пакета соответствуют записям в CODEMANIFEST этой клеточки)
- `Imports` каждой клеточки в точности соответствуют реальному графу внутренних импортов из Current
  State — без циклов между клеточками (правило DSL: клеточка A не может импортировать из B, если B
  импортирует из A)
- Все 7 внешних зависимостей имеют project-level usage-файл в `.goga/usages/cooks/`, подключённый
  (`Usages`) и применённый хотя бы в одной аннотации той клеточки, которая эту зависимость реально
  использует
- Специфика проекта из `CLAUDE.md` (file-based dialog protocol между `pkg/mcp` и `pkg/orchestrator`,
  proxy-трансформы в `pkg/proxy`, Docker-режим в `pkg/docker`) отражена в аннотациях соответствующих
  клеточек, а не потеряна при переносе в DSL
- Черновой каркас `cells/` отсутствует в рабочем дереве (не создан заново вместо клеточек в
  существующих директориях пакетов)

## Stack

- **Язык:** Go 1.26 (версию в `go.mod` не менять)
- **Frameworks:** cobra (CLI)
- **Libraries:** gorilla/websocket, yaml.v3, golang.org/x/term, golang.org/x/tools (go/analysis),
  golang.org/x/sys/windows, pgregory.net/rapid (тестовая)
- **Infrastructure:** нет БД/брокеров — только файловая система (`.afm/` для состояния/локов) и
  Docker как опциональная среда исполнения

## Risks and Constraints

- `pkg/orchestrator` — самая крупная и сложная единица (11 файлов); есть риск, что описание одной
  клеточкой окажется слишком крупным для фокусированного контракта — решение о дроблении явно
  делегировано на этап `goga-brainstorm` (см. Scope), без переноса файлов
- Проект содержит нестандартную для DSL-примеров специфику (файловый polling-протокол диалога,
  reverse proxy с рантайм-детекцией upstream, Docker-режим с дропом привилегий через `gosu`) — есть
  риск потерять эти нюансы при формальном сведении к типам/routines; каждый такой механизм явно
  перечислен в Acceptance Criteria, чтобы не быть упущенным
- `pkg/web` и `assets` — не имеют предметного API в привычном смысле (`go:embed` ассетов); при
  проектировании их клеточек контракт может свестись к минимальному (embedded FS + путь), это
  ожидаемо и не является ошибкой дизайна
- Циклических зависимостей в графе импортов на момент анализа не обнаружено — граф в Current State
  проверен по факту (`grep` реальных импортов)

## Scope Estimate

Одна задача, покрывающая миграцию всего проекта (15 единиц / минимум 16 клеточек — см. Acceptance
Criteria про обязательное разделение `pkg/web`), с обязательным порядком выполнения по 5 bottom-up
слоям (см. граф в Current State). Слои — не отдельные подзадачи с независимой пользовательской
ценностью, а обязательная последовательность самого `goga-brainstorm` (нельзя спроектировать контракт
клеточки, импортирующей типы ещё не спроектированной зависимости):

1. Слой 0 — 9 единиц / 10 клеточек-листьев (`pkg/config`, `pkg/flow`, `pkg/state`, `pkg/progress`,
   `pkg/mcp`, `pkg/proxy`, `pkg/web` → 2 клеточки: `embed.go` + веб-ассеты, `assets`,
   `tools/setstatuslinter`)
2. Слой 1 — 3 клеточки (`pkg/prompts`, `pkg/docker`, `pkg/executor`)
3. Слой 2 — 1 клеточка (`pkg/orchestrator`, с возможным дроблением на этапе brainstorm)
4. Слой 3 — 1 клеточка (`pkg/server`)
5. Слой 4 — 1 клеточка (`cmd/afm`)

## Existing Architecture

Клеточек Goga в проекте нет — это первичная миграция «с нуля». Черновой каркас `cells/`
(альтернативная раскладка с переносом файлов) обсуждался на этапе formulировния, но в текущем рабочем
дереве отсутствует — решение не использовать эту раскладку принято в ходе formulировния (см. Out of
scope). `.goga/config.yml` отсутствует, поэтому
project-level `codemanifest.usages`/`codemanifest.annotations` не заданы; единственный существующий
артефакт архитектуры Goga в проекте — `.goga/usages/cooks/*.md` (7 файлов, см. External Dependencies).

## Notes

- Гранулярность «1 Go-пакет = 1 клеточка» (15 юнитов, включая `assets` и `tools/setstatuslinter`) и
  решение вести миграцию одной задачей (не дробить на отдельные `docs/tasks/*.md` по слоям)
  подтверждены пользователем в ходе formulировния задачи (диалог propose-стадии)
- Решение не переносить `.go`-файлы в отдельное дерево `cells/`, а класть `CODEMANIFEST` прямо в
  существующие директории пакетов — явное решение пользователя (альтернатива с физическим переносом
  кода отклонена)
- Для `pkg/web` — Go-часть (`embed.go`) и веб-часть (html/css/js) описываются раздельными
  CODEMANIFEST «как есть», без выдумывания API; дальнейшее разделение — вне этой задачи
