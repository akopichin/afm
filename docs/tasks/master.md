# Учёт потребления (токены / деньги / килобайты) по стейджам с дашборд-панелью

## Current State

afm сегодня **не учитывает потребление ресурсов агентами вообще** — ни токенов, ни стоимости, ни объёма
трафика. Что установлено по коду и реальным логам прогонов:

- **Единственное место с `usage`** — `pkg/proxy/zai.go`: `ZAITransform` достаёт `usage` из SSE-ответа,
  но **только** для переписывания non-streaming→streaming под обход 529 у `api.z.ai`, и **ничего не
  сохраняет** — `msg.Usage` уходит в пересобранный JSON и забывается.
- **Прокси не инспектирует тело ответа при обычном passthrough.** `pkg/proxy/proxy.go:passthroughTo`
  использует `httputil.ReverseProxy` только с `Director` — без `ModifyResponse` и без чтения тела.
  Значит для `stream:true` (нормальный случай) байты проксируются «вслепую», `usage` не извлекается.
- **Данные уже на диске.** Каждый агент пишет stream-json в `.afm/runs/<run>/<stage>/<phase>.jsonl`.
  Финальное событие `"type":"result"` содержит (проверено на реальном логе):
  - `total_cost_usd` — стоимость, посчитанная **claude-клиентом** (не шлюзом);
  - `usage`: `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`;
  - `duration_ms`, `num_turns`, `subtype` (`success`/`error`), `session_id`.
  - afm парсит stream-json только для tool-actions (`pkg/executor/executor.go`) и диалогового
    транскрипта (`pkg/executor/transcript.go`) — **`result`/`usage` не читаются**.
- **`RunState`/`StageState`** (`pkg/state/state.go`) хранят лишь `status` + `updated_at` +
  `stage_names` — потребления нет.
- **Дашборд** (`pkg/server` + `pkg/web/dashboard`: `app.js`/`index.html`/`style.css`) потребление не
  показывает.
- Боль от отсутствия учёта задокументирована вручную: `docs/2026-07-04-design-stage-token-burn-report.md`
  считал «сожжённое» по тем же jsonl руками (~$35 за 4 попытки стадии `design`).

**Ключевая верификация (по запросу пользователя):** на прокси приходят **токены** для всех
Anthropic-совместимых моделей (в ответе есть `usage`), но **НЕ приходит стоимость** — `total_cost_usd`
считает claude-клиент, она живёт только в `result`-событии jsonl. KB и per-request таймстампы доступны
**только** на прокси (он видит тела и момент каждого запроса).

## Description

Реализовать учёт потребления по стейджам через **гибридную** архитектуру:

1. **Прокси-мидлварь** — слой инспекции ответов, который для **каждого** запроса (всех моделей, не
   только ZAI) парсит SSE/JSON-ответ, извлекает `usage` (токены) и считает байты запроса/ответа (KB) с
   таймстампом и моделью. Даёт all-models, KB и графики по времени. Базируется на обобщении `parseSSE`
   из `zai.go`.
2. **Pricing + атрибуция + агрегат + API** — опциональная секция `pricing:` в конфиге
   (input/output/cache $/Mtok по модели); стоимость **дерайвится из токенов только если pricing задан**
   (нет конфига → метрики денег нет, только токены/KB). Атрибуция запросов к стейджам (timing-корреляция
   через `events.jsonl`); агрегация по стейджу/времени/метрике; endpoint вида
   `/api/usage?metric=tokens|cost|kb&stage=…`.
3. **Дашборд-панель** — кнопка со стрелкой слева → выезжающая слева-направо панель: свич метрик
   (токены/деньги/KB), фильтр по стейджам, графики потребления по времени. Метрика «деньги» показывается
   только когда задан pricing-конфиг.

Стоимость — **единый механизм**: дерайв из токенов через pricing-конфиг, опционально. Двух источников
стоимости (авторитетный из jsonl + дерайв) не делаем — это сознательное упрощение по решению
пользования. jsonl-`result` остаётся источником **атрибуции по стейджу/фазе** и авторитетных токенов
(кросс-чек / фолбэк, когда прокси не активен).

## Scope

**In scope:**
- Прокси-слой инспекции **всех** ответов (SSE для `stream:true`, JSON для non-streaming): извлечение
  токенов (`input`/`output`/`cache_creation`/`cache_read`) + подсчёт байт запроса/ответа (KB) +
  таймстамп + модель, для всех Anthropic-совместимых upstream'ов. Обобщение `parseSSE` (`pkg/proxy`).
- Запись usage-записей (per-request) в лог прогона (напр. `.afm/runs/<run>/usage.jsonl`).
- Секция `pricing:` в конфиге (`pkg/config`): per-model $/Mtok для input/output/cache.
- Дерайв стоимости из токенов **только при наличии pricing**; отсутствие конфига → метрика денег скрыта.
- Атрибуция per-request usage-записей к стейджам (timing-корреляция через stage start/end из
  `events.jsonl`, владелец — `pkg/state`).
- Чтение `result`-событий из `<stage>/<phase>.jsonl`: авторитетные токены + `total_cost_usd` для
  кросс-чека стоимости и фолбэба (когда прокси не активен).
- Агрегация потребления по стейджу / по времени / по метрике (токены / стоимость / KB).
- Новый API-endpoint(ы) в `pkg/server` для отдачи агрегатов дашборду
  (`/api/usage?metric=…&stage=…`).
- Дашборд-панель (`pkg/web/dashboard`): кнопка-стрелка слева → выезжающая панель; свич метрик
  (токены/деньги/KB); фильтр по стейджам; графики по времени.

**Out of scope:**
- **Свой прайсинг/биллинг/лимиты/алёрмы** — нет квот, нет уведомлений, нет блокировок по превышению.
  Только отображение.
- **Авторитетная стоимость из jsonl как отдельный источник** — стоимость единообразно дерайвится из
  pricing-конфига; `total_cost_usd` из jsonl не показывается отдельно (может использоваться лишь как
  внутренний кросс-чек).
- **Поддержка не-Anthropic-совместимых шлюзов без usage в ответе** — если upstream не отдаёт `usage`,
  токены для него не считаются (фиксируется как факт, не дорабатывается).
- **Счёт без активного прокси как primary-функция** — основной захват идёт через прокси; jsonl-фолбэк
  (чтение `result`-событий — см. In scope) **в scope** и даёт токены + атрибуцию для claude-агентов;
  вне scope без прокси только KB и real-time per-request (см. Risks).
- **Сохранение/миграция стоимости в `state.json`** — агрегация считается по требованию (on-demand) из
  usage-лога; schema `RunState`/`StageState` не меняется под стоимость (только если не потребуется
  кэш — решает design-стадия).

## Acceptance Criteria

- **Все модели считаются.** При включённом прокси для любого Anthropic-совместимого upstream'а
  (claude, `api.z.ai`, glm-обёртки и т.п.) per-request usage-запись (токены + KB + таймстамп + модель)
  появляется в usage-логе прогона. Подтверждается на ≥2 разных upstream'ах.
- **Passthrough тоже считается.** Метрика собирается не только для `ZAITransform`, но и для обычных
  `stream:true`-ответов (прокси начал читать тело ответа, не только ZAI).
- **Атрибуция к стейджу.** Каждая usage-запись (или агрегат) соотносится со стейджом; в дашборде
  фильтр по стейджам показывает потребление именно этого стейджа.
- **Pricing опционален.** Без секции `pricing:` в конфиге метрика «деньги» скрыта (токены и KB
  показываются). С `pricing:` — стоимость дерайвится и показывается; цифра для claude-агента
  осмысленно близка к `total_cost_usd` из его `result`-события (кросс-чек в разумной погрешности).
- **Свич метрик.** В панели дашборда переключатель токены/деньги/KB меняет отображаемую метрику
  (включая оси графиков).
- **Графики по времени.** На выбранной метрике строится временной ряд с фильтром по стейджам.
- **API.** Новый endpoint отдаёт агрегаты (метрика × стейдж × временной интервал), консьюмится
  дашбордом; старые endpoints не сломаны (`handlers_test.go` зелёный).
- **Чистый `go build`/`go vet`/существующие тесты**, без понижения go-версии в `go.mod`. Линт (`golangci`/`goga lint`) чист.

## Risks and Constraints

- **Атрибуция стейджа на прокси — главная нерешённая задача.** Прокси видит HTTP-запросы, но не знает
  стейдж. timing-корреляция по `events.jsonl` (stage start/end) работает, пока стейджи не пересекаются
  по времени; **параллельные стейджи / вложенные сабагенты** дают неоднозначность. Сабагенты внутри
  одного стейджа атрибутируются корректно (тот же стейдж), но два одновременно идущих top-level стейджа
  — нет. Механизм атрибуции уточняется на design-стадии (timing vs явный маркер).
- **Счёт зависит от активного прокси.** Если upstream не задан (`proxy: skipped (no upstream)`),
  primary-захват (токены per-request, KB, real-time) не работает. jsonl-фолбэк даёт токены +
  атрибуцию для claude-агентов, но без KB/per-request. Это ограничение фиксируется явно (не блокер).
- **Парсинг SSE на лету.** tee-чтение стрима ради извлечения `usage` не должно тормозить отдачу ответа
  агенту (читать параллельно/после, не блокируя flush). reuse `parseSSE` покрывает `\n`-разделители
  (Anthropic); `\r\n`-edge-case из известных ограничений `zai.go` inherited.
- **Дрейф pricing↔реальность.** Стоимость дерайвится из $/Mtok в конфиге; если тарифы устарели или
  модель неизвестна — цифра расходится с реальным биллингом. Считается оценкой, не источником правды.
  Кросс-чек против `total_cost_usd` из jsonl для claude-агентов — способ валидации.
- **Объём usage-лога.** per-request лог может расти на длинных прогонах с многими сабагентами (инцидент
  упоминал 12 параллельных); продумать ротацию/агрегацию, не раздувать лог бесконечно.
- **Дашборд-чарты без библиотеки.** hand-rolled временные ряды могут оказаться дороже, чем подключить
  мини-либу; решение оставить за design-стадией (по умолчанию — без новой зависимости).

## Scope Estimate

Три подзадачи (каждая — независимая ценность), подтверждены пользователем:

1. **Прокси-захват usage** (backend, `pkg/proxy` [+ `cmd/afm`/`run.go` — уже поднимает прокси]) —
   слой инспекции всех ответов: токены + KB per-request, все модели, real-time; запись в
   `.afm/runs/<run>/usage.jsonl`. Обобщение `parseSSE`. Самодостаточна: usage-лог пишется даже без UI.
2. **Pricing + атрибуция + агрегат + API** (backend, `pkg/config` + новый accounting-пакет
   [или расширение `pkg/state`] + `pkg/server`; атрибуция читает `events.jsonl` через `pkg/state`,
   без зависимости на `pkg/orchestrator` — см. Existing Architecture) — секция
   `pricing:`, дерайв стоимости (опционально), атрибуция к стейджам, jsonl-result-reader
   (авторитетные токены + `total_cost_usd` кросс-чек + фолбэк без прокси), агрегация, endpoint
   `/api/usage`.
   Самодостаточна: API отдаёт агрегаты даже без UI.
3. **Dashboard UI** (frontend, `pkg/web/dashboard`) — кнопка-стрелка → выезжающая панель, свич
   метрик (токены/деньги/KB), фильтр по стейджам, графики по времени. Зависит от 1+2 (API).

Порядок: 1 → 2 → 3 (3 зависит от API из 2; 2 зависит от usage-лога из 1). Подзадачи 1 и 2 можно вести
последовательно, UI — последним.

## Existing Architecture

Затрагиваемые клеточки (`goga schema`, 16 cells, `goga lint` → 0 ошибок):

- **`pkg/proxy`** — ядро подзадачи 1: новый слой инспекции ответов (tokens + KB), обобщение `parseSSE`.
  Сейчас инспектирует только `ZAITransform`.
- **`pkg/config`** — секция `pricing:` (по образцу существующей `ProxyConfig`).
- **`pkg/server`** — новый endpoint `/api/usage` (по образцу существущих `/api/stages/…`).
- **`pkg/state`** — источник атрибуции и место агрегации: `events.jsonl` (stage start/end) реально
  пишется и владеется `pkg/state` (`Store.Apply`/`Store.Open`), не `pkg/orchestrator` (тот лишь
  потребляет `Store` как импорт). Новая accounting-логика (агрегация usage по стейджу/времени/метрике,
  реализуется здесь или в новом accounting-пакете) должна зависеть **только** от `pkg/state` (сейчас
  без зависимостей), а не от `pkg/orchestrator` — иначе получится запрещённый cross-import
  (orchestrator уже импортирует `Store`/`RunState`/`StageState`/`Transition` из `pkg/state`).
  `activeAgents` (приватное поле `Orchestrator`, `pkg/orchestrator/orchestrator.go:87`) не является
  частью контракта и не используется как источник атрибуции; если атрибуция «стейдж выполняется прямо
  сейчас» всё же понадобится — это требует нового экспортируемого метода `pkg/orchestrator` и должно
  быть явно зафиксировано на design-стадии как изменение контракта.
- **`pkg/executor`** — владеет форматом `<phase>.jsonl` (stream-json лог агента, включая `result`
  событие с `usage`/`total_cost_usd`): имя файла и формирование лога — `pkg/executor/executor.go`.
  jsonl-result-reader из подзадачи 2 читает файлы этой конвенции (уже используемой `pkg/orchestrator`
  для `detectDialogViolation`/plan adoption); новый cell-код может зависеть от `pkg/executor`
  напрямую без риска cross-import (ничего не импортирует обратно из accounting-пакета).
- **`pkg/web/dashboard`** — подзадача 3: выезжающая панель + свич + фильтр + графики (vanilla JS).
- **`cmd/afm`/`run.go`** — прокси уже поднимается до оркестратора; thread pricing/usage-опций через
  `Options`/`Config` по необходимости (по образцу proxy-threading из CLAUDE.md).

При добавлении нового accounting-пакета — завести под него отдельную клеточку с `CODEMANIFEST` +
`.usages/` (следовать конвенциям `.goga/usages/conventions.md`), не раздувать существующие клетки.

- **Решения, подтверждённые в диалоге propose-стадии:**
  - Суть прогона — **новая фича в afm** через goga-пайплайн (не интеграция goga как workflow, не
    housekeeping). Тема: учёт потребления по стейджам.
  - Архитектура — **гибрид** (прокси захватывает токены+KB per-request для всех моделей + jsonl для

    all-models + KB + графиков по времени (→ нужен прокси), а идеальная атрибуция стейджа и
    авторитетные токены бесплатны из jsonl.
  - **Стоимость опциональна через pricing-конфиг**: нет конфига → метрики денег нет (только

    отдельной метрикой не показывается (единый механизм стоимости).
  - Разбивка — 3 подзадачи (1/2/3 выше).
  - Графики — пока без новой chart-библиотеки (решение за design).
