# afmsdk Release Notes

Newest first. See the module's [README](./README.md) for usage; see the main project's [release-notes.md](../release-notes.md) for afm itself.

## 2026-08-13

### New: `afmsdk` — a Go SDK for driving afm flows from another Go program

- New nested Go module at `sdk/` (`github.com/akopichin/afm/sdk`, package `afmsdk`) — not yet tagged, no third-party dependencies, and zero dependency on any `github.com/akopichin/afm/...` package. `Client.Start(ctx, flowPath, workDir)` spawns `afm run --dir <isolated> --port <picked> <flowPath>` as a real subprocess; `Run.Status`/`Approve`/`Retry`/`Revise` talk to that run's own dashboard HTTP API for the rest of its lifecycle. See the [README](./README.md) for the full API and a usage example.
- **Why subprocess + HTTP, not an embedded orchestrator.** Every afm package is already public (no `internal/`), so embedding `pkg/orchestrator` directly was a real option. It was rejected once planning surfaced that `afm approve/retry/revise` (the CLI subcommands) take an exclusive `flock` on the run directory that the live `afm run` process already holds for as long as any stage sits in `awaiting_approval` — so the only channel into a *live* run is its own dashboard HTTP server, started with `--port`. This also means ctx cancellation must send `SIGINT`, never `SIGTERM` — afm's own graceful shutdown (`cmd/afm/run.go`) only traps `SIGINT`.
- **Isolation is load-bearing, not cosmetic.** `afm approve/retry/revise` resolve their target as "the latest run containing this stage ID" across the whole `.afm/runs/` directory — two concurrent runs of the same flow sharing one `.afm/` would be ambiguous. `Client.Start` auto-generates a unique isolated `--dir` per run (under `Config.BaseDir`, default `os.TempDir()`) specifically to avoid this, and picks a fresh `--port` per run for the same reason. `Start`'s `workDir` parameter (the subprocess's actual CWD) is deliberately a separate concept from that isolated state directory — one is pure state, the other is the target project the flow's agents operate on.
- Built via `superpowers:subagent-driven-development` — 11 tasks, each with a fresh implementer subagent and an independent task-scoped review, plus a final whole-branch review. Spec/plan: [`docs/superpowers/plans/2026-08-13-afm-go-sdk.md`](../docs/superpowers/plans/2026-08-13-afm-go-sdk.md).
- **Three genuine plan defects were found and fixed during implementation** (not just implementation bugs — the plan's own specified code was wrong in each case):
  1. The plan's `TestStageIDIsPathEscaped` asserted on `r.URL.Path`, which Go always decodes (a literal `/` and an escaped `%2F` both decode to the same string, so `.Path` can never show `%2F`) — the test could not pass with *any* correct implementation. An interim "fix" attempt (manually setting both `url.URL.Path` and `.RawPath` to the pre-escaped string) actually double-percent-encoded the wire format (`%2F` → `%252F`); reverted to the plan's original plain string-concat `post()`, and the test fixed to assert `r.URL.EscapedPath()` instead.
  2. The plan's test helpers were specified as `(t *testing.T, ctx context.Context, ...)`. This repo's `.golangci.yml` enables `revive` with `enable-all-rules: true` and does not disable `context-as-argument` (ctx must be the first parameter) — every helper signature was corrected to `(ctx, t, ...)`.
  3. The plan's `Revise()` integration test asserted on the stage reaching `StageRevising` — a real, durably-logged state, but one that lives only ~20–30ms (afm's re-plan goroutine races the HTTP response for the very POST that triggered it, and reliably wins). No HTTP poll, including a zero-sleep busy-loop, could reliably observe it — confirmed independently via raw `curl` against the built binary plus reading `events.jsonl` directly, outside the Go test binary entirely. Fixed with a tight local 10ms-interval poll for *any* departure from `awaiting_approval` instead of the specific (unobservable) intermediate state.
- **The final whole-branch review caught two cross-task issues** invisible to any single task's diff: the package doc's usage example unconditionally called `Wait(ctx)` after a `Failed` status, which deadlocks (afm deliberately keeps the subprocess alive on failure, unlike on success, so `Wait` never returns without cancellation) — fixed to cancel the context on the failure branch; and `Client.Start` leaked the isolated run directory on every error path after `pickFreePort`/`cmd.Start`/`waitReady` failed, since the caller got `nil, err` with no `*Run` to call `Cleanup()` on — fixed with `os.RemoveAll` on those paths.
- **Manually verified against a real `claude` agent**, not just the automated integration test suite: built a throwaway HTTP service (`POST /runs`, `GET /runs/{id}/status`, `POST /runs/{id}/{approve,retry,revise}`, `DELETE /runs/{id}`) wrapping `afmsdk`, and drove a real `agents: [planning]` / `command: claude` flow through it end to end — `Start` spawned the real subprocess and agent, `Status` tracked `planning` → `awaiting_approval`, `Approve` correctly completed the (planning-only) stage, the real `afm run` process exited cleanly on its own once the flow finished, the background `Wait` goroutine observed the clean exit, and `Cleanup` removed the run directory. Two environmental snags on the way, neither an SDK bug: this dev machine's `~/.afm/config.yaml` has `docker.enabled: true`, worked around with `AFM_IN_DOCKER=1` (forces native execution regardless of config); that in turn triggered a Docker-agent-recipe validation path that an older, separately-installed `afm` binary rejected (a config schema newer than that binary) — worked around by pointing the test harness at a freshly-built binary instead.
- **Incidental discovery from that manual test, not an SDK bug:** `/api/status`'s `flow_name` field was always empty for every run, CLI or SDK alike — `RunState.FlowName` was declared and read but never actually assigned anywhere in afm's own code. Fixed on a separate branch (`fix/flow-name`, afm core — not this module); will show up in the main project's [release-notes.md](../release-notes.md) once merged.
