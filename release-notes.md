## 2026-09-04

### Feature: file browser — "changed files" view (All / Unstaged / vs HEAD)

The Docker project file browser's left panel gained a tools toolbar at the top with a three-way view switch, so you can jump from the full source tree straight to just the files that changed — without hunting through the tree:

- **All** — the existing lazy source tree (unchanged default).
- **Unstaged** — a flat list of files that differ from the index (`git diff`, working tree vs index), plus untracked files as *added*.
- **vs HEAD** — a flat list of files that differ from the last commit (`git diff HEAD`, working tree vs HEAD), plus untracked files as *added*.

Untracked (new) files show up in **both** changed views — afm agents create files constantly, and you want to see them. The two modes only diverge when someone has staged edits (`git add`): a fully-staged file is absent from **Unstaged** (working tree matches the index) but present in **vs HEAD**. The name **Unstaged** describes the baseline precisely (staged edits are still uncommitted, but are deliberately excluded from working-tree-vs-index); a tooltip on each mode spells out the baseline and notes that untracked files are included.

Each row carries a status badge — **M**(odified) / **A**(dded) / **D**(eleted) — where the letter, not just the color, is the signal, and the status word is exposed to screen readers. A selectable file opens on click (the right pane's **DIFF** tab still shows `HEAD → current file`) and can be checkbox-selected to insert `[AFM file: …]` references, exactly like the tree. Deleted files are shown as a muted, non-clickable marker row (there is nothing on disk to open or reference). The search box is hidden in the changed views (it searches the tree) and returns in **All**; a **Refresh** button re-fetches on demand (no background git polling). The list scrolls within the modal and adapts to every skin × light/dark.

Backend: a new read-only, security-hardened `GET /api/files/changed?root&mode=index|head` (`workspace.FS.Changes`) that runs git only against the verified in-root `--git-dir`/`--work-tree`, with a sanitized environment (ambient `GIT_*` selectors stripped so nothing can redirect git at a foreign index/object store), treats every git-emitted path as untrusted (UTF-8 + path validation, and selectability decided by a real `openat2`+`fstat`, never by git's status letter), bounds its work (per-process byte cap, entry cap, per-path syscalls bounded to the capped survivors, cancellation on request close), and distinguishes a genuinely unborn repo from a corrupt HEAD. Like the rest of the browser it is Docker-only and returns `404` on a plain host run.

## 2026-09-03

### Feature: Docker project file browser — read-only source tree, diffs and file references in the dashboard

In Docker mode the dashboard can show a folder button that opens a read-only project file browser: browse the source tree, view files with syntax highlighting, see a per-file `HEAD → working tree` diff, and insert references to selected files into a plan or question review comment — the agent receives the exact container path and reads the file itself. The whole feature is **Docker-only** (it needs the host launcher's mount manifest) and **strictly read-only** (no create/edit/rename/delete from the dashboard). On a plain host run it is entirely absent: `/api/files/*` returns `404`, the capability is off, and no button renders.

**It is OFF by default — opt in** with `docker.file_browser.enabled: true` in the config, or with the env var `AFM_FILE_BROWSER=1` (accepts `1`/`true`/`0`/`false`). The env var takes **priority over the config** in both directions: `AFM_FILE_BROWSER=1` force-enables even when the config disables it, `AFM_FILE_BROWSER=0` force-disables even when the config enables it (empty/unset → the config decides). The decision is made host-side before Docker re-exec, so it also governs whether the browseable-roots manifest is forwarded into the container at all.

```yaml
docker:
  enabled: true
  file_browser:
    enabled: true            # opt-in; OFF by default (env AFM_FILE_BROWSER overrides this)
  extra_mounts:
    - path: ../shared-contracts
      name: contracts         # optional UI label; default = basename(path)
      browse: true            # a source mount — VISIBLE in the file browser (read-only)
    - path: ~/.ai-free
      browse: false           # credential mount — mounted to the agent, NOT browseable
    - ~/.legacy-agent          # legacy scalar form still works = browse:false (stays private)
```

**What it does**

- **Lazy source tree** of the project mount plus any `extra_mounts` explicitly opted in with `browse: true`; directories expand on demand, listings paginate, and `.git`/`.afm` are hidden.
- **Syntax highlighting** for Go, TypeScript/TSX, JavaScript/JSX and Python via `highlight.js/lib/core` (only those four grammars are bundled); everything else renders as escaped plain text. Highlighting is theme-aware — token colors map to the dashboard palette, so it adapts to every skin (base/coffee/goga/novacorps) and to light/dark mode.
- **`HEAD → working tree` diff** per file: tracked files show staged+unstaged changes together, untracked files render as fully added, a clean file returns an empty diff, and a live `modifiedAt` + **Reload** button let you re-check a file an agent is editing under you (a `304` keeps the current content with no flicker).
- **File references**, not content copies: selecting one or more files inserts a `[AFM file: "<absolute container path>"]` marker (the path is JSON-encoded, so quotes/backslashes/newlines are safe) into a plan or pending-question comment. It rides the existing `revise`/`dialog-answer` chains — no new event types, no bytes copied into `feedback.md`; the agent opens the path with its own tools.

**Security is part of the feature, not a follow-up**

- **Manifest allowlist is the only source of roots.** The host launcher — the single place that knows every mount's real container target — emits a versioned, base64 manifest of browseable roots (`AFM_DOCKER_FILE_ROOTS`); the server never accepts an absolute path over HTTP, only `root=<opaque-id>&path=<relative>`. Credential mounts and legacy scalar `extra_mounts` are never in the manifest, so an afm upgrade never silently exposes a token directory.
- **Kernel-enforced containment.** Every path open goes through Linux `openat2` with `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_SYMLINKS` — no check-then-open, no symlink escape, no `..` traversal. On a kernel too old for `openat2` (< 5.6) the feature degrades off rather than falling back to anything weaker.
- **Loopback-only dashboard when the browser is on.** With the file browser enabled the Docker dashboard port is published on `127.0.0.1` instead of `0.0.0.0`, so the code the browser can read isn't reachable from other hosts on the LAN. Because the browser is OFF by default, this only affects runs that explicitly opted in (config `enabled: true` or `AFM_FILE_BROWSER=1`) — plain Docker runs keep the previous `0.0.0.0` publish behavior. If you opt in but still need LAN access to the dashboard, use an SSH tunnel.
- **Bounded and shell-free.** File content is capped at 2 MiB and diffs at 4 MiB; git is invoked without a shell, with a 3 s timeout, reading only the `HEAD` blob from a verified in-root git dir. Error bodies carry a fixed code, never an absolute path or raw git stderr; source is served with `X-Content-Type-Options: nosniff` and rendered through exactly one `dangerouslySetInnerHTML` fed only by highlight.js output (no XSS, no Markdown path for file content).

**Hardening from an external review (5 P1 + 5 P2, each verified then fixed with a regression test)**

- **`docker.file_browser.enabled` is now honored through config merge** — `mergeFile` dropped `FileBrowser.Enabled`, so a per-layer override (e.g. a project `enabled: true` on top of a global default) was silently lost. Now every config layer's setting survives the merge.
- **Diff can no longer read a git object store outside the allowlist.** A `.git` symlink or gitfile (`gitdir: /outside`, exactly how worktrees/submodules work) let `git -C` follow it out of the mount. `.git` is now located through the secure fd (a symlink `.git` is refused structurally), the resolved git dir must live inside the root, and git runs with an explicit `--git-dir` (no `-C` re-discovery). Reproduced before the fix; closed after.
- **Diff can no longer OOM the process.** The `HEAD` baseline is size-checked (`cat-file -s`) before it's read, and an oversize baseline skips the in-memory diff entirely instead of buffering hundreds of MB and truncating afterward.
- **FIFO/socket/device files can no longer wedge a handler.** Reads open with `O_NONBLOCK` and require a regular file, so opening a FIFO returns `not_found` instead of blocking a goroutine forever; special files are non-selectable in the tree. Directory scans are bounded by a hard entry cap.
- **The capability flag now hides the comment picker too** — previously it gated only the header button, so a host run still showed "Attach project file" in comments and hit the disabled API. The gate is centralized in the browser provider; an in-flight file-reference request is generation-guarded so a stale response can't restore a selection after a run change, submit, or file switch. Frontend fixes also closed a root-switch tree race and made a failed "Load more" retryable.

**Verified live** (a local image built from the branch, a real Docker container, a real browser via Chrome DevTools): the dashboard published on `127.0.0.1:<port>`, `capability.file_browser` was true, `/api/files/roots` listed the project and the `browse:true` neighbor but **not** the legacy-scalar credential mount, the tree hid `.git`/`.afm`, Go/TS/JS/Python rendered with highlighting, the `HEAD → working tree` diff showed a modified file's added line and marked an untracked file `added`, `../credential` traversal returned `400` and a `.git` segment `404`, the `modifiedAt`/Reload UI rendered, and a file reference selected through the browser picker reached `feedback.md` (`revision 1`) as an absolute container path through the real revise chain. The Linux-only secure-filesystem tests (openat2 traversal/symlink rejection, `.git` symlink/gitfile refusal, oversize-baseline bound, FIFO non-hang, bounded scan, real `git` diff) were run in a Linux container and all pass. `make lint` (0 issues), `make build`, `go test ./...` (all packages, `-race`, no data races), and the dashboard suite (`vitest` + `tsc --noEmit`) are all green. Spec: `docs/superpowers/specs/2026-09-03-docker-project-file-browser-design.md`; plan: `docs/superpowers/plans/2026-09-03-docker-project-file-browser.md`. Docs: README "Project File Browser (Docker mode)" and `config.example.yaml`.

## 2026-09-02

### Fix: reliability audit — 13 races, hangs and durability gaps

An external reliability audit surfaced 13 findings across the orchestrator↔UI boundary, the file-based dialog protocol, and CI. Each was verified against the code before fixing; every fix ships with a regression test that was confirmed to fail when the fix is reverted. Grouped by area below.

**Orchestrator FSM races (Pause/Continue/Retry/complete)**

- **`completeStage` no longer runs side effects when the `EvComplete` CAS is lost.** It previously ignored the `Trigger(EvComplete)` result and unconditionally ran the after-hook, reflection and unblock cascade — so a `Pause`/`Revise` landing between the status read and the transition still fired all of them on a stage that never completed. Worse, it leaked `pendingAfterHooks`: `maybeRunAfterHook` incremented the counter, but `SpawnAgent`'s `shouldRun` skip dropped the decrementing callback on a now-paused stage, so `shouldExit()` never returned true and the run couldn't exit. Both `completeStage` (`orchestrator.go`) and `approveStage`'s planning-only branch (`control_api.go`) now gate every side effect on a successful `EvComplete` — and since a `done` stage can't be paused, the after-hook callback (and its decrement) is now guaranteed to run.
- **Pause→Continue during `script_before` no longer double-launches the stage.** `script_before` runs without an interrupt channel, so a `Pause` could succeed while it was still executing; by the time the hook returned, `Continue` had already spawned the agent independently (`resumeStageAtStatus`), and the hook goroutine — seeing status back at `running` (the ABA `running→paused→running`) — launched a second agent. A per-stage `pauseGen` generation counter (bumped by every `Pause`) is now captured before the hook and re-checked after: any pause during the hook makes `withBeforeHook` abdicate `mainFn`, leaving the single relaunch to `Continue`. This is strictly stronger than the old `currentStatus == paused` check, which the ABA slipped past.
- **Two concurrent `Retry` requests can no longer corrupt an already-restarted run.** `retryStage` cleared the interactive session/`.jsonl` *before* the `EvManualRetry` CAS, so the retry that lost the CAS could still wipe the freshly-created session of the one that won. Cleanup now runs *after* the CAS — only the winner clears.

**File-based dialog protocol (hangs)**

- **Reusing a question id after it was answered no longer hangs an interactive stage.** When an agent removed `answer.json` and rewrote `question.json` with a new question under the same id, the UI kept showing the old *answered* question with no input box. `ReadDialog` (`pkg/mcp/dialog.go`) now re-opens the entry when a fresh question arrives over a complete Q+A pair (adopts the new text, drops the stale answer), and `pollQuestions` re-appends the reused question to `dialog.jsonl` once the prior incarnation is answered — so the entry renders as pending again.
- **A question whose filename id differs from its JSON-body id no longer hangs forever.** `FindUnansweredQuestions` returned the id from the JSON body but checked the answer path by filename; the answer then landed at a path the agent never polled. The **filename id is now authoritative** (it's what the agent's polling loop and the answer-existence check both key off).

**Metrics & dashboard**

- **`STARTED`/`ELAPSED` survive an afm restart/resume.** `NewRunState` stamps `StartedAt = time.Now()`, and log replay restored stage statuses and idle/backoff accumulators but not the start time — so a resumed run's `STARTED` jumped to the moment of restart. `parseEventLog` (`pkg/state/state.go`) now restores `StartedAt` from the first logged event's timestamp; a fresh run's empty log leaves it at ≈Open time as before.
- **`DialogChannel` no longer applies stale `/dialog` responses.** With a 2 s poll and overlapping in-flight requests, an older (pre-answer) response resolving after a newer (answered) one re-opened an already-answered question. A request-generation guard (the same pattern `useStatus` already uses) now applies only the latest response; and a transient fetch error returns `null` (not `[]`), so a single failed poll no longer wipes the visible dialog.
- **Dialog actions can't double-submit and no longer hide errors (finding #8).** The SEND button and options disable while a POST is in flight (a second click used to fire a duplicate the server 409s), "✓ Sent" shows only after success, and a failed submit surfaces a visible, retryable error instead of an unhandled promise rejection.
- **Event-feed rows use stable, unique React keys (finding #12).** The old `${timestamp}-${type}` key collided for several same-type events accepted in the same millisecond (duplicate-key warning, unstable DOM reuse). Keys are now occurrence-disambiguated (`seq` when present, else `timestamp|type|stageId` + `#N`).
- **`GET /log` is tail-capped (finding #10).** The endpoint concatenated every phase log in full and the UI re-fetched and re-parsed it every 3 s, so cost grew unbounded with run length. The response is now capped to the last 1 MB (trimmed to a line boundary, with a truncation marker).
- **Pre-note save is race-honest (finding #9).** `POST /note` re-checks the stage status after writing `prenote.md`; if the stage started between the `pending` check and the write (so the note won't reach the first prompt), it returns `409` instead of a silent `200`.

**Durability & CI**

- **`hook_pending.json` is written atomically (finding #11).** It used a bare `os.WriteFile` with the error ignored; a crash or torn write left an after-hook (which never touches the FSM) with no recoverable Retry/Skip decision. It now writes via temp + fsync + rename + parent-dir fsync, and write errors are logged.
- **CI now runs the UI and SDK test suites (finding #13).** `make build` (a `vite build`) exercised neither Vitest nor `tsc --noEmit`, and SDK tests lived only in un-invoked Make targets — UI/SDK regressions could reach `main` on green CI. The `validate` job now runs `make web-test`, `make web-typecheck` and `make sdk-test` (new Makefile targets for the first two).

- **Verified live** (native build of the branch, docker disabled so the real current source runs, mock agent, real dashboard via Chrome DevTools): a 4-stage flow (planning+auto-approve+hooks → script → autonomous → interactive) ran clean to all-done with hook/script markers written; Pause→Continue during a long `script_before` produced `running→paused→running→done` with the agent launched **exactly once**; a reused question id re-rendered with an input box (not stuck on the answered one); a filename/JSON id mismatch was auto-answered at the filename path and completed; and a kill-mid-run restart resumed the same run with `STARTED` preserved. Tests: `pkg/orchestrator` (completeStage lost-CAS + counter-leak, pause-during-before-hook single-launch, retry lost-CAS, hook_pending round-trip), `pkg/mcp` (reused-id re-open, filename-id authoritative), `pkg/state` (StartedAt restored from first event), `pkg/server` (log tail-cap), `DialogChannel.test.tsx`/`EventFeedPanel.test.tsx` (stale-response guard, error-keeps-history, no double-submit, error surfaced, unique feed keys). `go build ./...`, `pkg/orchestrator`/`pkg/state`/`pkg/mcp`/`pkg/server` `-race`, `golangci-lint` (0 issues), 282 UI tests + typecheck, and `make sdk-test` all green.

## 2026-08-31

### Feature: agent-memory read/write control — `memory.mode` + `memory_use`

Agent memory (v3) previously injected the shared `memory.md` into **every** stage automatically and always rewrote it at end of run. Two new knobs make reading and writing independently controllable — and turn injection into an explicit opt-in.

```yaml
memory:
  path: docs/memory
  mode: rw          # lifecycle of the shared memory.md: r / w / rw (default rw)
  memory_use: true  # do stages READ memory at all? (default false → opt-in)
stages:
  - id: build
    reflect: { file: build.md, mode: rw }   # this stage's OWN file: r / w / rw
  - id: audit
    memory_use: false                        # opt THIS stage out of reading memory
```

- **`memory.mode` (`r`/`w`/`rw`, default `rw`)** governs the **shared `memory.md`**: `r` = read-only (injected into prompts, never rewritten), `w` = write-only (updated by the end-of-run pass, never injected), `rw` = both. `runEndOfRunMemory` now distills into `memory.md` only when the mode allows writing — with `mode: r` a hand-curated project memory is never overwritten, while per-stage `reflect` files are still written during the run.
- **`memory.memory_use` (global, default `false`) + per-stage `memory_use` (`*bool` override, unset = inherit).** This is the master switch for **reading**: a stage is injected memory only if it participates (`stage.memory_use ?? memory.memory_use`). Off by default — you opt in globally or per stage. It does **not** affect writing.
- **Two independent mode axes:** `memory.mode` controls the shared `memory.md`; `reflect.mode` (unchanged) controls a stage's OWN file; `memory_use` is the per-stage read master switch. Reading a stage's own file still additionally requires `reflect.mode` `r`/`rw`; `mode: w` writes it without reading it back.
- **Gates in code:** `memoryBlockForStage` (`memory_inject.go`) applies the participation gate (`MemoryConfig.UseFor`) then `CanReadProject()` for `memory.md`; `runEndOfRunMemory` (`reflection.go`) applies `CanWriteProject()`. `flow.MemoryConfig.Mode`/`MemoryUse` + `flow.Stage.MemoryUse *bool`, defaulted/validated in `ParseFile` (`memory.mode` must be `r`/`w`/`rw`).
- Verified live on real `claude` agents across two runs: with `memory.mode: r` + global `memory_use: true`, the seeded `memory.md` was injected into a plain stage and a `reflect: rw` stage but **not** into a stage overriding `memory_use: false`, and end-of-run left the seeded `memory.md` untouched while the stage's own file was written; with `memory.mode: w`, `memory.md` was **not** injected but was merged/rewritten by the end-of-run chain (preserving the existing seeded pattern). Tests: `pkg/flow` (mode/use helpers, parse defaults, per-stage override, invalid-mode validation), `pkg/orchestrator` (participation-off/override/write-only-hides read gates, read-only-skips-write end-of-run gate); `go build ./...` + `pkg/flow`/`pkg/orchestrator` `-race` + `golangci-lint` green. Docs: README "Agent Memory" (full read/write model + tables) and AGENTS.md.

## 2026-08-28

### Feature: agent memory v3 (directory + pattern chain)

A live run under v2 showed the structured YAML store (`evidence`/`confirm_count`/`first_seen`/`last_seen` per finding, `pkg/memory.Finding`/`Store`/`Reconcile`/`Evict`) was more machinery than the actual payoff justified — metadata nobody read, a two-agent reflect→consolidator pipeline that couldn't be inspected by eye, and per-stage relevance retrieval solving a scale problem that never materialized (the stores stayed small). v3 throws out the structured store entirely and replaces it with a **directory of plain Markdown rules files**, produced by a fixed, auditable chain of prompts.

- **`memory.path` is now a directory**, not a file. `flow.MemoryConfig{Path, MaxRules, Commit}` — the project-wide file is always `<path>/memory.md`, fixed name, cross-run. `max_findings`/`retrieval_threshold`/`core_confirm_count`/`final_reflect`/`project_file` are all **removed**; the end-of-run pass now always runs unconditionally once memory is enabled and at least one stage left a dataset.
- **Per-stage opt-in is an object, not a bool.** `reflect: { file: build.md, mode: rw }` — `mode` (`r`/`w`/`rw`, default `rw`) independently controls whether the stage's own file is written and/or injected back into it, so a downstream stage can read an upstream stage's file (`mode: r`) via `depends_on` without running its own write chain.
- **A five-step chain, not two agents.** **reflect** (RL-style dataset, same P1 exclude-list for afm/agent-protocol mechanics kept from v2) → **aggregate** (mutually-exclusive numbered pattern list) → **prioritize** (High/Medium/Low, all three tiers mandatory) → **code select-High** (`memory.SelectHigh`, deterministic, no LLM) → **update** (merges High patterns into the target file, caps at `max_rules` dropping Low first, rewrites `# Project rules` / `## Pattern` Markdown with priority encoded only by block order). Runs once per reflecting stage into its own file, and once more at end-of-run over every stage's dataset into `memory.md`.
- **`pkg/memory` shrank to pure path/parse helpers + git.** `ProjectFile`/`StageFile`/`AtomicWrite` (`paths.go`), `SelectHigh` (`selecthigh.go`), `Commit(dir, message)` (`commit.go` — `-- .`-scoped `git add`+`diff --cached`+`commit`, no push, only if there are staged changes under that directory). The entire structured-store core (`Finding`/`Store`/`Reconcile`/`Evict`/`Load`/`Save`/relevance `Select`/`Render`) is deleted.
- **`commit: true`** git-commits the memory directory at end of run with a fixed message, best-effort, never pushes.
- The scheduling/lifecycle envelope is unchanged from v2: `maybeRunReflection` triggered from `completeStage` after the unblock cascade, background via `SpawnDetached`, serialized by `reflectMu`, `pendingReflections` gates `shouldExit`, never touches the FSM, `reflect_failed` notice on any step failure.
- Tests: `pkg/flow` (`reflect{file,mode}` parsing/defaults/validation), `pkg/memory` (path resolution, `SelectHigh` parsing tolerant of the prioritize format, `Commit` against a temp git repo including the unrelated-staged-file scoping regression, atomic writes), `pkg/orchestrator`'s `TestMaybeRunReflection_*`/`TestEndOfRunMemory_*` (kept-envelope regressions, mode gating, script-stage skip, commit-on-enable) plus `TestIntegration_MemoryV3_{PipelineWritesStageFile,PointerReachesLaterStagePrompt}` (full reflect→aggregate→prioritize→update chain writes `reflect_dataset.yaml`/`patterns.md`/`prioritized.md`/`high.md` plus the stage's own Markdown file, then the end-of-run pass writes `memory.md` and its pointer reaches a later stage's actual built prompt via `memoryBlockForStage`+`prompts.Build`); `go build ./...` and the targeted `-race` runs green.
- Spec: `docs/superpowers/specs/2026-08-28-agent-memory-v3-design.md` (supersedes v2's storage/pipeline layer, keeps its scheduling envelope); plan: `docs/superpowers/plans/2026-08-28-agent-memory-v3.md`.
- Verified live — two runs of a real 3-stage `claude` flow (`reflect: {mode: rw}` on each). Every stage's chain produced `reflect_dataset.yaml`→`patterns.md`→`prioritized.md`→`high.md` and wrote its own `<path>/stepN.md`; the end-of-run pass wrote `memory/memory.md` with three mutually-exclusive High patterns (e.g. "Single Source of Truth Propagation", "Exact Path Fidelity and Write Verification") — generalized project patterns, **zero afm-boilerplate** (the P1 exclude-list held). Cross-run: run 2 merged into the same three patterns (no ballooning), and run 2's `step1` prompt carried the `<project_memory>` pointer to **both** `memory.md` and `step1.md` (mode `rw` → both injected), confirming per-stage injection-by-mode. Full `go test ./... -race` green.

## 2026-08-28

### Feature: agent memory v2 (structured, afm-owned)

A live 3-stage run of v1 (below) exposed four weaknesses: the captured memory was dominated by generic afm/agent-protocol mechanics rather than durable project-specific facts; every stage read the *entire* memory regardless of relevance; the prose `.md` store couldn't be deduplicated or evicted by value; and the updater/compressor agents rewrote the memory files in place with their own Write tool, so a killed agent could leave a partially written file. v2 replaces the prose store with a **structured, afm-owned YAML store** — `pkg/memory` now owns validation, metadata, eviction, and atomic writes; agents only extract and consolidate findings, never touch the store files themselves.

- **Structured findings, not prose.** `PROJECT_MEMORY.yaml` / `SESSION_MEMORY.yaml` (same cross-run/per-run split as v1) hold `pkg/memory.Finding` records — `scope`/`kind`/`topic`/`statement`/required `evidence` — plus afm-owned metadata (`first_seen`/`last_seen`/`confirm_count`). A finding without evidence is rejected at reconciliation time.
- **Two agents, not three.** **reflect** extracts candidate findings (prompt retuned to exclude afm/agent-protocol mechanics and require evidence); **consolidator** merges them against the current stores and verifies each candidate is durable/project-specific/evidenced (the compressor agent is **removed** — its job is subsumed by consolidation + code eviction).
- **afm-owned reconcile + eviction + atomic writes.** afm code reconciles `new`/`reinforced`/`unchanged` metadata, evicts the lowest-value findings once a scope exceeds `max_findings` (by `confirm_count`, then recency — deterministic, replacing v1's FIFO drop), and writes each store atomically (temp+rename). Agents write only their own candidate/merged byproducts (`reflect_dataset.yaml`, `consolidated.yaml`), never the store files.
- **Per-stage relevance retrieval, not a static pointer.** A small store (≤ `retrieval_threshold` findings) still gets a pointer to both files, read by the agent itself. Once the store grows past the threshold, afm inlines a bounded slice — every "core" finding (`confirm_count ≥ core_confirm_count`) plus findings whose tags/text match the current stage's id/name/description — computed and rendered in code, not by an agent.
- **Config:** `max_findings` (default 60), `retrieval_threshold` (default 25), `core_confirm_count` (default 3), `final_reflect` (unchanged). Removed: `max_bytes`, `compress_retries` (meaningless without a compressor).
- The enablement/scheduling layer is otherwise unchanged from v1: `memory:` + per-stage `reflect: true`, background/best-effort/serialized pipeline (`reflectMu`), `pendingReflections` gating `shouldExit`, never touches the FSM, `final_reflect` at `Run()` exit.
- Tests: `pkg/memory` unit coverage (schema validation, metadata reconciliation, eviction ordering, retrieval selection, atomic writes); `pkg/orchestrator`'s `TestReflectionPipeline_*`/`TestMaybeRunReflection_*`/`TestFinalReflection_*` (kept-envelope regressions) plus the new `TestIntegration_MemoryV2_*` (full reflect→consolidator→reconcile pipeline produces a validated finding with correct metadata, and its statement/pointer reaches a later stage's actual built prompt via `memoryBlockForStage`+`prompts.Build`, in both the small-store/pointer and large-store/inlined-slice cases); `go test ./... -race` and `golangci-lint run ./...` green.

## 2026-08-28

### Feature: agent memory (reflect → updater → compressor)

Every stage runs its agent in an isolated context, so whatever it learns — an API's real behavior, a required build flag, a rule it broke and had to correct — evaporates when the stage finishes, and the next stage starts blind. Agent memory carries those findings forward. Mark a stage `reflect: true` and, after it completes, afm runs a small **background, best-effort** pipeline of three agents that distills the stage's session into a persistent project memory that later stages (and later runs) are told to read.

```yaml
name: my-feature
memory:
  project_file: docs/PROJECT_MEMORY.md   # non-empty ENABLES the feature; path relative to root_dir
  max_bytes: 20000                        # per-file compression threshold (default 20000)
  compress_retries: 2                     # compressor attempts before the terminal fallback (default 2)
  final_reflect: true                     # also reflect once over the whole flow at the end (default false)
stages:
  - id: build
    reflect: true                         # this stage feeds memory after it completes
```

- **Two files, two lifetimes.** `PROJECT_MEMORY.md` lives in the repo at `memory.project_file` and accumulates **across runs** (long-term). `SESSION_MEMORY.md` is auto-created at `.afm/runs/<run>/SESSION_MEMORY.md` and **reset every run** (this run's short-term context). Both use a "Do's / Don'ts" format (🟩 Best Practices / 🟥 Anti-Patterns), written by the updater agent.
- **The pointer, not the content, is injected into every prompt.** afm appends a short block naming the two files' absolute paths to the global prompt of *every* stage (regardless of its own `reflect` value) — the agent reads the files itself with `Read`, so prompt size never grows with the memory.
- **A code-driven pipeline, not one smart agent.** After a `reflect: true` stage completes (in the background, the same ordering as `script_after`, so downstream stages are never blocked): **reflect** reads the stage session and writes an RL-shaped YAML dataset (`reflect_dataset.yaml`, kept on disk); **updater** merges/deduplicates it into both `.md` files in place; a pure-code **size check** then runs the **compressor** up to `compress_retries` times on any file over `max_bytes` (a dynamic "reduce to under N lines" pass on the last try), with a deterministic FIFO drop of the oldest entries as the terminal fallback (the header and the file itself are never destroyed).
- **Opt-in, best-effort, never touches the FSM.** `reflect` defaults `false`; `script:` stages are silently skipped (no agent session). Any pipeline step failing aborts the rest for that stage and surfaces a `reflect_failed` notice, but never fails the stage or the run. Pipelines are serialized (one writer to the shared files at a time) and tracked so the run can't exit mid-pipeline. `final_reflect: true` runs one extra reflection over the whole flow's session at `Run()` exit.
- **Three overridable prompts.** `reflect.md` / `updater.md` / `compressor.md` ship as embedded defaults under `assets/prompts/`, overridable per project via `prompts_dir` — the same mechanism as the existing phase prompts.
- Verified end-to-end with a **real 3-stage flow driven by live `claude` agents** (`agents: [auto]`, `reflect: true` on each, `final_reflect: true`): all three stages completed; each wrote `reflect_dataset.yaml` and its isolated `reflect.log`/`updater.log`; the updater genuinely read both files and consolidated new items; `PROJECT_MEMORY.md` (cross-run) and `SESSION_MEMORY.md` (per-run) filled with correctly-scoped 🟩/🟥 findings; the memory pointer appeared in a later stage's actual prompt (`autonomous.prompt.log` under `--debug`); and the flow-final reflection ran exactly once over the whole run. Tests: `TestParseMemory_*`/`TestValidateMemory_*` (flow), `TestBuildMemoryPrompt_*`/`TestFileExceeds`/`TestFifoDropOldestBlocks`/`TestReflectionPipeline_*`/`TestMaybeRunReflection_*`/`TestInitSessionMemory_*`/`TestFinalReflection_*`/`TestIntegration_Memory*` (orchestrator), plus `TestBuildMemoryPointer_*`/`TestLoadPrompts_IncludesMemoryPrompts` (cmd/afm); `make lint` clean, full Go suite `-race` green. Spec: `docs/superpowers/specs/2026-08-28-agent-memory-design.md`; plan: `docs/superpowers/plans/2026-08-28-agent-memory.md`.

## 2026-08-24

### Fix: FSM/frontend stability audit — one permanent hang, several lost-status/lost-message bugs

A parallel four-angle audit (FSM transition tables, non-FSM event delivery, flow-hang paths, frontend integration) surfaced seven defects; each fixed with a regression test written to fail first, plus a live Docker+browser run of the flagship hang. All in the same recurring families the codebase's own post-mortems warn about.

- **#1 (critical, permanent hang) — a non-interactive / `agents:[auto]` stage whose agent asked a dialog question and then exited before writing its completion artifact hung forever.** The stage gets parked in `awaiting_user_input` (by `retry.go`'s open-question hold or `onAgentCompleted`), but the non-interactive auto-answer path only wrote `answer.json` — it never drove the stage back out. The FSM's only exit from `awaiting_user_input` is `EvUserAnswered`, published exclusively by `NotifyAnswer` (the *human* HTTP answer path); the auto-answerer never emitted it, so nothing restarted the exited agent. Headless runs were unrecoverable, and even an `afm` restart mis-recovered the autonomous case into a missing-`plan.md` failure. Fixed by extracting `resumeAfterAnswer` (the body of `NotifyAnswer`) and calling it from the auto-answer path too, so auto-answer is symmetric with a human answer: agent still polling → FSM-only no-op; agent exited → critical-bus `EventUserAnswered` → `onUserAnswered` restarts it. Verified live: a mock autonomous agent that asks then exits with no summary now gets auto-answered, restarted, completes — and its dependent stage runs (proving the full completion cascade fired), with a `user_answered` transition appearing in `events.jsonl` despite no human involved.
- **#6 (medium) — a failed auto-answer write was never retried.** `pollQuestions` set `processed[key] = true` *before* `WriteAnswer`; a write error (disk, or an `O_EXCL` race) then left the key marked with no file on disk, so the agent's bash loop waited on `answer.json` until the executor idle timeout (~30 min) and failed. The key is now marked only after a successful write.
- **#5 (medium) — `EvScheduleRetry`/`EvResumeAfterRetry` omitted `AwaitingUserInput` from their `From` lists.** When the poller raced a stage into `awaiting_user_input` (stray question) just before the agent returned a retryable 529, both retry transitions were silently dropped and the whole backoff showed the wrong status; it only self-healed via a fall-through re-run — fragile enough that any future `return` on that path would have turned it into a hang. Both events now accept `AwaitingUserInput`.
- **#3 (high, lost message) — `hook_failed`/`hook_resolved` vanished on reload.** These were published live to the UI bus with no durable backing (the after-hook path never touches the FSM at all; the before-hook path's status transition reconstructs only as a generic `stage_status_changed`, losing the error/resolution text). A reloading user — or a second teammate opening the dashboard — never saw the failure or its resolution. A shared `publishHookNotice` now mirrors both to `notices.jsonl` (which `/api/events` replays), across all six publish sites.
- **#7 (medium) — retry feed lines lost/mis-rendered on reload.** The `EvScheduleRetry` transition was recorded with an empty reason, so on reload `retry_scheduled` reconstructed with no payload (`retry:` with the attempt/backoff gone); the attempt message is now stored as the transition reason. Separately, the "incomplete work, retrying" notice was published as a fake `stage_status_changed` whose data was a message, not a status — it rendered as an empty `→` badge live and was lost on reload; it now uses `EventRetryScheduled` and is mirrored to `notices.jsonl`.
- **#2 (high, stale UI) — the WebSocket-driven status refresh died permanently after 200 feed events.** The effect guarded on `refreshedForEvent === events.length`, but the feed is capped at `MAX_EVENTS = 200`, so once saturated `events.length` stayed `200` forever and the guard always returned early — on any real (long) run, stage-status/attention/desktop-notification refreshes silently fell back to the throttled 3s poll, which browsers throttle hard in a backgrounded tab. Now the effect tracks the last event by object identity (which changes on every new event) instead of by array length.
- **#4 (high, lost/reordered messages) — the reconnect merge reordered and could drop events that happened during a WebSocket outage.** `mergeHistory` did `[...deduped, ...live]`, so events present only in the freshly-fetched (authoritative, server-sorted) history — i.e. everything that happened while the socket was dead — landed at the *front* of the feed (visually oldest, missed by stick-to-bottom scroll) and were dropped first by `slice(-200)` when the buffer was full. History (already time-sorted server-side) is now the base and only genuinely-live-only events are appended at the end.

Verified: `make lint` clean, full Go suite green, dashboard 263 tests + build green, and the #1 hang reproduced-then-fixed in a real `akopichin/afm:latest` Docker run driven through the actual orchestrator.

### Fix: root-caused a long-standing test flake (`storage failure: write events.jsonl: invalid argument`) to a real process-group-kill bug in the executor, not OS flakiness

- The error text was itself the red herring: `(*os.File)`'s methods are nil-receiver safe in Go, so writing to a `Store` whose `eventsLog` had already been nilled out by a racing `Close()` doesn't panic — it silently returns `fs.ErrInvalid`, whose message is literally "invalid argument", indistinguishable at a glance from a genuine OS-level `EINVAL`. That's what made this look like unexplained environment flakiness across many unrelated-looking tests for a long time, rather than the two concrete bugs it actually was.
- **Bug 1 (test infrastructure, ~35 call sites across 11 files in `pkg/orchestrator`): tests started `orch.Run(ctx)` in a bare goroutine and only waited for a stage's status to look terminal, never for `Run` itself to return**, before letting `t.Cleanup` close the store. `Run`'s own shutdown sequence (`cancel` → `concurrency.WaitAgents()` → return) is the actual guarantee that every agent goroutine has stopped touching the store — a terminal-looking status doesn't provide that guarantee on its own. Fixed with one shared helper, `runOrchestratorAsync` (`pkg/orchestrator/testrun_helper_test.go`), applied at every call site: starts `Run` in the background and registers a `t.Cleanup` that cancels the context and waits on a `done` channel closed after `Run` actually returns, with an honest `t.Error` after a generous 10s instead of silently proceeding.
- **Bug 2 (real production bug, `pkg/executor/executor.go`): `cmd.Process.Kill()` only kills the direct child process, not its process group.** A `stage.Command` script whose last line spawns a child without `exec`ing into it (e.g. a plain trailing `sleep N`) leaves that grandchild holding the `stdout` pipe `cmd.StdoutPipe()` created — when the parent script gets killed (context cancellation, idle timeout, or the SIGINT grace-period fallback), the orphaned grandchild keeps that pipe's write end open, and the executor's own read loop never sees EOF: `<-done` blocks for however long the orphan happens to keep running (observed as 11–31s delays, matching test scripts' `sleep` durations exactly). Fixed with `killProcessGroup` (`syscall.Kill(-pid, sig)`, targeting the whole process group) plus `SysProcAttr{Setpgid: true}` so the spawned script becomes its own group leader — applied at all four kill sites in `run()` (idle timeout, context cancellation, and both steps of the SIGINT-then-force interrupt sequence). This is a real, not just test-only, reliability bug: the same mechanism could make afm's own "clean shutdown" (`waitAgents()`, bounded 10s) leave an agent goroutine running in the background well past that bound on a real `afm run` cancellation, if the stage's own command has this shape.
- Root-caused via `systematic-debugging`, not by guessing: the first hypothesis (OS/sandbox quirk) was ruled out by `git stash`-isolating the flake (still reproduced on an unmodified tree) and by a deliberate stress test — running extra concurrent `go test` processes on the same machine made the flake noticeably *more* frequent, the signature of a real race under load, not random environmental noise.
- **A related, narrower finding surfaced while fixing this**: an earlier same-day cleanup (see below) had removed a check in `onAgentCompleted` believing it to be a pure duplicate of a similar check in `runWithRetry` — it wasn't. `runWithRetry`'s check is deliberately gated to interactive/autonomous stages only (non-interactive stages are the auto-answer feature's job, see below); `onAgentCompleted`'s was ungated and covered every other phase/stage combination that gate skips (e.g. a non-interactive planning stage whose mock agent synchronously writes a question and returns immediately, faster than the poller can auto-answer it). Restored with the same "stale vs. live" distinction (current status already `AwaitingUserInput` means a poller raced ahead of a genuinely-finished agent; anything else means the question is live and worth holding for) rather than re-deleted a second time.
- One incidental fix found along the way: `TestRevise_DurableTransition`'s mock planning runner was dead code — it was assigned to the `Orchestrator`'s internal `runner` field directly, but `runnerFor` only ever returns that field when `opts.Runner` is set, which this test never did. The test was unknowingly making a real, slow `claude` CLI call on every run instead of using its mock.

### Fix: dialog poller could hang a stage forever on question-id reuse; malformed `question.json` now retried instead of shown broken

- Diagnosed from two real production logs (`goga`'s `skip-review-on-build` flow, `agents:[auto]` stages driven by a `goga-brainstorm` revision cycle), not reproduced synthetically first — root-caused via `systematic-debugging` before any fix was attempted.
- **Bug 1 — reused question id after being answered hung a stage in `running` forever, invisible to the browser.** The prompt tells agents "never reuse an id within a phase," but a real agent's revision loop reused the same id (`q2`) for a second, genuinely different question after the first `q2` was answered — confirmed byte-for-byte from the agent's own action log (`Write q2.question.json` → `cat q2.answer.json` → `Write q2.question.json` again → `rm -f q2.answer.json`). `pollQuestions`'s `processed` map (`stageID|phase|id → bool`) never released a key once set, so the second, real, unanswered `q2` was permanently invisible: no `ask_user` event, no dialog entry, and no way to fix it short of restarting the whole `afm` process (a page reload can't help — the bug lives server-side, in the orchestrator's memory). Fixed by pruning any `processed` key that drops out of the current unanswered set on every poll tick, so a legitimately reused id is treated as new the moment it reappears unanswered.
- **Bug 2 — a `question.json` the poller couldn't parse was shown to the user as broken forever, when the underlying cause was often a torn read, not an agent mistake.** Byte-for-byte comparison against the same log proved it: the "malformed" preview captured at failure time is an exact prefix of the file's later, fully valid content, which never changed — afm's own poller had read the file mid-write (the agent's `Write` tool call hadn't finished landing on disk yet), and the old code's immediate fallback-stub-and-persist-to-disk behavior locked in that transient snapshot as if it were final, permanently, with a second on-disk overwrite compounding the very race that caused it.
  - New 3-layer state machine in the question poller, interactive stages only: (1) a **grace tick** — the first sighting of broken content is remembered and ignored; if it was a torn read, the very next 1-second tick reads a complete, valid file with zero agent involvement, which is exactly what would have silently fixed both real incidents; (2) **stable + still broken** (the same bytes on a second consecutive tick — proof the write actually finished) — afm nudges the agent through the exact file-based channel its own bash polling loop already reads (`<phase>.<id>.answer.json`), asking it to rewrite the same id with valid JSON, up to 3 times; (3) **exhausted** — after 3 failed nudges, afm gives up asking for valid JSON, persists a real parseable stub with no answer options (free text only), and only then shows it to the user — the dashboard already renders option-less questions correctly with zero frontend changes needed.
  - The synthetic nudge answer is written via a new `mcp.WriteInternalAnswer` (refactored out of `WriteAnswer`) that skips the dialog-history side effect entirely — an interactive stage's dialog panel is watched live, and a stray "→ please fix your JSON" bubble with no matching question would itself be a confusing artifact of an afm↔agent exchange the user was never part of, undermining the whole point of not bothering them during retries.
  - A companion fix in the poller (`unblockRewrittenMalformedQuestions`) handles the agent actually responding to a nudge by rewriting the same id: since the nudge's own answer.json would otherwise make that id look "already answered" forever (the same trap as Bug 1, but self-inflicted by the retry mechanism itself, not an agent mistake), afm detects the content change and removes its own stale synthetic answer so the rewritten file becomes visible again.
  - **Caught only by driving the actual UI in a real browser, not by inspection**: the first version of that companion fix removed the stale nudge answer but never stopped tracking the id once it was genuinely fixed — so the exact same "content changed" check kept firing on every later tick and deleted the next real answer.json too, silently discarding a human's actual reply to the now-working question. Reproduced live (clicked "Yes, continue" on the recovered question, the answer vanished from disk, the stage hung) before being fixed with a new `mcp.CanParseQuestion` check that stops tracking a key entirely once its rewrite is confirmed valid.
  - **A third bug, found while updating an existing test to the new behavior**: the unblock logic only freed an id once it detected the agent had rewritten the file — an agent that never responds to a nudge at all (crashed, ignored it, hung) never changes the content, so the retry count could never advance and the stage hung forever, the same failure class the whole feature exists to prevent. Fixed with `MalformedNudgeTimeout` (10s default, overridable in tests like the existing `RetryBackoff`/`MaxRetries`): a nudge is also considered "done" once the timeout elapses with no response, regardless of content. Verified against all three shapes of agent behavior in one real `afm run` through the dashboard — fixes its own JSON, never fixes it but keeps trying, and never responds at all — watching the event feed show exactly 3 attempts ~10s apart for the last one before the free-text fallback appeared.
  - Six new tests cover all three layers plus the two supporting fixes (`pkg/orchestrator/dialog_poller_test.go`, `pkg/mcp/dialog_test.go`, `pkg/server/handlers_test.go`), including one proving the dashboard's own "always show a pending question, even before dialog.jsonl catches up" fallback path also correctly hides a question mid-retry instead of leaking internal state to the user.

### Fix: a genuinely-finished stage could still hang forever behind an old, abandoned question — plus the architectural cleanup this pointed at

- A **third** real production log showed a stage that had asked and gotten answers to 15/15 questions, had its agent write a valid `execution_summary.md`, and exit cleanly — and still hung in `awaiting_user_input` forever. Root cause: a single question from hours earlier (an artifact of the reused-id bug above, abandoned via a manual workaround once the user moved past it) was still sitting on disk unanswered, and afm's own logic couldn't tell "genuinely still waiting on this" apart from "long-dead tail nobody will ever answer" — an open question, however stale, always overrode a real completion signal.
- Fixed at the source: `runWithRetry` (retry.go) now checks the phase's completion marker *before* checking for an open question, not after — a `nil` completion check (phases that don't have one) counts as already satisfied, so nothing about the original "hold for a legitimately open question" behavior changes for the case it was built for.
- **Then a live test of that exact fix immediately surfaced the same bug's twin**: `onAgentCompleted` (orchestrator.go) had its *own*, fully independent copy of the same "is there an open question" check — and it had already drifted out of sync with the fix above (patched one, not the other), reproducing the identical hang one layer downstream. Rather than patch the copy a second time, it was deleted outright: `EventAgentCompleted` has exactly two publishers (`runWithRetry`, and the script-completion path, which can never have an open question in the first place), so by the time the event is consumed, the decision has already been made correctly — the consumer doesn't need, and shouldn't keep, its own copy of that logic.
- **Widening the aperture further surfaced a third, structurally identical gap**: even with both checks fixed, afm's background question poller (a separate goroutine ticking every second) could independently move a stage to `awaiting_user_input` — because of the same kind of abandoned question — *while the agent process was still alive and about to finish for real*. The FSM's `EvComplete` rule and `completeStage`'s precondition only recognized `Running`/`Retrying` as valid stages to complete from; racing to `AwaitingUserInput` a heartbeat before the agent's own exit silently dropped the completion forever, with no process left alive to retry. Fixed by widening both to also accept `AwaitingUserInput`. Auditing for the same shape in the planning phase (not yet hit live, found by inspection) turned up the identical gap in `EvPlanReady` and `onAgentCompleted`'s planning branch — fixed the same way.
- Verified with a real `afm run` in the browser (a mock agent that leaves a stray question behind but finishes cleanly) and two new integration tests driving the actual race with a real subprocess and a well-timed `sleep`, not a synthetic status pre-seed: `TestIntegration_PollerRaceDoesNotStrandCompletedStage` and `TestIntegration_PollerRaceDoesNotStrandPlanningStage`.
- The broader lesson, now written down for future similar bugs: whenever a fact about stage readiness is derived from the filesystem (`FindUnansweredQuestions`, the various `Check*Completion` functions) and more than one place independently *acts* on that fact, those places are guaranteed to drift the next time only one of them gets edited. The fix isn't "patch both" — it's collapsing to one canonical decision point and one FSM transition table that actually enumerates every status a concurrently-running poller could race a stage into, not just the sequential happy path.

## 2026-08-18

### New: `paused` stage status — pause a stage on purpose, resume it later

- A new stage status, `paused`, for three cases: (1) `auto_run: false` in `flow.yaml` gates a stage's first activation — it pauses instead of starting, showing a panel with a Continue button, instead of running unattended; (2) a "Pause" item in the stage kebab menu gracefully stops an already-running/planning/revising/retrying stage (reuses the existing `interruptChans`/SIGINT mechanism `Revise` already used for agent_suggest); (3) script-only stages (`script:`) can only be paused via (1), before they ever start — mid-script graceful stop isn't architecturally possible (`RunScript` has no interrupt channel), so the Pause menu item is hidden once a script stage is running.
- `Continue` resumes a paused stage exactly the way afm already resumes a crashed-and-restarted one: `StageState.PausedFrom` (the status a stage was paused out of) feeds the same `resumeStageAtStatus` dispatcher `recovery.go` already used for post-crash recovery — "manually paused" and "process died mid-run" reduce to the same question, "the process this status implies isn't running, start it." A stage paused before ever starting (`PausedFrom: pending`) just re-runs the normal first-activation path instead.
- Built via `superpowers:subagent-driven-development` (14 tasks, fresh implementer + reviewer per task, one fix round on Task 13, final whole-branch review on Opus with one Important finding fixed in one fix wave) from a spec+plan (`docs/superpowers/specs/2026-08-17-paused-stage-status-design.md`, `docs/superpowers/plans/2026-08-17-paused-stage-status.md`). Three genuine plan defects found and fixed *during* implementation, not designed for up front: Task 3's `EvPause` FSM rule omitted `Pending` from its `From` list (the auto_run gate would have silently no-op'd); Task 1 silently broke a pre-existing hardcoded-status-list test (`afm-event.test.ts`) that wasn't caught until Task 11 ran the full frontend suite instead of just the build; the plan's own `App.tsx` snippet for the Pause kebab handler had no error handling, inconsistent with the file's own `handleSubmitNote` convention.
- The final whole-branch review caught what no single task's scoped diff review could: `pkg/web/dashboard/src/hooks/use-attention/use-attention.ts` (the header "Action needed" dot / favicon pulse / title flash / desktop-notification pipeline) never learned about `paused` — a stage sitting at the `auto_run:false` gate, the feature's flagship "stop and wait for me" scenario, gave a backgrounded tab zero out-of-focus signal. Fixed in one fix wave alongside two Minor findings (a stale 5-method `StageActions` doc comment, missing `--c-paused` CSS across three skins).
- **A live incident during manual verification surfaced a real bug the automated review missed entirely**: pausing a stage with `agents: [auto]` + `interactive: true` left the dashboard with *no visible way to resume it at all* — `pkg/server/stageview.go`'s `ShowPlan` computation treated `paused` the same as every other non-`failed` status for autonomous stages (i.e. don't show the plan panel, where the Continue button lives), a rule written for a world where autonomous stages could reach `failed` but never `paused`. Fixed (`showPlan := !autonomous || failed || paused`) and used the incident as a prompt for a dedicated audit of every stage-kind × `paused` combination, which turned up two more real bugs: `withBeforeHook` could double-spawn an agent if `Pause()` landed while a plain `script_before` shell script was still running in the background (no interrupt channel there, only the main agent gets one) — both from the paused stage itself resuming later *and* from an already-armed `Continue`; and `resumeStageAtStatus`'s `StatusRetrying` branch never checked for autonomous stages the way its `StatusRunning` sibling already did, so a `Continue` after pausing an autonomous stage mid-retry-backoff misrouted it into a real planning agent — for a stage that never has a `plan.md` and never goes through planning at all.
- Verified twice against a real `claude` agent through the actual dashboard in a real browser (Chrome DevTools MCP) inside the real `akopichin/afm:latest` Docker image, not mocks: once for the two headline cases (auto_run gate, manual pause + resume with `--resume` continuing the same session), and a second, dedicated 5-stage pass specifically exercising the three bugs found above — pausing exactly mid-`script_before`, mid-planning, and on both an autonomous auto_run-gate and a script auto_run-gate — confirming the Continue button, the resume, and the underlying file output were all correct in every case, and that a hook interrupted by `Pause()` finished silently in the background without spawning a duplicate agent.
- **A follow-up "any FSM leaks left?" audit found a fourth bug, same class as the `withBeforeHook` one, at a different entry point**: `SpawnAgent` queues its goroutine behind the `max_parallel` concurrency semaphore before `runWithRetry` ever runs, so `interruptChans` isn't registered yet — a stage re-paused while queued (e.g. `Continue()` resumed it straight into a full bucket, then the user hit Pause again before it got a slot) had nothing to signal, and once a slot freed up the queued call would still start a real agent on an already-paused stage. Initial fix: a `currentStatus == paused` check at the top of `runWithRetry`, mirroring `withBeforeHook`'s check.
- **Architectural follow-up, prompted directly by "why so many places that can leak — can't there be one place that controls this?"**: the two scattered checks are now one. `concurrency.Manager` (`pkg/orchestrator/concurrency/concurrency.go`) gained a `shouldRun func(stageID string) bool` field, checked by `SpawnAgent` right after the goroutine clears the semaphore and right before it calls `run()` — the exact point where a queued call wakes up, regardless of which of afm's many call sites queued it. `orchestrator.New` wires it with `func(id string) bool { return opts.Store.Get(id) != state.StatusPaused }`. This made the `runWithRetry`-level check fully redundant (removed, along with its now-superseded test) since every agent phase funnels through `SpawnAgent` before ever reaching `runWithRetry`; `withBeforeHook`'s check stays, since it guards a different window (the `script_before` hook's own execution time, which is *inside* `run()`, past where a single pre-run check can see). New regression test `TestSpawnAgent_SkipsRunWhenPausedWhileQueuedBehindSemaphore` proves the fix against the real semaphore-queueing mechanism (`ChannelSemaphore`), not just the predicate in isolation. Full suite + `-race` green on `pkg/orchestrator/...` after the change.
- **A fifth bug, the most serious yet, found during a full manual verification pass against a real `glm47` agent through the real dashboard**: `Continue()` could hang a whole flow forever. `resumeStageAtStatus`'s "already complete, recovered from disk" fast paths (an autonomous/script stage whose completion artifact was already written when it got paused) finalized the resumed stage directly, skipping the `failBlockedStages`/`startPlanningForUnblocked`/`startReadyStages`/`tryActivatePrePlanned` cascade every *normal* stage completion goes through — so nothing ever re-evaluated stages waiting on it as a dependency. They sat in `pending` forever; the only way out was restarting the whole `afm` process (whose startup bootstrap runs that cascade once after every stage, masking the bug there). Reproduced live: a `agents:[auto]` stage got manually paused right after writing its completion artifact, `Continue`'d cleanly to `done`, and its dependent never started. Fixed by routing those fast paths through the same `completeStage` chokepoint `onAgentCompleted` already uses (which gained a `reason` parameter so the specific "recovered execution_summary.md"/"recovered .done" log text isn't lost). New regression test `TestContinue_RecoveredCompletion_UnblocksDependent` proves a dependent stage actually unblocks, not just the resumed one — it initially passed for the wrong reason (a goroutine-scheduling race let the bootstrap's own cascade mask the bug) until stabilized with an explicit delay to force the `Continue()` code path specifically.
- Spec/plan: `docs/superpowers/specs/2026-08-17-paused-stage-status-design.md`, `docs/superpowers/plans/2026-08-17-paused-stage-status.md`.

## 2026-08-14

### Fix: dashboard UI could freeze mid-run (stuck stage/progress, permanent OFFLINE) after a long completed flow

- Diagnosed from a real production run's logs (a 13-stage review flow, ~1h23m): the durable event log/state (`events.jsonl`/`state.json`/`notices.jsonl`) showed every stage genuinely reached `done`, but the dashboard still showed a mid-flow stage as running, the footer stuck at `11/13`, and a permanent `OFFLINE` badge — a UI/connection-lifecycle bug, not an orchestration bug (no data loss, no stuck agent).
- Root cause: the header status badge, stage list, and footer are all fed by a single `useStatus()` object polled via a plain 3-second `setInterval` with no timeout/retry/backoff and no tab-visibility awareness (`pkg/web/dashboard/src/hooks/use-status/use-status.ts`), while the Event Feed panel is fed by a separate, self-healing WebSocket channel (reconnect + full-history resync on reconnect). Browsers throttle background-tab `setInterval` polling far more aggressively than delivery on an already-open WebSocket, so a tab backgrounded right as a long flow finishes can miss the existing `dashboardExitGrace` window entirely (a flat 5s hold added earlier, commit `d2ad944`) — by the time the poll would fire, the CLI process (and dashboard server) has already exited, and every later poll/reconnect attempt fails silently forever.
- Two complementary fixes:
  1. `useStatus` now forces an immediate `/api/status` refetch on `visibilitychange` (tab becomes visible) and `window focus` — a throttled background tab catches up the instant it's looked at again instead of waiting for its next, possibly delayed, poll tick.
  2. The CLI's fixed 5s sleep is replaced by `waitForDashboardDrain` (`cmd/afm/run.go`): still waits 5s (`dashboardExitGraceMin`) unconditionally, then keeps the dashboard/WS server alive while at least one client is still connected — tracked via a new `Server.ConnectedClients()` counter (`pkg/server/websocket.go`) — up to a bounded 2-minute ceiling (`dashboardExitGraceMax`), giving a throttled tab real headroom to notice completion without hanging forever if the tab is simply never closed.
- New tests: `pkg/server/websocket_clients_test.go` (client-count tracking), `cmd/afm/run_dashboard_drain_test.go` (drain-timing logic: min-grace floor, early exit on disconnect, hard ceiling, Ctrl-C short-circuit), plus three new cases in `use-status.test.ts` covering the visibility/focus refetch behavior.
- Found via `/superpowers:systematic-debugging` against a copied `.afm/runs/` log directory from the actual affected run, not reproduced live — no formal spec/plan doc for this one.

### New: `openai-agent` autoShim recipe — a real tool-loop for OpenAI-compatible providers with function calling

- The existing `type: openai` autoShim recipe only ever gives the model a single one-shot text completion — fine for `planning`/`review` stages, where afm just takes the raw text, but useless for `agents: [auto]` (autonomous) or `interactive: true` stages, which need the agent to actually write files, run scripts, and answer dialog questions. Plugging an OpenAI-compatible provider into those stage types via `type: openai` just stalled or failed: no tool calls were ever made, so no side effects ever happened.
- New recipe type, `type: openai-agent`, for any OpenAI-compatible `/chat/completions` endpoint that supports real function calling (`tools`/`tool_choice`, including streamed `tool_calls` in the standard index-keyed delta format). The generated wrapper execs a new adapter script, `openai-agent-as-claude`, which runs an actual multi-turn loop: call the API, execute any returned tool call for real, feed the result back into the conversation, repeat until the model answers with plain text or a configurable `max_turns` cap (default 40) is reached.
- The model gets exactly **one** tool — `bash` (run a shell command, return stdout+stderr+exit code) — deliberately, not a set of distinct read/write/skill tools. afm's own stage-completion and file-based dialog protocols are already purely filesystem-poll-based (an autonomous stage just needs `execution_summary.md` to exist; an interactive stage just needs `question.json`/`answer.json` files), so a single shell-command tool is sufficient to satisfy both, plus running project scripts and even blocking-poll dialog waits (the model runs the same `while [ ! -f answer.json ]; do sleep …; done` loop a real agent would, as one long-running tool call). A short system-prompt note teaches the model the one non-obvious convention it needs — that a mentioned "skill" is a markdown file it should read itself via `bash` rather than a built-in tool.
- Each executed tool call is printed live as a claude-shaped `tool_use` stream-json line (the same shape a real `Bash` tool call produces) as soon as it runs, not batched at the end — this drives the dashboard's live action feed during the loop and also resets afm's 30-minute idle-timeout between turns, instead of the process going silent until the whole multi-turn task finishes.
- Deliberate error-handling split: hitting `max_turns` without a final answer is a graceful stop (exit 0, a note appended to the output) — afm's existing incomplete-work/retry handling for autonomous stages already covers this case correctly. An actual request failure (network error, non-2xx) is a hard failure (exit 1) — unlike the existing one-shot `type: openai` adapter, which intentionally swallows a request failure into an empty "success" (safe for a single best-effort text completion, but wrong here: a silently "successful" empty tool-loop would hide a genuinely broken run instead of surfacing it).

### Fix: dashboard's auto-selected stage could get stuck forever on fast, back-to-back script stages

- `App.tsx`'s auto-advance (moves the selected stage forward once it finishes) only ever checked in the exact poll tick the *selected* stage transitioned `!done → done`, then searched forward for a stage already in `ACTIVE_STAGE_STATUSES`. Script stages (`Stage.IsScript()`) can run so briefly (a plain shell command) that a whole extra stage finishes between two 3s `/api/status` polls — by the time the frontend finally saw stage1 as `done`, stage2 had *also* already raced through `running → done`, so nothing downstream was active in that snapshot. The old code gave up right there: it never rechecked, so the selection sat on the finished stage1 indefinitely even once stage3/4 were genuinely running — reported as the dashboard "залипает" (freezes) on the first script stage in a chain of 2–4.
- **Fix:** replaced the one-shot check with a `wasLive` ref that persists for as long as a given stage stays selected (reset only when `selectedStageId` itself changes, e.g. a manual click) — as long as the selected stage is `done` and was observed non-`done` at some point under this selection, the forward search for the next active stage re-runs on *every* poll instead of only the one tick it first turned `done`. This self-corrects within one poll interval instead of sticking forever. The existing "manually re-selecting an already-finished stage doesn't get yanked back to the active one" behavior is unchanged (a stage selected by click while already `done` never sets `wasLive`, so the forward search never fires for it).
- Regression test added (`App.test.tsx`) reproducing the exact race: stage1 finishes with nothing yet active downstream (old code would stick here forever), stage3 becomes active on the *next* poll — asserts the selection catches up. All existing auto-advance tests (single-hop advance, manual-selection-sticks) still pass unmodified.

### New: persistent IDLE/BACKOFF footer metrics — survive reload/restart, freeze offline
- The footer's `IDLE`/`BACKOFF` counters (added 2026-07-29) were computed entirely client-side by replaying `stage_status_changed` events held in the browser's capped 200-event cache (`useIdleTime`/`useStatusDuration`) — accurate within one open tab, but a page reload (or an `afm` process restart) reset both counters to zero, and on a long run even a live tab could lose older episodes once they aged out of the cache. `STARTED`/`ELAPSED` never had this problem, since they're just `now - StartedAt` against a server-persisted anchor.
- **Fix: moved accounting server-side, incrementally.** `RunState` (`pkg/state/state.go`) gained two accumulators, `IdleAccumulatedMs`/`BackoffAccumulatedMs`, persisted in the snapshot and restored by replaying `events.jsonl`. A single helper, `accountIdleAndBackoff(rs, stageID, to, t)`, updates both — using `rs.Stages` as it was *before* the transition is applied — and is called from **both** places that apply transitions to a `RunState`: the live path (`Store.Apply`) and the replay path (`parseEventLog`, used by `Store.Open`/`LoadRunState`). These are genuinely separate code paths (`parseEventLog` doesn't go through `Apply`), so calling the helper from only one of them would have silently diverged the live-run numbers from what a restart recomputes.
- **Idle is a single flow-wide condition** (`isIdle`), not a per-stage sum: idle whenever any stage is `awaiting_user_input`/`awaiting_approval`, OR a stage is `failed` while no stage is actively `running`/`planning`/`revising` (`retrying` deliberately doesn't count as "active" — it's passive backoff, tracked separately). **Backoff sums in parallel, not merged:** several stages simultaneously `retrying` accumulate independently, the same simplified model the original `useStatusDuration` used. `IdleSince()`/`BackoffOpenSince()` are computed on read from `Stages[].UpdatedAt` (idle: the max across all stages; backoff: each stage currently `StatusRetrying`) rather than persisted — the accumulators only need to capture *closed* episodes.
- **Two accuracy bugs fixed along the way, found while wiring replay to match the live path exactly:** (1) `Store.Apply` (via `SetStageStatus`) called `time.Now()` a second time after the fsync that already had a timestamp in hand, so the time recorded in the log and the time used for accounting could differ by the fsync's duration — fixed with `SetStageStatusAt(t.Time)`, using the one timestamp that actually went into the log. (2) `NewRunState` used to stamp untouched `pending` stages' `UpdatedAt` with `time.Now()` at construction time — harmless on a fresh run, but on every `Store.Open` during a resume, "now" is the moment the process restarted, not any real transition, and this fabricated timestamp would win `maxUpdatedAt()`'s max over genuine historical transitions, corrupting `IdleSince` and undercounting Idle after every restart. Fixed by leaving it as the zero value, which the max/accounting logic already treats as "no transition yet."
- **API:** `/api/status` now returns `idle_accumulated_ms`, `idle_since` (omitempty), `backoff_accumulated_ms`, `backoff_open_since` (`[]time.Time`, empty when nothing is currently open).
- **Frontend: anchor + tick, no more event replay.** New `useIdleMs`/`useBackoffMs` (`pkg/web/dashboard/src/hooks/`) compute `accumulated + (now - since)` the same way the already-working `useElapsed` does, and take a `connected: boolean` — while `false`, the displayed value just holds still instead of ticking off a stale `since` from before the WebSocket dropped; on reconnect, `useStatus`'s poll delivers an already-corrected server anchor, no client-side catch-up math needed. This replaces `useIdleTime`/`useStatusDuration` outright (both deleted, along with their now-dead imports in `App.tsx`/tests) — those hooks derived state from `useEventFeed`'s 200-event cache, which silently underreported both counters on long runs once old transitions aged out.
- `ELAPSED`/`STARTED` were untouched — they were already restart-safe and, by design, keep ticking through an offline WebSocket.
- Spec/plan: `docs/superpowers/specs/2026-08-07-persistent-idle-backoff-design.md`, `docs/superpowers/plans/2026-08-07-persistent-idle-backoff.md`.

### New: `afm init` rewritten as an archetype-driven wizard, plus `afm validate`

- The old `afm init` only asked for id/name/description/`depends_on`/`agents` per stage, one blind text field at a time — no exposure to `artifacts`/`inputs`, `verify`, `interactive`, `script`, or `plan:`, and no way to know if the result was even valid before a real `afm run` spun up actual agents.
- **New wizard flow:** pick one of four archetypes first — single change (`planning → implementation → review`), build + verify loop (`build` with a `verify:` gate → `check`, one auto-retry on failure), parallel tracks → integration (N independent stages merging into one), or fully custom stage-by-stage. Each stage then asks: stage mode (standard agent stage / `auto` / `script`), for standard mode whether it already has a plan file or needs a planning agent, which phases to run (`implementation`/`review`, multi-select), and one optional "advanced settings?" question gating artifacts/inputs/verify/interactive/custom-command instead of always asking all of them.
- **New: `afm validate <flow.yaml>`** — dry-run schema check (cycles, unknown `depends_on`/`inputs` references, etc.) via the existing `flow.ParseFile`, with no agents spun up. The wizard now runs this on its own output before declaring success, and offers edit-manually / restart / exit if it's invalid.
- `pkg/flow`'s `Flow`/`Stage`/`Artifact`/`Input` YAML tags gained `omitempty` (plus inline `flow`-style lists for `agents`/`skills`/`depends_on`) — needed because the project had only ever `Unmarshal`ed these types, never `Marshal`ed them; without this, the wizard's generated flow.yaml would have every zero-value field (`command: ""`, `verify: ""`, `supervisor: false`, …) printed out.
- **A real schema-validity bug caught during design review, before any code was written:** the natural first choice for the verify-loop archetype's `check` stage was `agents: [review]` with no planning agent — but `flow.Flow.validate()`'s "must have planning agent, a plan path, or script" rule rejects exactly that combination, so every verify-loop flow the wizard generated would have failed its own validation. Fixed by defaulting `check` to `script` mode instead (mechanical check, paired with `build`'s `verify:`) before implementation started; a dedicated test (`TestBuildVerifyLoopStages_CheckDefaultsToScriptAndIsValid`) round-trips the generated flow through the real `flow.ParseFile` as a permanent regression guard.
- **A second bug caught by the final whole-branch review, not any per-task review:** `buildParallelTracksStages` read the "how many tracks?" answer with no lower bound, so typing a negative number crashed the wizard outright (`runtime error: makeslice: cap out of range`). Fixed with a one-line clamp to at least 1 track, with its own regression test.
- Old `afm init` implementation (`stageInput` struct, line-by-line `prompt()` loop, manual YAML string-building) fully removed — no compatibility shim.
- Built via 8 TDD tasks (fresh subagent per task, spec/quality review after each) plus a whole-branch review; two cosmetic minors (a test-name scope nit, and restarting the wizard mid-repair-loop can orphan the previous invalid file on disk under a different flow name) were parked as deferred rather than fixed.
- Spec/plan: `docs/superpowers/specs/2026-08-05-init-wizard-design.md`, `docs/superpowers/plans/2026-08-05-init-wizard.md`.

## 2026-07-31

### New: `auto_recover` config flag — auto-retry failed stages on run start/resume

- Killing the process or Docker container mid-run used to leave the interrupted stage (and everything cascaded from it via `blocked_by_dep`) stuck in `failed` forever — `afm run` would resume the run dir, but `startPlanningForPending` deliberately left terminal `failed` stages untouched, so every one of them needed a manual `afm retry <id>` before the flow could continue.
- **New:** `auto_recover` (top-level config, default `true`) resets every stage currently `failed` back to `pending` as the very first thing a run does on start/resume (`autoRecoverFailedStages()`, called at the top of `startPlanningForPending`) — reusing the same `Failed → Pending` FSM transition the dashboard's manual retry button already used, and the same stale-interactive-session cleanup manual retry does. All failed stages are reset regardless of why they failed (no reason-based filtering — deliberately simple). No new ordering logic was needed: a reset stage just re-enters the same `depsDone()`-gated pending flow every never-yet-run stage already goes through, so `depends_on` order falls out for free. Set `auto_recover: false` to go back to requiring manual retries.
- Built via 4 TDD tasks (fresh subagent per task, spec/quality review after each), a whole-branch review, and one fix round (a stale doc comment plus a missing spec-listed test for the "only touches `failed`, never `done`/`awaiting_approval`" selectivity guard).
- **Verified live end-to-end, twice, against a locally built Docker image** (`akopichin/afm:auto-recover-test`, same `Dockerfile.runtime` the real release uses): a 5-stage sequential flow, letting 2-3 stages complete, then `docker kill`-ing the running container mid-stage and re-running `afm run`. The log line `auto_recover: stage "s4" failed -> pending` (and `s5`) appeared, `events.jsonl` recorded the `manual_retry`/`auto_recover` transitions, and the flow completed all 5 stages with zero manual intervention.
- **A real, pre-existing bug found only by that live Docker test, unrelated to `auto_recover` itself:** `docker kill`'s default SIGKILL gives the container's `afm` process no chance for graceful shutdown, so a script stage killed mid-execution is left in `running` (not `failed`) with no `.done` file. The `StatusRunning` resume branch of `startPlanningForPending` never checked `Stage.IsScript()` before falling through to `runImplementationAgent` — which unconditionally looks for `plan.md`, a file script stages never write — so the stage failed immediately on the very first resume attempt with a spurious `plan.md: no such file or directory` instead of just restarting the script. Fixed by mirroring the `IsScript()` check `retryStage` (manual retry from the dashboard) already had, checked before the `IsAuto()`/autonomous branch since a script stage is never autonomous. Regression-tested (`TestRecovery_ResumesScriptStageStuckRunning`) and re-verified live on a rebuilt image with the exact same kill-mid-stage scenario — the stage now just restarts the script and the flow completes normally, no `failed` transition at all.
- Spec/plan: `docs/superpowers/specs/2026-07-31-auto-recover-design.md`, `docs/superpowers/plans/2026-07-31-auto-recover.md`.

### New: `script` stages and `script_before`/`script_after` hooks — shell steps without an LLM agent

- A stage can now run a plain shell script instead of an AI agent (`script: |`) — for glue steps like notifications, deploy commands, or a linter run that don't need an LLM. It skips planning/approval entirely: as soon as its dependencies are done, the script runs and the stage moves straight to `done`/`failed` on exit code.
- **`script_before` / `script_after`** are hooks that run immediately before/after *any* stage's own content (agent, autonomous track, interactive dialog, or another script) — orthogonal to stage type, so they combine freely with `agents`/`supervisor`/`interactive`/etc. Both hooks retry automatically on failure (3 attempts, 1s/2s/3s backoff). If `script_before` still fails, the stage blocks in a new `hook_failed` status until you hit **Retry** or **Skip** on the dashboard; if `script_after` still fails, the stage is **not** reverted from `done` — same Retry/Skip notice, but non-blocking. `script_timeout`/`script_before_timeout`/`script_after_timeout` (default `5m` each, added during final review — the first version left scripts unbounded when no explicit timeout was set) bound how long each is allowed to run.
- Output streams to the dashboard's event feed (`[hook] line`) and to the same Log panel an agent's output shows up in.
- **A genuine crash-recovery gap, found during the whole-branch review**: a stage that finished its real work right before `afm run` crashed used to skip `script_after` entirely on resume (the recovery path fired the completion transition directly, without the after-hook call the live path already had). Fixed by wiring the hook into every recovery completion site, with a dedicated regression test simulating exactly that crash window.
- **Two subtle concurrency bugs, caught by the implementers' own `-race` runs mid-build, not by review:** (1) a TOCTOU race where a `hook_failed` transition was published before the decision-wait channel was registered, so a fast resolver (dashboard button, automation) could lose the decision; fixed by registering the channel first. (2) A stage's shutdown could kill a freshly-spawned `script_after` goroutine before it ran, since after-hooks never touch the FSM status `shouldExit()` normally waits on; fixed with a small in-flight counter scoped only to after-hook goroutines (deliberately not touching the counter/timing of any other stage type, verified by re-running the full non-hook integration suite before/after).
- **Two more bugs found only by testing an actual Docker build in a real browser** (not caught by any unit/integration test): the Dockerfile's multi-source `COPY --from=web` step for `assets`/`skins` silently kept an old dashboard bundle instead of the freshly-built one whenever a differently-named file already existed at the destination — meaning **every Docker build had been serving a stale frontend** since before this feature, unrelated to it but only surfaced by testing it; and `RunScript` logged output with type `"stdout"`, while the dashboard's Log panel only recognizes `"text"`, so script/hook output never showed up there. Both fixed.
- **A third bug found only by watching the event feed live**: script/hook output was published only to the ephemeral live WebSocket (the same mechanism `agent_action` already used) — a dashboard that connected even a couple of seconds after a fast script finished would never see its output in the feed (only the Log panel, which reads the log file from disk). Fixed by also recording it durably (`appendNotice`, the same mechanism `agent_completed`/`context_warning` already use for `/api/events` replay) — verified live by deliberately connecting 10 seconds after a fast stage finished and confirming the feed caught up.
- Built end-to-end via 19 TDD tasks (fresh subagent per task, spec/quality review after each, adversarial review on the concurrency-sensitive ones), a whole-branch review that caught the crash-recovery and timeout-default gaps above, and a dedicated regression audit — comparing the modified `startReadyStages`/`retryStage`/`onAgentCompleted`/recovery/`/log`-endpoint/dashboard code line-by-line against the pre-feature baseline — confirming zero behavioral change for every pre-existing (non-script) stage type.
- Spec/plan: `docs/superpowers/specs/2026-07-29-script-stages-and-hooks-design.md`, `docs/superpowers/plans/2026-07-29-script-stages-and-hooks.md`.

## 2026-07-29

### Fix: event feed's sticky auto-scroll and "↓ latest" button lost their state on maximize/restore
- `Maximizable` (the component behind every panel's fullscreen toggle) used to switch between rendering `<>{children}</>` and `createPortal(...)` depending on maximize state — two structurally different element types at the same tree position, so React unmounted and remounted everything inside on every toggle. That silently reset the event feed's `useStickToBottom` state: scrolling up to read history, then maximizing/restoring the panel, snapped the feed back to the bottom and hid the "↓ latest" jump button — exactly backwards from what a user reviewing history would want.
- **First attempt was wrong, caught mid-implementation:** the original plan kept `createPortal` but only switched its `container` argument (an anchor div ↔ `document.body`), reasoning React would treat that as an in-place update. It doesn't — verified directly with a minimal repro that a portal's container is part of its identity for React's reconciler, so changing it between renders remounts the subtree just as much as switching Fragment↔Portal did.
- **Actual fix:** dropped portals from `Maximizable` entirely. A single stable `<div>` never leaves its position in the tree; only its `className` toggles between normal in-flow layout and a fullscreen `position: fixed` overlay (`maximize-overlay`, unchanged CSS). Since the div's type and position never change, React only ever diffs props — never unmounts. Safe in this codebase specifically because no ancestor between `Maximizable` and `document.body` sets `transform`/`filter`/`perspective`/`contain`/`will-change` or a `position` + non-`auto` `z-index` combination that would trap the fixed overlay (checked directly against `react-resizable-panels`' own styles and this project's CSS).
- Verified end-to-end in a real Chrome tab against a locally built Docker image (`local/afm:dev`, same `Dockerfile.runtime` the real release uses) driving a live `afm run`: scrolled the feed to the top, maximized the panel, restored it, and confirmed both the scroll position and the jump button survived the round-trip — the exact regression this fixes.
- Spec/plan: `docs/superpowers/specs/2026-07-29-dashboard-event-feed-ui-fixes-design.md`, `docs/superpowers/plans/2026-07-29-dashboard-event-feed-ui-fixes.md`.

### New: Idle and Backoff counters in the footer
- Previously there was no way to see, at a glance, how much of a run's wall-clock time was spent waiting on you vs. burned on automatic retry backoff.
- **New footer counters**, next to the existing `Elapsed`: **Idle** — time the flow was genuinely waiting on you; **Backoff** — cumulative time in automatic `retrying` backoff, no user involved (`useStatusDuration(events, BACKOFF_STATUSES)`, `pkg/web/dashboard/src/hooks/use-status-duration/` — a generic per-status-set duration accumulator, processing `stage_status_changed` incrementally so a closed episode survives the frontend's capped 200-event buffer).
- **Idle's real-world semantics, found and fixed same day:** the first version summed each stage's own time in `awaiting_user_input`/`awaiting_approval`/`failed` independently. In a real run this produced a wrong reading: retrying a stage (agent genuinely working) while *downstream* stages sat cascaded-`failed` (`blocked_by_dep`, waiting on the upstream stage — see the `runAutonomousAgent`/downstream-retry fix in the 2026-07-27 entry) kept Idle climbing the whole time, even though nothing was actually waiting on the user.
- **Fix:** Idle is now a single flow-wide condition, not a per-stage sum — `useIdleTime(events)` (`pkg/web/dashboard/src/hooks/use-idle-time/`): `idle(t) = a question is open on any stage (awaiting_user_input/awaiting_approval) OR (a stage is failed AND no agent is currently active — running/planning/revising)`. A pending question always counts, regardless of what else is running; a merely-`failed` stage stops counting the instant any agent becomes active elsewhere, and resumes the moment nothing is. (`retrying` counts as neither a question nor "active" — it's passive backoff, tracked separately.) Same incremental, truncation-surviving processing as `useStatusDuration`, now walking the whole stage timeline instead of one stage's own episodes.
- Verified live against a locally built Docker image, plus a dedicated regression test (`App.test.tsx`, "a cascaded-failed downstream stage does not count as Idle while another stage is actively running"): Idle stays at `0:00` while an upstream stage runs with a downstream stage failed, and only starts climbing once the upstream stage finishes and nothing is left active.

### Fix: "thinking" indicator kept showing while the dashboard was offline

## 2026-07-15

### Retry on 529/502/503/504 + removal of proxy and accounting

### claude wrappers: bounded retry + stream-json + `--bare` (config `claude_bare`)
- **Bounded retry loop** (`pkg/orchestrator/retry.go`): fixed `RetryBackoff=5s` × `MaxRetries=15` (as in ralphex), replacing the previous exponential `[5s,10s,30s]` (4 attempts). z.ai 529 is transient; this survives the overload window. Confirmed: claude sends `stream:true` itself (via `--output-format stream-json`), so force-streaming isn't needed.
- **`--output-format stream-json` + `--include-partial-messages`** added to generated claude wrappers (`pkg/docker/wrapper.go`): covers non-interactive stages (which the executor doesn't pass ExtraArgs to) and gives partial deltas. `--output-format` is deduplicated (interactive stages already get it via the executor).
- **`--bare` + config `client.claude_bare`**: `--bare` = claude Code minimal mode (skips CLAUDE.md/hooks/skills/memory), body ~4 KB instead of ~127 KB (lower load on z.ai). **BUT `--bare` breaks the Skill tool** — goga-* skills stop resolving (the agent has to imitate them itself). So **default is `claude_bare: false`** (skills matter more). `claude_bare: true` is for flows WITHOUT skills.

### `type: cursor` — Cursor Cloud Agents API
- The Cursor Cloud API (`api.cursor.com`) **has no** synchronous OpenAI `/v1/chat/completions` (returns 404) — it's a **Cloud Agents API**: an async, run-based API where "chat" means starting a cloud code agent. So `type: openai` (which hits `${BASE_URL}/chat/completions`) **never worked and cannot work** with Cursor. The historical note about "Cursor via `api2.cursor.sh`" under `type: openai` was wrong — removed.
- New recipe type `type: cursor` → a wrapper with `CURSOR_*` env (`CURSOR_API_KEY`/`CURSOR_BASE_URL`/`CURSOR_MODEL`) and `exec /usr/local/bin/cursor-as-claude`. The adapter: reads the prompt from stdin → `POST /v1/agents` (no-repo, `mode:"agent"`) → polls `GET /agents/{id}/runs/{runId}` until a terminal status (`FINISHED`/`ERROR`/`CANCELLED`/`EXPIRED`) → emits claude stream-json (an `assistant` envelope with the `result` text + a `result` event) → archives the agent (best-effort, to avoid leaving clutter). `model: auto` (or empty) → the `model` field is omitted, Cursor uses its default.
- `auth.to` for cursor is any `env:VAR` (conventionally `CURSOR_API_KEY`); `url` is required (`https://api.cursor.com/v1`). Doesn't require `claude` in PATH (unlike openai). Requires `jq`+`curl` in the image. Tests: `TestAgentRecipe_CursorType`, `TestCreateWrappers_CursorTemplate`/`_CursorNoClaudeRequired`.
- **Note:** the first response takes ~30–90s (cloud-VM startup when the agent is created); the run itself is fast afterward (`durationMs` in seconds). Tolerable for interactive dialog, but not instant.

## 2026-07-14

### Docker `autoShim` — generated wrappers without mounting
- With the flag `docker.autoShim: true` afm **generates claude-compatible wrappers** for recipe agents (`docker.agents.<cmd>`) directly in the container — without `-v` mounting the host binary and without `extra_mounts` for tokens. The real wrappers (`glm47`/`glm51`/`glm52`/`deepseek-v4`) are "model+url+auth+sysprompt → `exec claude`", so they're described as a recipe and regenerated.
- **Recipe:** `model` (required → `ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS}_MODEL`, one for all 3 tiers), `url` (gateway), `system_prompt` (`file:<path>` → `--append-system-prompt-file`), `auth.from` (`env:VAR` | `file:<path>` — where afm reads the secret on the host) + `auth.to` (`env:<VAR>` ∈ {`CLAUDE_CODE_OAUTH_TOKEN`,`ANTHROPIC_API_KEY`,`ANTHROPIC_AUTH_TOKEN`}).
- **Data flow:** the host reads the secret and sysprompt content from host-only files → transient env `AFM_SECRET_<CMD>`/`AFM_SYSPROMPT_<CMD>` (bare-form `-e`, value doesn't end up in the `docker run` argv); the container gets `url`/`model`/`auth.to` from the mounted `config.yaml`. The wrapper bakes in `ANTHROPIC_BASE_URL` (by host-match against `proxy.upstream` — z.ai routes through the proxy for 529-protection, deepseek goes direct), substitutes the secret from the transient env, `unset`s it, and `exec`s the absolute `claude`.
- **Unified wrapper-dir** (`docker.CreateWrappers`) = claude proxy-shim + generated wrappers; `proxy.CreateShim` removed. `orchestrator.proxyForCmd` is now generated-aware (`generated` → self-route via the baked `BASE_URL`, wrapper-dir on PATH). `docker.ScanCommands` skips generated (not mounted); `docker.UsedRecipes` — secrets are resolved only for recipes actually used in the flow (no false fail-fast / no leaking secrets of unused agents). Missing secret → fail-fast with the agent's name. `afm-init` adds `.afm/secrets.env` to `.gitignore`.
- **Bonus:** a recipe can describe a docker-only agent whose binary doesn't exist on the host (e.g. `deepseek-v4`) — `autoShim` generates it in the container.
- Spec: `docs/superpowers/specs/2026-07-14-docker-autoshim-design.md`.

### `type: openai` — OpenAI-compatible providers
- A recipe with `type: openai` → a wrapper with `OPENAI_*` env (`OPENAI_API_KEY`/`OPENAI_BASE_URL`/`OPENAI_MODEL`) and `exec /usr/local/bin/openai-as-claude` — a bash translator: reads the prompt from stdin, calls `${OPENAI_BASE_URL}/chat/completions` (stream=true), translates SSE into claude stream-json. Supports Cursor (`api2.cursor.sh`), DeepSeek, local LLMs, and any OpenAI-compatible endpoints.
- `auth.to` for openai is any `env:VAR` (NOT limited to ClaudeAuthEnvVars); `url` is required. Requires `jq`+`curl` in the image (added to `Dockerfile.runtime`).
- Backward compat: empty `type` (or `"claude"`) = previous claude behavior; unknown `type` value → validation error.

### Fix: generated wrapper wasn't found (executor LookPath)
- `exec.Command` resolved the bare command (`glm47`) via `LookPath` against the parent process's (afm's) PATH, while the wrapper-dir (`ProxyShimDir`) was only added to the child's env → `start glm47: executable file not found`. The executor now resolves the command to `ProxyShimDir/<cmd>` (absolute path); for mounted binaries it falls back to the bare name. Regression test `TestRunAgentResolvesWrapperCommand`. Without this fix autoShim didn't work end-to-end.
